## 二、关键问题与优化记录

### 1. RAG 能回答 FAQ，却无法稳定回答真实售后问题

相关提交：1ebd31b、cfd31b9、f639599

- **问题或踩坑：** 商品推荐和精确 FAQ 能工作，但退款、物流、优惠券等具体意图可能绕过 RAG；旧逻辑只看最高候选分数，再把整批候选都注入上下文。Qwen3 Rerank 升级时还出现了“只换模型名但请求协议未切换”的问题，合法的 0.0 分数也曾被 Python 的 or 链吞掉。
- **优化与修复：** 建立按意图区分的固定 RAG 路由；按每条证据的来源和分数量纲独立过滤；缓存命中后重新校验知识版本和证据门槛；为 compatible/native Rerank 分别实现请求与解析，并保留超时、熔断和 RRF 降级。
- **效果与证据：** 34 条本地 RAG 评测中，Recall@K 和 MRR 均为 0.9167，引用率 0.9167，无答案 F1 为 0.9524；保留“会员升级”和“订单后改地址”两个失败样本，没有通过删题制造满分。
- **面试表达：** 我先区分“没有检索”“检索到噪声”和“模型没有使用证据”，再分别修路由、过滤和生成校验，而不是把所有问题归因于模型能力。

### 2. 检索分数量纲混用，融合排序表面生效、实际失真

相关提交：1ebd31b、892f13e、c0b6411

- **问题或踩坑：** 同一个阈值同时比较 cosine、Elasticsearch score、BM25、RRF 和 rerank 分数，语义完全不同；RRF 分又被原始 BM25 分覆盖。推荐只有单一召回时，结果容易集中在同一品类。
- **优化与修复：** 将 cosine、引擎原始分、融合分和 rerank 分拆成独立字段与阈值；文本与向量采用 RRF 融合；增加品类、浏览、购买和共同购买召回；超量召回后使用 Cross-Encoder Rerank 和 MMR，在相关性与多样性之间做约束。
- **效果与证据：** 30 条真实商品目录离线集达到 Recall@10 0.9333、MRR@10 0.8250、NDCG@10 0.8411；“蒸烤一体机”和“100W 车载充电器”仍作为 zero-hit badcase 保留。
- **面试表达：** 检索优化不是盲调一个阈值，而是先保证每个分数的物理含义正确，再讨论融合、重排和业务约束。

### 3. Redis 被当作长期记忆事实源，用户约束会丢失或被摘要改写

相关提交：508f980、621e3b2、4808450、d9ae0e6

- **问题或踩坑：** 预算、品牌和使用场景只存在 Redis，TTL 或重启后会消失；LLM 摘要可能把“预算 3000 元”压成“预算有限”，无法继续做硬过滤；后台抽取若整体覆盖，还会用空值或脏值污染已有画像。
- **优化与修复：** MySQL 保存结构化购物档案，Redis 只做缓存；显式用户表达优先于摘要和隐式行为；长文本的 LLM 富化异步执行并设置 8 秒上限，结果严格归一化后做增量 merge；清除聊天只推进可见历史游标，不删除长期记忆。
- **效果与证据：** 预算、品牌、用途和负向偏好可以跨会话保存，Redis 丢失后可从 MySQL 回填；用户可以查看、删除或关闭个性化；异步富化失败不阻塞主对话。
- **面试表达：** 我把短期对话、摘要记忆、长期偏好和 RAG 知识分开治理，并明确每类信息的事实源、优先级和生命周期。

### 4. “请模型输出 JSON、记得调工具”不是运行时保证

相关提交：3bfd41f、d5ca74f、f639599

- **问题或踩坑：** 自由文本 JSON 解析失败时可能落入过宽分支；订单、物流和优惠券事实问题如果模型跳过工具，仍可能生成看似合理的答案。资金风险词曾在风险表和意图表分别维护，出现一边识别、一边漏路由。
- **优化与修复：** Provider 支持时优先结构化输出，失败进入确定性安全回退；必需事实工具由图节点强制补调；工具失败必须显式降级；资金风险词改为单一事实源派生意图表，避免两份规则漂移。
- **效果与证据：** 同一冻结集上，资金风险相关基线由 96/112 提升到 99/112，数据 SHA 未改变；后续冻结会话集扩展为 134/134，覆盖意图、工具选择、参数、注入和写操作边界。
- **面试表达：** Prompt 是软约束，结构化 schema、确定性路由和服务端工具校验才是可测试的协议。

### 5. 自然语言售后已经表达清楚，系统却仍要求用户手输订单号

相关提交：d5ca74f、32ef02c、d9ae0e6

- **问题或踩坑：** “没发货的耳机我要退款”已经被识别成退款，但旧链路假设用户会提供订单号，模型无法可靠拼出订单项 ID；多笔相似订单时自动猜测还可能造成错单风险。
- **优化与修复：** 在 LLM 和写工具之前增加确定性 OrderReferenceResolver，按用户归属、显式 ID、订单状态、时间、商品、品牌、型号和规格逐层过滤；唯一候选自动继续，多候选返回持久化选择卡；选择过程用行锁保证幂等，Worker 执行前再次校验最新状态。
- **效果与证据：** 真实完整栈中，无需输入订单号即可定位 SM202608050002 / SMITEM202608050002 并生成退款确认卡；确认前订单和订单项状态保持不变。“收到的东西坏了”场景还暴露并修复了待付款订单误入候选的问题。
- **面试表达：** 开放自然语言由模型理解，但身份、订单定位和业务资格采用确定性规则和权威数据，模糊时主动澄清而不是让模型猜。

### 6. 请求 token 防不了同一业务动作换 token 重复执行

相关提交：b4a1044、d5ca74f、32ef02c、4cbba4d

- **问题或踩坑：** action token 只能防同一 token 重放，用户仍可能为同一订单重新生成另一个 token；HTTP 超时也无法证明远端到底提交成功还是失败，直接重试可能重复产生副作用。
- **优化与修复：** 使用 userId + actionType + 业务资源构造 business key，并对规范化参数计算指纹；活跃业务键由数据库唯一约束占位；未知结果进入 INCONCLUSIVE，只查询 Java 幂等账本和领域状态，达到时间或次数边界转 MANUAL_REVIEW，禁止自动重放副作用。
- **效果与证据：** 同业务同参数复用原提案，不同参数冲突；重复确认只产生一个终态和一次业务效果。多智能体重构后，所有 PROPOSE 工具进一步收口到 root Supervisor。
- **面试表达：** 我区分了传输层 token、业务幂等键和远端未知结果，并明确项目实现的是“幂等账本 + 有界对账 + 人工复核”，不是 exactly-once。

### 7. 单元测试通过，不代表 Worker、MQ 和 WebSocket 故障时能够收敛

相关提交：d5ca74f、f052e3b

- **问题或踩坑：** Worker 被杀、RabbitMQ 暂停、重复投递或 checkpoint Redis 故障时，单纯的状态机测试无法证明任务不会丢失或重复执行；WebSocket 先推送后落库还可能让客户端看到数据库中不存在的 DONE。
- **优化与修复：** 建立任务账本、lease、续租、fencing、checkpoint 和恢复扫描；业务终态先落库再推送；前端按 messageId 幂等合并 PARTIAL/DONE；使用独立 Compose 环境真实 kill Worker、停止 RabbitMQ 和 Redis。
- **效果与证据：** 六条故障断言全部通过：Worker 租约接管后只有一个 effect；RabbitMQ 恢复后任务只执行一次；重复投递只有一个终态；checkpoint 失败时任务进入 DEAD，绝不误报成功。
- **面试表达：** 可靠性不能只看 happy path，我会验证“进程在哪一步死掉”以及数据库、队列、客户端最终各自看到什么。

### 8. 推荐归因只信浏览器 requestId，无法支撑可信质量评估

相关提交：10801b5、ed000b3、90ed4db、3d799d0

- **问题或踩坑：** 客户端可以伪造曝光、点击、商品或位置；Redis 快照过期后没有可审计事实；只看 CTR/CVR 也无法反映误导推荐带来的退款、退货和差评。
- **优化与修复：** 将曝光和点击持久化，Java Cart/Order 通过内部接口验证用户、商品、位置和有效期后再冻结最后触点；归因异常只丢分析字段，不阻断交易。Commerce v2 又增加不可变 Outcome Ledger，统一记录加购、支付、取消、退款、退货、评价、售后联系和复购。
- **效果与证据：** 本地真实漏斗中，同一 requestId 从曝光、点击一直冻结到订单项；后续可以同时评估转化、退货率、差评率、售后联系率和追问轮数，而不是只优化短期点击。
- **面试表达：** 推荐系统应优化长期用户效用，归因链路必须服务端验证，分析能力不能反向降低交易可用性。

### 9. 只有日志，没有可回放的 Agent 决策过程

相关提交：f052e3b、618055b、3c1996a、95d33a6

- **问题或踩坑：** 普通日志只能看到零散调用，无法回答模型使用了哪个 Prompt、为什么选某个工具、证据从哪里来、失败在哪个节点，也无法把一次坏回答转成回归样本。
- **优化与修复：** 持久化 agent_run、agent_step 和 agent_handoff，记录模型、Prompt、工具、版本、延迟、token、成本、父子关系和脱敏输入输出；接入 OpenTelemetry/Tempo；增加 Response Verifier、Judge、badcase 候选、人工审核和回归重放。
- **效果与证据：** 管理端能够按“Supervisor 计划 → 专家 → Artifact → 校验 → 行动策略”回放真实链路，并以中文展示错误原因；已核验的坏样本可以进入冻结回归集，而不是停留在聊天截图。
- **面试表达：** Trace 不只是运维日志，它同时承担调试、评测数据生产、审计和模型/Prompt 版本对比。

### 10. 固定 RAG 浪费调用，完全 Agentic RAG 又容易失控

相关提交：4943c76、e653afb

- **问题或踩坑：** 所有请求预取 RAG 会增加无关检索、上下文 token 和延迟；让 Agent 自由反复检索又会出现重复 query、调用次数不确定和成本上升。
- **优化与修复：** 默认使用 conditional 模式：明确政策意图固定检索，证据不足且任务相关时才开放 Agentic RAG；同一任务最多执行两条归一化后不同的查询，重复 query 在调用前拒绝；保留已有证据，达到预算后明确结束。
- **效果与证据：** 检索调用数有硬上限，重复查询不会消耗外部 API；政策问题仍保留来源和知识版本，工具或检索失败时进入可解释降级。
- **面试表达：** 我没有把 Agentic RAG 用在所有请求上，而是用 badcase 和成本边界决定何时开放动态检索。

### 11. 第一版“多智能体”只是换提示词，没有真正隔离

相关提交：4cbba4d、c0ed47a、d9ae0e6

- **问题或踩坑：** 伪多智能体把完整 llm_messages 交给专家，专家既能看到不需要的历史，也可能直接回答用户或提出写操作；并行结果的汇合顺序和失败状态也不稳定。
- **优化与修复：** Supervisor 先生成结构化计划，通过 LangGraph Send 动态扇出最多两个独立专家；专家只接收脱敏 SpecialistTask、验证后的订单/图片上下文和静态只读工具范围；每个专家最多两轮、12 秒；Artifacts 按计划顺序稳定汇合，最终答复和 ActionProposal 只属于 Supervisor。
- **效果与证据：** “订单延迟且能否退款”可并行调用履约和售后政策专家；测试覆盖真实并发、稳定汇合、超时降级、专家写工具拒绝和 root-only 提案。真实退款提案中两个 child run 均没有 PROPOSE 调用。
- **面试表达：** 多 Agent 的价值不是角色名字多，而是上下文隔离、工具最小权限、可并行任务和单一写入口都能被测试证明。

### 12. 专家 Artifact 看起来有引用，实际可能是模型伪造或旧草稿

相关提交：d240d70、90ed4db

- **问题或踩坑：** 模型可能输出工具协议残片或自行构造 sourceRefs；还出现过根 Supervisor 已返回真实商品卡，但 child Artifact 仍保留“没有商品”的旧草稿，导致 Trace 自相矛盾。
- **优化与修复：** Artifact Validator 要求每条证据都对应成功的白名单工具调用，且证据类型必须匹配工具；行动提案必须有相关业务域事实，退款还要有政策证据；Artifact 在持久化和 handoff 前先校验，商品事实从服务端验证卡片确定性重建，并清理 Provider 协议残片。
- **效果与证据：** 2026-08-11 的通勤包 Run 中，child Artifact 为 SUCCESS，包含商品、预计到手价 844.2 元、库存 999、报价快照和取舍，并记录 SHOPPING_FACTS_REBUILT_FROM_VERIFIED_CARDS，不再出现父子 Trace 矛盾。
- **面试表达：** Agent 的中间产物不能因为“长得像 JSON、有引用字段”就可信，证据必须能回溯到真实成功工具和权威业务快照。

### 13. Text2SQL 能查数据，但直接开放数据库不可接受

相关提交：e4e078e、91a0601、c0ed47a、90ed4db

- **问题或踩坑：** 让管理员用自然语言查经营数据时，模型可能访问原始表、PII、系统库或跨库表，也可能生成多语句、无 LIMIT、大时间范围 SQL；“销量最高”一类问题还存在业务口径歧义。
- **优化与修复：** DataAnalyst 独立于客户多 Agent 图；先生成 DataAnalysisPlan，歧义时要求澄清；只允许查询十个无 PII 语义视图。sqlglot Guard 仅接受单条 SELECT/受控 CTE、一个白名单视图、显式字段、LIMIT ≤ 200、时间范围 ≤ 90 天；使用独立 analytics_reader 和 3 秒执行预算，失败最多修复一次。
- **效果与证据：** 真实 Run 可回放 PLAN、SQL_GUARD、EXPLAIN、QUERY 和 RESULT，得到支付峰值 6379 元、已完成退款峰值 488 元和缺货 SKU 2 个。MySQL 对 definer view 的 EXPLAIN 权限不足时只记录降级，不为方便调试扩大底表权限。
- **面试表达：** Text2SQL 的重点不是生成 SQL，而是语义层、身份隔离、AST 校验、资源预算、口径澄清和结果可追溯。

### 14. 图片搜商品不能只把图片交给大模型描述

相关提交：90ed4db、3d799d0、95d33a6

- **问题或踩坑：** 任意 URL/文件路径会带来越权和数据泄露风险；图片可能有多个商品主体；外部 grounding、embedding、rerank 任一 API 故障都可能让整条搜索失败；索引中的价格和库存又可能过期。
- **优化与修复：** 浏览器只提交不透明 imageAssetId，Java 重新校验用户归属、审核、MIME 魔数、大小、像素和过期状态；Qwen3-VL 定位最多五个主体，多主体让用户点选；使用 1024 维多模态向量、文本/图像多路召回、RRF 和 VL Rerank，最后由 Java 权威快照剔除下架或无库存商品。三个云能力使用独立超时和熔断器，连续五次可重试失败后熔断 60 秒；grounding、rerank、embedding 和索引异常分别降级为整图、RRF、受限文本理解或明确失败，索引升级通过版本化实体索引和别名原子切换。
- **效果与证据：** 2026-08-11 完整栈验收时，视觉索引别名指向正确模型版本，包含 282 个文档并处于 READY；25 条冻结评测集覆盖同图、压缩裁剪、不同角度、同类替代和无匹配。锁文件中的 Recall/MRR 等是发布门槛，不冒充已上线业务指标。
- **面试表达：** 视觉搜索是资产安全、主体选择、向量检索、精排、商品事实复验和外部 API 降级的完整链路，不是一次 VLM 问答。

### 15. 导购只按类目推荐，无法真正帮助用户做购买决策

相关提交：90ed4db、3d799d0、95d33a6

- **问题或踩坑：** “买一个包”对学生、通勤和户外的含义不同；仅召回类目会忽略用途。索引价格、库存和优惠可能不新鲜，模型容易推荐超预算或不可购买商品；多个结果也缺少清晰取舍。商业推荐如果不治理，还可能牺牲用户利益。
- **优化与修复：** Supervisor 先编译 24 小时有效的 ShoppingMission，保存用途、人群、硬约束、软偏好和未知槽位；每次只问一个最能缩小候选的问题，最多两轮。商品先通过 Java 批量生成 5 分钟有效的单 SKU FinalOfferSnapshot，再做预算、上架、库存和优惠硬过滤。排序使用版本化用户效用模型：用途 45%、已验证特征 20%、报价与可售性 20%、显式偏好 10%、多样性 5%；每个结果说明适合谁、不适合谁和主要取舍。运营候选只有在结果不少于五个时最多插入一个，不能排第一，效用不得低于被替换自然候选的 95%，并必须披露。
- **效果与证据：** 真实通勤包请求返回指定商品，原价 938 元、预计到手价 844.2 元、库存 999，并带报价快照、优惠、排序分量和证据。另有 27 条 Commerce v2 冻结契约，将硬约束、报价准确、运营披露、售后资格、归因、SQL Guard、库存公式和专家只读设为发布门槛；当前已通过数据集锁和契约校验，但不将其表述为线上效果指标。
- **面试表达：** 导购 Agent 的目标不是“多返回几张商品卡”，而是把开放需求转成任务、只用可信事实筛选、主动解释取舍，并用长期售后结果反向评估。

### 16. 售后资格不能只由 RAG 文本和模型判断

相关提交：d240d70、90ed4db、3d799d0

- **问题或踩坑：** 政策文档可能缺失、过期或互相冲突，模型即使检索到文本，也不适合独立判断用户是否具备退款/退货资格。
- **优化与修复：** 在订单域建立版本化 EligibilityDecision，根据订单状态、时间窗口、SKU/商品/类目/全局规则、凭证和例外条件返回 ELIGIBLE、INELIGIBLE、NEEDS_EVIDENCE、POLICY_UNAVAILABLE 或 CONFLICT；RAG 只提供政策解释和引用，规则缺失或冲突时保守答复并转人工。
- **效果与证据：** 售后咨询可同时调用履约专家和政策专家，Artifact 中分别保留订单事实、政策证据和资格结论；真正退款仍由 Supervisor 生成确认卡，确认前不会产生业务写入。
- **面试表达：** RAG 解决“政策依据是什么”，规则引擎解决“当前订单是否满足条件”，两者职责不能混在模型的一段自然语言里。

### 17. AI 链路不断变复杂，延迟、成本和启动稳定性需要同步治理

相关提交：be64e62、4943c76、2447392、e653afb、ef9aa06

- **问题或踩坑：** 规划、专家、RAG、视觉 API 和分析 Agent 会叠加模型调用；全部使用思考模式、串行执行或无预算重试，会让延迟和成本不可控。开发环境还出现过旧 Conda 环境掩盖 sqlglot 缺失、端口竞态和 WSL 资源峰值过高。
- **优化与修复：** Supervisor、专家和 DataAnalyst 的结构化提取使用 non-thinking JSON 模式，正常对话和 Judge 保留完整模型；独立只读专家并行，专家数、轮次、超时和 RAG 查询数均有硬上限；画像富化异步执行；外部视觉能力有限重试、独立熔断并可降级；按 queue、intent、RAG、tool、generation、total 记录时延，并区分 priced/unpriced token。start.sh 统一通过 shop Conda 环境启动 API、Worker 和 MCP，按顺序执行迁移、只读账号、队列、索引别名和内部接口预检；只回滚本次启动的进程，前端端口冲突时动态协调，外部 AI 能力 DEGRADED 不阻止商城基础服务启动。
- **效果与证据：** 最坏调用次数和失败路径从开放式行为变成有界策略；性能门禁提供 enqueue、queue、TTFT 和 total 的 P95 口径，当前阈值属于本地确定性门禁，不声称为线上 SLO。完整栈已可一键启动，Agent readiness 同时校验 MySQL、Redis、RabbitMQ、Worker、Gateway、MCP 和 ES 映射。
- **面试表达：** 没有生产对照数据时，我不会编造“延迟下降多少”，但能说明减少了哪些不必要调用、如何限制最坏成本，以及如何用分阶段指标继续测量。

### 18. 自动重试耗尽后必须有收敛点，人工决策与自动化恢复之间要有可验证的交界

- **问题或踩坑：** 消息可靠投递（事务后发送 + 幂等台账）只保证"送达且不重复"，不回答"指令反复失败时系统如何收敛"。退款 Saga 重试耗尽进入 MANUAL_REVIEW 后没有转出路径：用户重复发起被拒绝、对账定时器无分支、库存恢复直接返回——自动化的边界是死路，而不是移交人工。
- **优化与修复：** 建成人工复核闭环：进入复核时把原阶段写入 review_origin_status；管理端审批（loadDataList / approve / reject）——通过则按原阶段恢复、重试计数清零、对账定时器自动续跑，驳回则终态 REJECTED、用户重新发起即重开；审批动作用客户端幂等键 review_id + CAS 条件更新保证并发单次生效，refund_review_ledger 台账落账。恢复推进前重新校验申请时冻结的金额/数量/属性与订单项当前值，人工窗口期数据漂移（改价/改属性/退订）时审批停在复核态，绝不盲目恢复。同期还补齐了检索通道的污染检疫（知识库片段逐条剔除、工具结果替换为隔离占位符）与委托身份信道（X-Agent-User-Id 系统信道 fail-closed），见三份决策文档与垂直故事。
- **效果与证据：** Order 模块 65 条测试全绿，其中审批与恢复链路 24 条（幂等命中、跨单冲突、CAS 竞争、四种冻结字段漂移、驳回跳过校验、reconcile 恢复链路端到端）；退款状态映射新增"退款申请已驳回"；schema 幂等迁移新增 review_origin_status 列与审批台账表。
- **面试表达：** 自动重试和幂等解决"消息不会丢、不会重"，但重试耗尽后系统必须有一个收敛点——我把收敛点设计成人工复核闭环：进入时记录原阶段，审批通过就从断点恢复让定时器自动续跑，驳回则终止本次申请、用户可重开；审批动作本身幂等 + CAS 并发单次生效。恢复推进前重新校验冻结字段，防止人工窗口期的数据漂移退错钱——人工决策和自动化恢复之间必须有一个可验证的交界。

## 五、面试时必须主动说明的边界

- 当前是本地完整栈和演示数据，没有真实生产流量、GMV、CTR/CVR、线上售后率或 SLO。
- 离线评测规模有限，冻结集满分只说明当前确定性契约通过，不代表开放世界准确率 100%。
- 多智能体只在职责独立、可并行或需要隔离审查时使用；简单任务仍走规则、Workflow 或单专家。
- 写操作实现了确认、业务幂等、状态核对和人工复核，不承诺网络分区下 exactly-once。
- 视觉搜索依赖云 API，本地已实现熔断和降级，但尚无生产级供应商 SLA 与长期成本数据。
- DataAnalyst 只读十个治理视图；InventoryOps 只生成建议，不自动改库存或创建采购单。
- 运营推荐目前是受规则约束的候选插入，不是广告竞价、预算和结算系统。
- 项目没有进行模型训练或微调，主要工作集中在 Agent 编排、RAG/检索、工具治理、评测、可靠性和全栈落地。
- 当前 27/27 Commerce、18/18 安全与 162/162 Search/RAG contract 均为确定性合成证据，不是在线模型或真实用户准确率。

- 管理端试用和匿名报告机制已实现，但 `REAL_USER` 样本仍为未采集，不能声称 FCR、CTR/CVR 或业务 uplift。
- Java 高风险链路已有定向测试和 Testcontainers IT，但 common/order 当前行覆盖只有约 12.89%/13.39%，不包装成高覆盖工程。

## 六、建议优先准备的六个故事

1. 从伪多智能体到隔离 Supervisor Harness：为什么拆、如何限制专家、如何保证 root-only 写操作。
2. 从类目推荐到 ShoppingMission + 权威报价：用途追问、硬约束、解释排序和商业治理。
3. 从普通 RAG 到证据可验证的条件式 Agentic RAG：路由、分数量纲、引用和成本预算。
4. 从“能生成 SQL”到受治理 DataAnalyst：语义视图、AST Guard、最小权限和 Trace。
5. 从图片问答到完整视觉商品搜索：图片资产安全、多模态召回、精排、商品复验和熔断降级。
6. 从 happy path 到可恢复 Agent：业务幂等、未知结果、Worker 租约、故障演练和 badcase 回归。

这六个故事都应按“症状 → 定位证据 → 第一版错误假设 → 最终方案与取舍 → 可复现结果 → 当前边界”展开，能够覆盖 AI 应用、Agent、AI 全栈和 Java 后端面试中的大部分项目深挖。
