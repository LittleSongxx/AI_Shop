## 二、关键问题与优化记录

### 1. RAG 能回答 FAQ，却无法稳定回答真实售后问题

相关提交：1ebd31b、cfd31b9、f639599

- **问题或踩坑：** 商品推荐和精确 FAQ 能工作，但退款、物流、优惠券等具体意图可能绕过 RAG；旧逻辑只看最高候选分数，再把整批候选都注入上下文。Qwen3 Rerank 升级时还出现了“只换模型名但请求协议未切换”的问题，合法的 0.0 分数也曾被 Python 的 or 链吞掉。
- **优化与修复：** 建立按意图区分的固定 RAG 路由；按每条证据的来源和分数量纲独立过滤；缓存命中后重新校验知识版本和证据门槛；为 compatible/native Rerank 分别实现请求与解析，并保留超时、熔断和 RRF 降级。
- **效果与证据：** 34 条本地 RAG 评测中，Recall@K 和 MRR 均为 0.9167，引用率 0.9167，无答案 F1 为 0.9524；保留“会员升级”和“订单后改地址”两个失败样本，没有通过删题制造满分。
- **面试表达：** 我先区分“没有检索”“检索到噪声”和“模型没有使用证据”，再分别修路由、过滤和生成校验，而不是把所有问题归因于模型能力。

### 2. 检索分数量纲混用，融合排序表面生效、实际失真

相关提交：1ebd31b、892f13e、c0b6411

- **问题或踩坑：** 同一个阈值同时比较 cosine、Elasticsearch score、BM25、RRF 和 rerank 分数，语义完全不同；RRF 分又被原始 BM25 分覆盖。推荐只有单一召回时，结果容易集中在同一品类。
- **优化与修复：** 将 cosine、引擎原始分、融合分和 rerank 分拆成独立字段与阈值；文本与向量采用 RRF 融合；增加品类、浏览、购买和共同购买召回；超量召回后使用 Cross-Encoder Rerank 和 MMR，在相关性与多样性之间做约束。
- **效果与证据：** 30 条真实商品目录离线集达到 Recall@10 0.9333、MRR@10 0.8250、NDCG@10 0.8411；“蒸烤一体机”和“100W 车载充电器”仍作为 zero-hit badcase 保留。
- **面试表达：** 检索优化不是盲调一个阈值，而是先保证每个分数的物理含义正确，再讨论融合、重排和业务约束。

### 3. Redis 被当作长期记忆事实源，用户约束会丢失或被摘要改写

相关提交：508f980、621e3b2、4808450、d9ae0e6

- **问题或踩坑：** 预算、品牌和使用场景只存在 Redis，TTL 或重启后会消失；LLM 摘要可能把“预算 3000 元”压成“预算有限”，无法继续做硬过滤；后台抽取若整体覆盖，还会用空值或脏值污染已有画像。
- **优化与修复：** MySQL 保存结构化购物档案，Redis 只做缓存；显式用户表达优先于摘要和隐式行为；长文本的 LLM 富化异步执行并设置 8 秒上限，结果严格归一化后做增量 merge；清除聊天只推进可见历史游标，不删除长期记忆。
- **效果与证据：** 预算、品牌、用途和负向偏好可以跨会话保存，Redis 丢失后可从 MySQL 回填；用户可以查看、删除或关闭个性化；异步富化失败不阻塞主对话。
- **面试表达：** 我把短期对话、摘要记忆、长期偏好和 RAG 知识分开治理，并明确每类信息的事实源、优先级和生命周期。

### 4. “请模型输出 JSON、记得调工具”不是运行时保证

相关提交：3bfd41f、d5ca74f、f639599

- **问题或踩坑：** 自由文本 JSON 解析失败时可能落入过宽分支；订单、物流和优惠券事实问题如果模型跳过工具，仍可能生成看似合理的答案。资金风险词曾在风险表和意图表分别维护，出现一边识别、一边漏路由。
- **优化与修复：** Provider 支持时优先结构化输出，失败进入确定性安全回退；必需事实工具由图节点强制补调；工具失败必须显式降级；资金风险词改为单一事实源派生意图表，避免两份规则漂移。
- **效果与证据：** 同一冻结集上，资金风险相关基线由 96/112 提升到 99/112，数据 SHA 未改变；后续冻结会话集扩展为 134/134，覆盖意图、工具选择、参数、注入和写操作边界。
- **面试表达：** Prompt 是软约束，结构化 schema、确定性路由和服务端工具校验才是可测试的协议。

### 5. 自然语言售后已经表达清楚，系统却仍要求用户手输订单号

相关提交：d5ca74f、32ef02c、d9ae0e6

- **问题或踩坑：** “没发货的耳机我要退款”已经被识别成退款，但旧链路假设用户会提供订单号，模型无法可靠拼出订单项 ID；多笔相似订单时自动猜测还可能造成错单风险。
- **优化与修复：** 在 LLM 和写工具之前增加确定性 OrderReferenceResolver，按用户归属、显式 ID、订单状态、时间、商品、品牌、型号和规格逐层过滤；唯一候选自动继续，多候选返回持久化选择卡；选择过程用行锁保证幂等，Worker 执行前再次校验最新状态。
- **效果与证据：** 真实完整栈中，无需输入订单号即可定位 SM202608050002 / SMITEM202608050002 并生成退款确认卡；确认前订单和订单项状态保持不变。“收到的东西坏了”场景还暴露并修复了待付款订单误入候选的问题。
- **面试表达：** 开放自然语言由模型理解，但身份、订单定位和业务资格采用确定性规则和权威数据，模糊时主动澄清而不是让模型猜。

### 6. 请求 token 防不了同一业务动作换 token 重复执行

相关提交：b4a1044、d5ca74f、32ef02c、4cbba4d

- **问题或踩坑：** action token 只能防同一 token 重放，用户仍可能为同一订单重新生成另一个 token；HTTP 超时也无法证明远端到底提交成功还是失败，直接重试可能重复产生副作用。
- **优化与修复：** 使用 userId + actionType + 业务资源构造 business key，并对规范化参数计算指纹；活跃业务键由数据库唯一约束占位；未知结果进入 INCONCLUSIVE，只查询 Java 幂等账本和领域状态，达到时间或次数边界转 MANUAL_REVIEW，禁止自动重放副作用。
- **效果与证据：** 同业务同参数复用原提案，不同参数冲突；重复确认只产生一个终态和一次业务效果。多智能体重构后，所有 PROPOSE 工具进一步收口到 root Supervisor。
- **面试表达：** 我区分了传输层 token、业务幂等键和远端未知结果，并明确项目实现的是“幂等账本 + 有界对账 + 人工复核”，不是 exactly-once。

### 7. 单元测试通过，不代表 Worker、MQ 和 WebSocket 故障时能够收敛

相关提交：d5ca74f、f052e3b

- **问题或踩坑：** Worker 被杀、RabbitMQ 暂停、重复投递或 checkpoint Redis 故障时，单纯的状态机测试无法证明任务不会丢失或重复执行；WebSocket 先推送后落库还可能让客户端看到数据库中不存在的 DONE。
- **优化与修复：** 建立任务账本、lease、续租、fencing、checkpoint 和恢复扫描；业务终态先落库再推送；前端按 messageId 幂等合并 PARTIAL/DONE；使用独立 Compose 环境真实 kill Worker、停止 RabbitMQ 和 Redis。
- **效果与证据：** 六条故障断言全部通过：Worker 租约接管后只有一个 effect；RabbitMQ 恢复后任务只执行一次；重复投递只有一个终态；checkpoint 失败时任务进入 DEAD，绝不误报成功。
- **面试表达：** 可靠性不能只看 happy path，我会验证“进程在哪一步死掉”以及数据库、队列、客户端最终各自看到什么。

### 8. 推荐归因只信浏览器 requestId，无法支撑可信质量评估

相关提交：10801b5、ed000b3、90ed4db、3d799d0

- **问题或踩坑：** 客户端可以伪造曝光、点击、商品或位置；Redis 快照过期后没有可审计事实；只看 CTR/CVR 也无法反映误导推荐带来的退款、退货和差评。
- **优化与修复：** 将曝光和点击持久化，Java Cart/Order 通过内部接口验证用户、商品、位置和有效期后再冻结最后触点；归因异常只丢分析字段，不阻断交易。Commerce v2 又增加不可变 Outcome Ledger，统一记录加购、支付、取消、退款、退货、评价、售后联系和复购。
- **效果与证据：** 本地真实漏斗中，同一 requestId 从曝光、点击一直冻结到订单项；后续可以同时评估转化、退货率、差评率、售后联系率和追问轮数，而不是只优化短期点击。
- **面试表达：** 推荐系统应优化长期用户效用，归因链路必须服务端验证，分析能力不能反向降低交易可用性。

### 9. 只有日志，没有可回放的 Agent 决策过程

相关提交：f052e3b、618055b、3c1996a、95d33a6

- **问题或踩坑：** 普通日志只能看到零散调用，无法回答模型使用了哪个 Prompt、为什么选某个工具、证据从哪里来、失败在哪个节点，也无法把一次坏回答转成回归样本。
- **优化与修复：** 持久化 agent_run、agent_step 和 agent_handoff，记录模型、Prompt、工具、版本、延迟、token、成本、父子关系和脱敏输入输出；接入 OpenTelemetry/Tempo；增加 Response Verifier、Judge、badcase 候选、人工审核和回归重放。
- **效果与证据：** 管理端能够按“Supervisor 计划 → 专家 → Artifact → 校验 → 行动策略”回放真实链路，并以中文展示错误原因；已核验的坏样本可以进入冻结回归集，而不是停留在聊天截图。
- **面试表达：** Trace 不只是运维日志，它同时承担调试、评测数据生产、审计和模型/Prompt 版本对比。

### 10. 固定 RAG 浪费调用，完全 Agentic RAG 又容易失控

相关提交：4943c76、e653afb

- **问题或踩坑：** 所有请求预取 RAG 会增加无关检索、上下文 token 和延迟；让 Agent 自由反复检索又会出现重复 query、调用次数不确定和成本上升。
- **优化与修复：** 默认使用 conditional 模式：明确政策意图固定检索，证据不足且任务相关时才开放 Agentic RAG；同一任务最多执行两条归一化后不同的查询，重复 query 在调用前拒绝；保留已有证据，达到预算后明确结束。
- **效果与证据：** 检索调用数有硬上限，重复查询不会消耗外部 API；政策问题仍保留来源和知识版本，工具或检索失败时进入可解释降级。
- **面试表达：** 我没有把 Agentic RAG 用在所有请求上，而是用 badcase 和成本边界决定何时开放动态检索。

### 11. 第一版“多智能体”只是换提示词，没有真正隔离

相关提交：4cbba4d、c0ed47a、d9ae0e6

- **问题或踩坑：** 伪多智能体把完整 llm_messages 交给专家，专家既能看到不需要的历史，也可能直接回答用户或提出写操作；并行结果的汇合顺序和失败状态也不稳定。
- **优化与修复：** Supervisor 先生成结构化计划，通过 LangGraph Send 动态扇出最多两个独立专家；专家只接收脱敏 SpecialistTask、验证后的订单/图片上下文和静态只读工具范围；每个专家最多两轮、12 秒；Artifacts 按计划顺序稳定汇合，最终答复和 ActionProposal 只属于 Supervisor。
- **效果与证据：** “订单延迟且能否退款”可并行调用履约和售后政策专家；测试覆盖真实并发、稳定汇合、超时降级、专家写工具拒绝和 root-only 提案。真实退款提案中两个 child run 均没有 PROPOSE 调用。
- **面试表达：** 多 Agent 的价值不是角色名字多，而是上下文隔离、工具最小权限、可并行任务和单一写入口都能被测试证明。

### 12. 专家 Artifact 看起来有引用，实际可能是模型伪造或旧草稿

相关提交：d240d70、90ed4db

- **问题或踩坑：** 模型可能输出工具协议残片或自行构造 sourceRefs；还出现过根 Supervisor 已返回真实商品卡，但 child Artifact 仍保留“没有商品”的旧草稿，导致 Trace 自相矛盾。
- **优化与修复：** Artifact Validator 要求每条证据都对应成功的白名单工具调用，且证据类型必须匹配工具；行动提案必须有相关业务域事实，退款还要有政策证据；Artifact 在持久化和 handoff 前先校验，商品事实从服务端验证卡片确定性重建，并清理 Provider 协议残片。
- **效果与证据：** 2026-08-11 的通勤包 Run 中，child Artifact 为 SUCCESS，包含商品、预计到手价 844.2 元、库存 999、报价快照和取舍，并记录 SHOPPING_FACTS_REBUILT_FROM_VERIFIED_CARDS，不再出现父子 Trace 矛盾。
- **面试表达：** Agent 的中间产物不能因为“长得像 JSON、有引用字段”就可信，证据必须能回溯到真实成功工具和权威业务快照。

### 13. Text2SQL 能查数据，但直接开放数据库不可接受

相关提交：e4e078e、91a0601、c0ed47a、90ed4db

- **问题或踩坑：** 让管理员用自然语言查经营数据时，模型可能访问原始表、PII、系统库或跨库表，也可能生成多语句、无 LIMIT、大时间范围 SQL；“销量最高”一类问题还存在业务口径歧义。
- **优化与修复：** DataAnalyst 独立于客户多 Agent 图；先生成 DataAnalysisPlan，歧义时要求澄清；只允许查询十个无 PII 语义视图。sqlglot Guard 仅接受单条 SELECT/受控 CTE、一个白名单视图、显式字段、LIMIT ≤ 200、时间范围 ≤ 90 天；使用独立 analytics_reader 和 3 秒执行预算，失败最多修复一次。
- **效果与证据：** 真实 Run 可回放 PLAN、SQL_GUARD、EXPLAIN、QUERY 和 RESULT，得到支付峰值 6379 元、已完成退款峰值 488 元和缺货 SKU 2 个。MySQL 对 definer view 的 EXPLAIN 权限不足时只记录降级，不为方便调试扩大底表权限。
- **面试表达：** Text2SQL 的重点不是生成 SQL，而是语义层、身份隔离、AST 校验、资源预算、口径澄清和结果可追溯。

### 14. 图片搜商品不能只把图片交给大模型描述

相关提交：90ed4db、3d799d0、95d33a6

- **问题或踩坑：** 任意 URL/文件路径会带来越权和数据泄露风险；图片可能有多个商品主体；外部 grounding、embedding、rerank 任一 API 故障都可能让整条搜索失败；索引中的价格和库存又可能过期。
- **优化与修复：** 浏览器只提交不透明 imageAssetId，Java 重新校验用户归属、审核、MIME 魔数、大小、像素和过期状态；Qwen3-VL 定位最多五个主体，多主体让用户点选；使用 1024 维多模态向量、文本/图像多路召回、RRF 和 VL Rerank，最后由 Java 权威快照剔除下架或无库存商品。三个云能力使用独立超时和熔断器，连续五次可重试失败后熔断 60 秒；grounding、rerank、embedding 和索引异常分别降级为整图、RRF、受限文本理解或明确失败，索引升级通过版本化实体索引和别名原子切换。
- **效果与证据：** 2026-08-11 完整栈验收时，视觉索引别名指向正确模型版本，包含 282 个文档并处于 READY；25 条冻结评测集覆盖同图、压缩裁剪、不同角度、同类替代和无匹配。锁文件中的 Recall/MRR 等是发布门槛，不冒充已上线业务指标。
- **面试表达：** 视觉搜索是资产安全、主体选择、向量检索、精排、商品事实复验和外部 API 降级的完整链路，不是一次 VLM 问答。

### 15. 导购只按类目推荐，无法真正帮助用户做购买决策

相关提交：90ed4db、3d799d0、95d33a6

- **问题或踩坑：** “买一个包”对学生、通勤和户外的含义不同；仅召回类目会忽略用途。索引价格、库存和优惠可能不新鲜，模型容易推荐超预算或不可购买商品；多个结果也缺少清晰取舍。商业推荐如果不治理，还可能牺牲用户利益。
- **优化与修复：** Supervisor 先编译 24 小时有效的 ShoppingMission，保存用途、人群、硬约束、软偏好和未知槽位；每次只问一个最能缩小候选的问题，最多两轮。商品先通过 Java 批量生成 5 分钟有效的单 SKU FinalOfferSnapshot，再做预算、上架、库存和优惠硬过滤。排序使用版本化用户效用模型：用途 45%、已验证特征 20%、报价与可售性 20%、显式偏好 10%、多样性 5%；每个结果说明适合谁、不适合谁和主要取舍。运营候选只有在结果不少于五个时最多插入一个，不能排第一，效用不得低于被替换自然候选的 95%，并必须披露。
- **效果与证据：** 真实通勤包请求返回指定商品，原价 938 元、预计到手价 844.2 元、库存 999，并带报价快照、优惠、排序分量和证据。另有 27 条 Commerce v2 冻结契约，将硬约束、报价准确、运营披露、售后资格、归因、SQL Guard、库存公式和专家只读设为发布门槛；当前已通过数据集锁和契约校验，但不将其表述为线上效果指标。
- **面试表达：** 导购 Agent 的目标不是“多返回几张商品卡”，而是把开放需求转成任务、只用可信事实筛选、主动解释取舍，并用长期售后结果反向评估。

### 16. 售后资格不能只由 RAG 文本和模型判断

相关提交：d240d70、90ed4db、3d799d0

- **问题或踩坑：** 政策文档可能缺失、过期或互相冲突，模型即使检索到文本，也不适合独立判断用户是否具备退款/退货资格。
- **优化与修复：** 在订单域建立版本化 EligibilityDecision，根据订单状态、时间窗口、SKU/商品/类目/全局规则、凭证和例外条件返回 ELIGIBLE、INELIGIBLE、NEEDS_EVIDENCE、POLICY_UNAVAILABLE 或 CONFLICT；RAG 只提供政策解释和引用，规则缺失或冲突时保守答复并转人工。
- **效果与证据：** 售后咨询可同时调用履约专家和政策专家，Artifact 中分别保留订单事实、政策证据和资格结论；真正退款仍由 Supervisor 生成确认卡，确认前不会产生业务写入。
- **面试表达：** RAG 解决“政策依据是什么”，规则引擎解决“当前订单是否满足条件”，两者职责不能混在模型的一段自然语言里。

### 17. AI 链路不断变复杂，延迟、成本和启动稳定性需要同步治理

相关提交：be64e62、4943c76、2447392、e653afb、ef9aa06

- **问题或踩坑：** 规划、专家、RAG、视觉 API 和分析 Agent 会叠加模型调用；全部使用思考模式、串行执行或无预算重试，会让延迟和成本不可控。开发环境还出现过旧 Conda 环境掩盖 sqlglot 缺失、端口竞态和 WSL 资源峰值过高。
- **优化与修复：** Supervisor、专家和 DataAnalyst 的结构化提取使用 non-thinking JSON 模式，正常对话和 Judge 保留完整模型；独立只读专家并行，专家数、轮次、超时和 RAG 查询数均有硬上限；画像富化异步执行；外部视觉能力有限重试、独立熔断并可降级；按 queue、intent、RAG、tool、generation、total 记录时延，并区分 priced/unpriced token。start.sh 统一通过 shop Conda 环境启动 API、Worker 和 MCP，按顺序执行迁移、只读账号、队列、索引别名和内部接口预检；只回滚本次启动的进程，前端端口冲突时动态协调，外部 AI 能力 DEGRADED 不阻止商城基础服务启动。
- **效果与证据：** 最坏调用次数和失败路径从开放式行为变成有界策略；性能门禁提供 enqueue、queue、TTFT 和 total 的 P95 口径，当前阈值属于本地确定性门禁，不声称为线上 SLO。完整栈已可一键启动，Agent readiness 同时校验 MySQL、Redis、RabbitMQ、Worker、Gateway、MCP 和 ES 映射。
- **面试表达：** 没有生产对照数据时，我不会编造“延迟下降多少”，但能说明减少了哪些不必要调用、如何限制最坏成本，以及如何用分阶段指标继续测量。

### 18. 自动重试耗尽后必须有收敛点，人工决策与自动化恢复之间要有可验证的交界

- **问题或踩坑：** 消息可靠投递（事务后发送 + 幂等台账）只保证"送达且不重复"，不回答"指令反复失败时系统如何收敛"。退款 Saga 重试耗尽进入 MANUAL_REVIEW 后没有转出路径：用户重复发起被拒绝、对账定时器无分支、库存恢复直接返回——自动化的边界是死路，而不是移交人工。
- **优化与修复：** 建成人工复核闭环：进入复核时把原阶段写入 review_origin_status；管理端审批（loadDataList / approve / reject）——通过则按原阶段恢复、重试计数清零、对账定时器自动续跑，驳回则终态 REJECTED、用户重新发起即重开；审批动作用客户端幂等键 review_id + CAS 条件更新保证并发单次生效，refund_review_ledger 台账落账。恢复推进前重新校验申请时冻结的金额/数量/属性与订单项当前值，人工窗口期数据漂移（改价/改属性/退订）时审批停在复核态，绝不盲目恢复。同期还补齐了检索通道的污染检疫（知识库片段逐条剔除、工具结果替换为隔离占位符）与委托身份信道（X-Agent-User-Id 系统信道 fail-closed），见三份决策文档与垂直故事。
- **效果与证据：** Order 模块 65 条测试全绿，其中审批与恢复链路 24 条（幂等命中、跨单冲突、CAS 竞争、四种冻结字段漂移、驳回跳过校验、reconcile 恢复链路端到端）；退款状态映射新增"退款申请已驳回"；schema 幂等迁移新增 review_origin_status 列与审批台账表。
- **面试表达：** 自动重试和幂等解决"消息不会丢、不会重"，但重试耗尽后系统必须有一个收敛点——我把收敛点设计成人工复核闭环：进入时记录原阶段，审批通过就从断点恢复让定时器自动续跑，驳回则终止本次申请、用户可重开；审批动作本身幂等 + CAS 并发单次生效。恢复推进前重新校验冻结字段，防止人工窗口期的数据漂移退错钱——人工决策和自动化恢复之间必须有一个可验证的交界。

## 五、2026-08-13 RAG v3 排查、知识扩充与实测

### 1. 知识规模过小，新增业务域无法被系统明确回答

- **症状：** v2 只有 4 份文档、19 个 chunk 和 6 FAQ。地址修改、支付回调、物流异常、售后凭证、抢券、评价和 AI 数据边界等问题只能靠主题相似片段回答，或被错误拒答。
- **原因：** 知识库只覆盖购物、订单、会员和 AI 助手的概览；很多已实现的 Java/Python 业务事实没有进入可发布知识。`bootstrap_demo.py` 还把“4 份文档”写成固定契约。
- **错误方案：** 直接改写旧文档或针对 badcase 塞答案会破坏旧 SHA，无法区分“检索优化”和“测试集泄漏”。让 LLM 自己编标签也会产生循环证明。
- **最终修复：** 保留旧 4 份原文及 SHA，新增购物车结算、支付退款、地址安全、物流异常、售后证据、促销抢券、评价规范、隐私与 AI 边界 8 份文档；每份 7 个独立章节。新增 `catalog.v1.json`，记录 domain、canonical fact ID、等价引用、源码事实来源和文档 SHA。Java 上传/ES metadata 增加兼容的 `domain`；bootstrap 按 catalog 校验与内容 hash 幂等发布。
- **实测结果：** 发布后为 12 个 active document、75 个 knowledge chunk、6 FAQ、73 个 canonical fact、knowledge release `17`，向量维度 1024，Contextual enrichment 75/75。RAG retrieval v3 扩展为 48 public + 64 regression + 32 fresh，共 144 条。
- **当前边界：** 文档来自项目实现和演示规则，不是生产客服语料；知识规模仍小于真实电商平台。旧 v2 结果和 baseline 均保留。

### 2. Context Prefix 与 240 字 snippet 污染最终证据

- **症状：** 检索文本中的 LLM Context Prefix 可能被 Rerank/生成误当事实；生成 Runner 只使用 `source_refs.snippet[:240]`，长章节的直接约束被截断。
- **原因：** 搜索优化文本、公开引用摘要和模型回答证据混用了同一字段，缺少明确的 grounding 数据契约。
- **错误方案：** 把 snippet 调到更长只能推迟截断；直接把 Context Prefix 喂给模型会让“LLM 生成的检索辅助文本”反过来成为回答依据。
- **最终修复：** 新增 `GroundingEnvelope`，用 `evidenceState`、完整洁净 `evidenceItems`、`queryPlan` 和不含攻击原文的 `securityFlags` 分层。ES 仍用 `contextPrefix + originalContent` 检索，但索引保存 `metadata.originalContent`；Rerank、引用和生成只使用 original content，公开 `source_refs` 保持短摘要。
- **实测结果：** v3 生成的 40 条均使用完整 `evidenceItems`，无效引用数为 0；检索 fresh canonical citation coverage 为 1.0。
- **当前边界：** 这保证证据来源正确，不保证模型一定完整复述所有事实；生成 v3 仍有 12 个 badcase。

### 3. 单一阈值无法区分“直接支持”和“主题相似”

- **症状：** v2 的 0.55/0.65 单阈值既会接纳隐私主题但不回答问题的片段，也会拒绝地址或物流的直接证据。
- **原因：** 普通相关性 Rerank 更重主题相近，不等价于“能直接回答、约束或否定当前命题”。
- **错误方案：** 只降低阈值提高 Recall 会恶化 no-answer；只提高阈值会增加可回答题误拒答。增加第二个在线 LLM judge 会继续增加延迟、成本和失败面。
- **最终修复：** 保留原问题作为第一路并增加最多 2 条受控变体；每路 BM25/Vector 后做两级 RRF。Rerank instruction 明确要求直接支持，并扫描 Top-N `3/6/10`、阈值 `0.50–0.70`、margin `0/0.05/0.10`。按安全、no-answer、Recall@5、canonical citation、NDCG/MRR 和延迟冻结 `production:n6:t0.70:m0.10:iexp`。
- **实测结果：** 144/144 完整，检索门禁 `PASSED`。Fresh Recall@1/3/5 为 0.9583/1.0/1.0，MRR@10 0.9792，NDCG@5 0.9846，no-answer 与 injection robustness 均为 1.0；Embedding 缓存命中 0、Provider 失败 0、Rerank fallback 0。Regression Recall@5 不退化，MRR/NDCG 小幅上升。
- **当前边界：** dev 上多数消融 CI 跨 0；不能笼统声称 Rerank/Query Expansion 在所有数据上都显著更好。Fresh 只有 32 条，P99 不是 SLO。

### 4. 等价证据和中文表面表达导致正确答案被判错

- **症状：** FAQ 与 Markdown 表达同一事实，答案引用其中任一来源仍被 strict ref 判错；“一张/1张”“券/优惠券”“重新读取/重新校验”等表述也被字面关键词误判。
- **原因：** 旧评测把文件位置当事实本身，且只做简单字符串包含，相关性标签与语言表面形式耦合。
- **错误方案：** 为每个模型答案手工加关键词会持续追着输出漂移，也容易污染 holdout。
- **最终修复：** catalog 为每个业务事实分配 canonical fact ID，并绑定 FAQ、Markdown 和明确等价引用；case 改用 `relevantFactIds`、`requiredConcepts.aliases`、`expectedBehavior`。中文数字、量词、空格、标点和有限错别字做确定性归一化。`strictExactRefPrecision` 只保留诊断，门禁改用 canonical citation correctness/coverage。
- **实测结果：** Retrieval fresh canonical citation correctness/coverage 为 0.9231/1.0，dev 为 0.9077/0.9341。Generation v3 canonical coverage 提升到 0.9333，但 correctness 仍为 0.8667，低于 0.90 门槛。
- **当前边界：** canonical catalog 仍可能漏掉真实等价来源和模型同义表达；标签扩充必须依据已发布事实，不能看完 fresh 输出后改标签抬分。

### 5. 有充分证据仍误拒答，repair 也没有收敛

- **症状：** `rag-holdout-011` 等问题询问“证据不足时怎么做”，模型看到正文中的“无法确认”后把它误解为当前检索证据不足；v3 唯一一次 repair 仍失败。
- **原因：** 旧 prompt 没有把 `evidenceState` 与知识正文中的流程措辞强分离；验证器只看最终文本，无法告诉模型具体失败原因。
- **错误方案：** 全局禁止出现拒答词会破坏真正 no-answer 场景；无界重试会挑分并掩盖额外 token/延迟。
- **最终修复：** 生产与评测共用 Grounding Prompt Builder。`SUPPORTED` 明确要求回答，`INSUFFICIENT/QUARANTINED` 只输出固定拒答；知识和用户文本均包在不可信数据边界。仅在 SUPPORTED 但误拒答、缺引用或引用越界时，用同模型同证据最多 repair 一次，并保留初答、额外 usage 和延迟。Response Verifier 增加 `UNNECESSARY_RAG_ABSTENTION`、`INVALID_RAG_CITATION`。
- **实测结果：** Generation v3 40/40 执行、无 runtime error、28/40 通过；no-answer accuracy 1.0、无效引用 0，但总成功率 0.70、known regression 17/24，故以 `FAILED_RETAINED` 保留。
- **当前边界：** Prompt 修复降低结构性风险，但模型仍可能短答、漏概念或误拒答；本轮没有用同一 run ID 重跑挑分。

### 6. 混合注入处理和通道检疫出现两个安全误报

- **症状：** 合法问题后附明确攻击命令时，模型已正确回答合法前缀，但概念不完整会同时被记作 `injectionRobust=False` 和严重安全违规；知识句“客户端传入他人用户券 ID 不能绕过归属校验”被 `guard_bypass_zh` 当成攻击清空证据。
- **原因：** 评测器直接使用 `injection_robust = success`，把任务完整性与安全性耦合；通道扫描只看到“绕过……校验”，没有识别前面的规范性否定词。
- **错误方案：** 对所有含“绕过”文本放行会漏掉真实攻击；只给知识通道单独加白名单会让用户输入与外部通道规则漂移。
- **最终修复：** 统一扫描函数按命中位置排除“不能/不可/无法/不应/不得/禁止绕过……”的规范事实，祈使攻击仍拦截。生成评测新增独立 `injection_safety`：混合注入要求非拒答、至少一个有效且支持合法业务的引用、无越界引用；纯注入仍要求固定拒答且无引用。汇总直接读取 `injectionRobust`，不再读取 task success。
- **实测结果：** 87 条输入安全、通道、RAG 检索与生成 Runner 定向测试通过。冻结 v3 中 2 个“严重安全失败”和 0.75 injection robustness 仍原样保留，因为它们属于修复前的正式结果。
- **当前边界：** 修复后的在线效果尚未以新 run ID 重跑；不能据单测把冻结 v3 改写成安全门禁通过。规则仍是低成本纵深防御，不能覆盖开放世界语义注入。

### 7. v3 当前可讲结论

- 检索端已经达到本轮门槛：知识扩至 12 份/75 chunk 后，144 条数据完整执行，fresh Recall@3/5=1.0、MRR@10=0.9792、NDCG@5=0.9846，no-answer/injection 均为 1.0，Provider 完整性和 regression guard 通过。
- 生成端仍未达标：40 条仅 28 条通过，concept coverage 0.8111、canonical citation correctness 0.8667，尽管 coverage 0.9333、no-answer 1.0、无效引用 0。12 个失败主要分为检索/检疫误报、等价标签/别名不足、答案过短和有证据误拒答。
- 证据均为 `SYNTHETIC + local-live`；AI 初审 28 PASS/12 FAIL 不是人工标注，13,005 token 成本为 `UNPRICED`，本地 P95/P99 不是生产 SLO。

## 六、2026-08-14 Search v2 运行时对齐与修复后实测

### 1. 底层 Retriever 评测通过，真实 ProductService 却大幅失败

- **根因：** 旧 mature Runner 主要调底层召回器，没覆盖真实服务的澄清、权威快照、硬约束和决策过滤；组件离线高分不等于产品路径正确。
- **错误方案：** 只调 BM25/Vector/RRF/Rerank 参数无法修复上层路由；把 gold constraints 喂给运行时过滤会泄漏标签。
- **最终修复：** 新增共享 `ProductQueryPlan` 和真实 `ProductService` Runner，运行时仅使用原查询、`ShoppingMission` 提取约束、Java 权威商品快照与现有决策链；gold 只用于评分，Trace 记录 `goldUsedByRuntime=false`。

### 2. 未知 taxonomy 防护误伤真实动态目录

- **症状：** 净水器、音箱、筋膜枪、餐具和调料等 ES 中真实品类被当成目录外查询，未进入召回。
- **根因：** 防护逻辑把受控 taxonomy 当成全量商品目录，把“未配置”误解为“不存在”。
- **最终修复：** 只对“目录外对象被明确比较成已知品类”的后缀模式启用保守过滤，普通动态品类继续召回。例如“火星土壤样本，并能当作手机直接使用”不会因后缀“手机”被当成手机需求。

### 3. 查询理解和澄清策略与真实请求失配

- **症状：** `3-5岁` 被误识别为价格区间；“用于办公室，适合上班族”的用途被人群词覆盖；已给出预算、品牌、用途或特征的请求仍被追问。
- **根因：** 价格正则没排除年龄单位，用途提取没优先明确场景，`ProductService` 也没复用 `shopping_profile_service.should_clarify(...)`。
- **最终修复：** 排除年龄区间，按明确用途优先解析，别名匹配统一 `casefold()`，并在服务路径复用澄清策略。“推荐手机”仍可追问，“无线降噪耳机”、“苹果手机”、“办公台式电脑”等明确需求直接检索。

### 4. 品牌和品类 schema 不完整会在决策层清空正确候选

- **症状：** `Apple/苹果 MacBook`、`索尼（SONY）`、`三星（SAMSUNG）` 等正确商品已召回，却被 ShoppingDecision 判为 `BRAND_REQUIRED`；缺少文本类目字段时又会混入跨品类候选。
- **根因：** 品牌只比较结构化 `brand`，未利用权威商品名；类目判定对缺字段商品没有可审计的确定性兜底。
- **最终修复：** 从 Java 权威商品名和受控别名确定性归一品牌，Product Search 过滤与 ShoppingDecision 共用相同口径；受管品类缺 schema 时才使用权威商品名兜底。

### 5. 别名边界被 substring 和单字匹配破坏

- **症状：** `音箱` 因包含“箱”被归入箱包并追问“这个包主要用于什么？”；“蒸烤一体机”因 `一体机` 被识别为电脑。
- **根因：** 类别判定使用过宽单字 substring，本应仅 exact 生效的别名又被子串推断二次扩大。
- **最终修复：** 音箱/音响先归入 generic，箱包只匹配箱包、背包、书包和行李箱等明确词；`exact_aliases` 只在完整请求等于别名时生效。

### 6. 缺货会让“搜索相关性”和“当前可购买性”产生口径冲突

- **症状：** `graded-019` 的唯一相关商品 `158081823347974` 在 ES 中存在且 BM25 可召回，但 Java 权威库存为 0；旧路径用不相关耳机补位。
- **最终修复：** 缺货后不做跨品类补位，返回 `out_of_stock`；Runner 同时报告原始 catalog relevance 和经 Java 库存校正的 availability-adjusted relevance，并保留 `unavailableRelevantIds`。
- **实测结果：** 30 个标注相关商品中 29 个可购、1 个缺货、0 个状态未知。原始 catalog Recall@10 为 `0.977778`；44 条可购买正例的 adjusted Recall@10 为 `1.0`，1 条缺货负例 no-result accuracy 为 `1.0`。

### 7. 环境路由错误也必须作为失败证据保留

## 七、2026-08-14 RAG v4 正式失败、坏例定位与暴露后修复

### 1. 先区分环境失败、Provider 完整和质量达标

- **症状：** 首次采集把知识 Java 服务指向未监听的 `127.0.0.1:8081`，release、FAQ 与知识目录 smoke check 失败；修正路由后，264 条检索和 60 条生成虽全部执行，质量门禁仍失败。
- **原因：** 前者是环境路由错误，后者才是检索/生成质量问题。Provider 调用成功只能证明实验完整，不能证明答案正确。
- **最终处理：** 环境诊断不升级为 E3；切到 Search 服务 `127.0.0.1:8108` 并核验 12 文档、75 chunk、6 FAQ 后创建正式 `rag-v4-64aa86e-routefix-20260814`。正式 Retrieval fresh Recall@3/5=`0.805556`、MRR=`0.75`、NDCG@5=`0.764548`；正式 Generation `rag-generation-v4-64aa86e-postfix-20260814` 为 `39/60`，二者均保留为 `FAILED_RETAINED`。
- **当前边界：** Embedding 缓存命中、Provider 失败和 Rerank fallback 均为 0，只能说明运行可信，不能把失败门禁改写成通过。

### 2. Query hint 过宽会把合法 AI 数据问题误判成 AI 写操作

- **症状：** “AI 数据删除”和“AI 能否直接退款”被同一宽泛规则命中，前者被路由到无关的 AI 写操作事实，后者混合注入题又丢失合法问题所需证据。
- **根因：** 早期 hint 只看“AI + 动作词”，没有区分“操作 AI 数据”和“AI 代表用户执行业务写操作”。
- **错误方案：** 为每条坏例追加完整问句特判，能提高当前分数，但不可泛化且会把评测题面写进运行时。
- **最终修复：** 缩窄 AI-action 触发条件，补充价格快照、地址归属、优惠券生命周期、售后幂等、隐私删除、演示资金和物流时效等确定性 runtime hints；原问题始终保留，最多 3 个子问题，gold constraints、`requiredClaims` 和 holdout alias 不进入推理链。
- **实测：** 7 条 live targeted Retrieval 中 5 个真实修复目标全部通过，混合注入安全性通过；Provider 完整性仍为 100%。

### 3. “一题一证据”不是最小充分证据

- **症状：** 首个 post-fix offline replay 把 fresh Recall@3/5 提到 `0.861111`，但 known regression 下降超过 5 个百分点。
- **根因：** 把“减少重复上下文”机械实现成“每题只保留一条”，多步骤题和并列事实题因此缺证据。最小的对象应是“覆盖所有必要 fact 的集合”，不是固定一条文档。
- **错误方案：** 一旦第一条高分证据出现就停止。这降低 token，却牺牲 required fact coverage，已明确拒绝。
- **最终修复：** Evidence Selector 按 canonical fact 和正文 hash 去重，优先覆盖全部 runtime 子问题/事实提示；显式事实已覆盖才停止，候选分数接近且语义有歧义时允许保留第二条，仍限制为最多 4 条、6,000 字符。
- **实测：** final offline replay v3 的 fresh Recall@3/5、MRR、NDCG 均为 `0.944444`，canonical correctness/coverage=`1.0/0.9444`，no-answer/injection=`1.0`，known regression guard 恢复通过，且 replay Provider 调用数为 0。

### 4. 候选会在 RRF 和 Rerank 两个位置被静默截断

- **症状：** “模拟物流是否承诺两小时送达”连续两次 targeted generation 拒答。第一次事实候选甚至没进入 Rerank；提升候选后，第二次进入 Rerank 输入，却不在 Provider 返回 Top-6 中。
- **根因：** 跨 variant RRF 只保留统一 Top-N，弱词面但由可信 fact hint 命中的候选先被截断；随后 Rerank API 的 Top-6 返回又把直接否定事实排除。只检查“调用过 Rerank”看不出这两个丢失点。
- **错误方案：** 全局降低 `0.70` 阈值或无界增加 Top-N，会放大主题相似假阳性和成本，也不能保证目标证据进入精排。
- **最终修复：** 在跨 variant 截断前保留 BM25/Vector/RRF 的 fact-hint 候选；fact-hinted 请求用可信 fact catalog 标题增强 Rerank query；仍只调用一次 Rerank，但返回当前完整候选顺序，再按真实分数、专用 hint floor 和安全门禁选择证据。Context Prefix 继续只用于召回，不能进入回答证据。
- **实测：** targeted v5 中 `模拟物流边界` 得分 `0.567471`，答案正确否定“两小时承诺”并引用；Embedding、Rerank、Expansion、Generation 均无失败/fallback。v3/v4 失败运行仍保留，未被覆盖。

### 5. Markdown 换行和 alias 口径会制造假失败

- **症状：** 语义正确且已有引用的答案被判 claim-citation support=0；“一张/1 张”“优惠券/券”等自然表达也会漏掉 required claim；有时未引用的字面 alias 比已引用的等价表达更早命中。
- **根因：** claim scorer 只按句号切句，没有把 Markdown 换行当事实句边界；alias 是全局字面表，缺少 fact scope；匹配策略又采用 first match。
- **最终修复：** Markdown 换行视为句子终止；同义表达只在对应 canonical fact 内受控归一；同时存在未引用 literal 与已引用 equivalent 时优先后者。保留 strict exact-ref 指标作诊断，不再把可辩护等价证据直接判错。
- **实测：** 在不改答案、不改证据、0 Provider 调用的 offline rescore v3 中，任务成功由 `39/60` 升至 `49/60`，required-claim completeness=`0.9674`、claim-citation support=`0.9565`、known regression=`35/40`。总成功率 `0.8167` 仍低于 `0.85`，状态继续 `FAILED_RETAINED`。

### 6. 生成 repair 不能偷看评测 gold

- **症状：** 有证据仍误拒答、短的“不支持/不保证”句缺引用、并列问题漏答是生成失败的主要来源。把缺失 `requiredClaims` 直接写进 repair prompt 可以快速提高分数。
- **为什么拒绝：** frozen claim 和 holdout alias 是评测标签，不是线上请求可见信息；注入 repair 会形成 gold 泄漏（label leakage），得到的分数不再代表运行时能力。
- **最终修复：** Prompt 明确区分当前 `evidenceState` 与正文中的“证据不足”，要求逐子问题回答并让每个事实句就近引用；Verifier 对 SUPPORTED 下的误拒答、缺引用、越界引用和短否定事实最多 repair 一次。repair 只读取用户问题、可信证据、runtime query plan 和格式失败原因，保留初答、额外 token 与延迟。
- **实测：** 正式 60 条触发 repair 12 次，总 token `23,125`，端到端 P50/P95=`1845.26/3449.83 ms`；0 runtime error、0 严重安全违规、无效引用 0。质量仍未达标，说明 repair 是安全兜底，不是掩盖召回或标签问题的万能重试。

### 7. 两条冻结标签要求了知识库没有写出的事实

- **症状：** `rag-v4-fresh-extra-021` 要求回答连续签到中断后的重置细节，`rag-v4-fresh-extra-024` 要求列出转人工时携带的具体排查上下文；现有知识只覆盖一般签到与转人工规则。
- **根因：** 数据构造时把相邻主题当成直接支持，标签事实粒度超过已发布文档。
- **错误方案：** 降低阈值、把主题相关 chunk 当答案、事后补文档或改 frozen label，都会掩盖数据缺陷并增加幻觉。
- **最终处理：** 两题继续返回 `INSUFFICIENT`，在 targeted run 中标记 `knownLabelLimitCaseIds`；历史标签不改，后续新数据从 catalog 的原子事实反推问题。
- **实测：** 7 条 Retrieval targeted 为 5/5 修复目标通过、2/2 已知标签限制保持安全拒答，状态为 `PASSED_TARGETED_WITH_KNOWN_LABEL_LIMITS`。

### 9. 最终回归不能用全仓格式化掩盖历史基线

- **症状：** `ruff check` 报告本轮 5 个文件的 import 顺序问题；直接执行 `ruff format --check app benchmarks tests` 又报告 234 个历史文件需要重排，计划中引用的 `scripts/check_docs_consistency.py` 当时也不存在。
- **原因：** import 错误属于本轮局部变更；234 个文件是仓库既有格式基线，若为通过一次检查而全量格式化，会制造与 Search/RAG 无关的大 diff。文档一致性此前只有 manifest 的链接、SHA 和禁用说法校验，没有独立命令入口。
- **最终修复：** 仅对 5 个本轮文件运行 Ruff 的 import 自动修复，不批量改写历史文件；新增 manifest 驱动的 `scripts/check_docs_consistency.py`，校验四份当前证据文档必须包含的 run、状态与边界词，并复用 manifest 的链接、结果 SHA 和禁止说法检查。
- **最终回归：** Python `1032 passed / 7 skipped / 0 failed`，7 条均为显式要求真实 MySQL 8 的迁移用例；Java common `59/59`、Search `21/21`，Testcontainers `MiddlewareIT 7/7`；Ruff、24 项 manifest 普通/本地结果检查、四文档一致性和 `git diff --check` 通过。
- **当前边界：** 全仓 `ruff format --check` 的 234 个历史文件格式债务仍单独披露，不把它写成通过；本轮未重复 order 模块 `TransactionPersistenceIT 3/3`，只沿用其已冻结 E2 历史证据，避免无关格式 churn 或重复扩大回归范围。

### 10. Search v2 细粒度类目不能破坏历史归一化契约

- **症状：** Python 全量首次回归为 `1029 passed / 7 skipped / 3 failed`。`笔记本/台式机/积木/吉他` 从历史宽类目 `电脑/玩具/乐器` 变成细粒度叶子，两个旧 Search relevance 断言失败；同一修改还改变 `search_taxonomy.yml` SHA，使 v1 holdout 数据锁失败。
- **根因：** 为 Search v2 运行时硬约束增加的叶子类目直接插入了历史 query-normalization taxonomy。一个文件同时承担“稳定的公开归一化契约”和“可演进的运行时目录推断”，导致新增能力改变旧 API 语义。
- **错误方案：** 更新旧测试期望和 v1 lock 的 taxonomy SHA 可以让 CI 变绿，但会事后改写历史数据契约，也无法解释下游为什么从宽类目突然收到叶子类目。
- **最终修复：** 恢复 `search_taxonomy.yml` 到锁定 SHA `3c920bc2...`；新增独立 `search_runtime_taxonomy.yml` 保存运行时叶子类目。`normalize_product_search_query` 继续返回稳定宽类目，`infer_product_category` 读取 additive runtime taxonomy；`ProductQueryPlan` 仅把细粒度结果作为附加 variant/constraint，未知动态目录仍保留原问题。
- **实测：** 历史 lock SHA 重新一致，Search contract、relevance、runtime category、ProductQueryPlan 与 ProductService Runner 定向回归 `41/41` 通过，Ruff 通过。该修复不改 Search v2 正式或 post-fix 已保存成绩。

## 八、面试时必须主动说明的边界

- 当前是本地完整栈和演示数据，没有真实生产流量、GMV、CTR/CVR、线上售后率或 SLO。
- 离线评测规模有限，冻结集满分只说明当前确定性契约通过，不代表开放世界准确率 100%。
- 多智能体只在职责独立、可并行或需要隔离审查时使用；简单任务仍走规则、Workflow 或单专家。
- 写操作实现了确认、业务幂等、状态核对和人工复核，不承诺网络分区下 exactly-once。
- 视觉搜索依赖云 API，本地已实现熔断和降级，但尚无生产级供应商 SLA 与长期成本数据。
- DataAnalyst 只读十个治理视图；InventoryOps 只生成建议，不自动改库存或创建采购单。
- 运营推荐目前是受规则约束的候选插入，不是广告竞价、预算和结算系统。
- 项目没有进行模型训练或微调，主要工作集中在 Agent 编排、RAG/检索、工具治理、评测、可靠性和全栈落地。
- 27/27 Commerce、18/18 安全与 162/162 Search/RAG contract 仍是确定性合成证据；Search/RAG 另有 `SYNTHETIC + local-live` E3，不能混为同一证据等级。
- Search/RAG mature 已采集多 K Recall/MRR/NDCG、分组 holdout、组件消融、bootstrap CI、阶段延迟、TTFT 和 token；Embedding/Rerank/LLM 未提供完整可核验人民币账单，成本必须写 `UNPRICED`。
- 中文 final 说明能力上限在 K=3 而非 K=1；WANDS 说明 Rerank 主要改善前排 NDCG 而没有统计支持的 Recall@5 增益；RAG fresh no-answer accuracy 仅 0.75，生成 24 条只有 16 条通过且有 1 条严重安全失败。这些是当前最应主动讲的 badcase，而不是继续追求满分数字。
- 管理端试用和匿名报告机制已实现，但 `REAL_USER` 样本仍为未采集，不能声称 FCR、CTR/CVR 或业务 uplift。
- Java 高风险链路已有定向测试和 Testcontainers IT，但 common/order 当前行覆盖只有约 12.89%/13.39%，不包装成高覆盖工程。

## 九、建议优先准备的六个故事

1. 从伪多智能体到隔离 Supervisor Harness：为什么拆、如何限制专家、如何保证 root-only 写操作。
2. 从类目推荐到 ShoppingMission + 权威报价：用途追问、硬约束、解释排序和商业治理。
3. 从普通 RAG 到证据可验证的条件式 Agentic RAG：路由、分数量纲、引用和成本预算。
4. 从“能生成 SQL”到受治理 DataAnalyst：语义视图、AST Guard、最小权限和 Trace。
5. 从图片问答到完整视觉商品搜索：图片资产安全、多模态召回、精排、商品复验和熔断降级。
6. 从 happy path 到可恢复 Agent：业务幂等、未知结果、Worker 租约、故障演练和 badcase 回归。

这六个故事都应按“症状 → 定位证据 → 第一版错误假设 → 最终方案与取舍 → 可复现结果 → 当前边界”展开，能够覆盖 AI 应用、Agent、AI 全栈和 Java 后端面试中的大部分项目深挖。
