## 1. 面试时先讲清楚的全局背景

这次排障不是修一个孤立页面，而是在一个已有大量未提交修改的全栈项目中同时处理四类用户可见问题：

1. 推荐问题可以回答，但多数售后、物流等 RAG 问题失败或过早转人工。
2. 管理端侧栏和内容区同时滚动，整页下滚时产生视觉漂移。
3. 购物车数量为 1 时减号被禁用，没有符合业务直觉的删除动作。

## 3. 案例一：推荐成功，不代表 RAG 链路正常

### 3.1 现象

“最近有什么新品”能够返回商品卡片，“会员等级如何计算”也能命中 FAQ；但换成退货、物流、优惠券、发票或地址修改等问题时，经常不引用知识，甚至连续两轮后自动转人工。

这个现象很容易让人先怀疑模型 Key、Embedding、Qwen3 Rerank 或 Elasticsearch。但推荐走的是 `PRODUCT_SEARCH` 工具链，精确 FAQ 又有独立快速路径，它们成功只能证明各自分支可用，不能证明通用 RAG 图路由正确。

### 3.2 证据链

1. 在线 LLM、Embedding 和 Qwen3 Rerank 均能请求成功，排除“Key 全部失效”。
2. 精确 FAQ 可以命中，说明知识目录和基础检索并非整体不可用。
3. 非精确退货问题回答内容基本正确，但 `sourceRefs=[]`，说明模型可能靠通用知识回答，并没有收到知识库证据。
4. 代码跟踪发现 `build_context_node` 只对 `CHAT` 和 `PRODUCT_CONSULT` 预取 RAG；`REFUND`、`QUERY_LOGISTICS`、`INVOICE` 等更需要政策约束的具体意图反而绕开了检索。
5. 首次补齐意图路由后，退货问题虽然命中正确文档，却一次注入 6 条候选，暴露了第二个问题：旧逻辑只判断最高分是否过门槛，随后把所有候选都当作引用。
6. Worker 在二次意图识别后没有重新计算未解决计数，基础设施降级回答也没有清零计数，导致“系统已经回答，但状态机仍认为未解决”。

### 3.3 根因

这是三个问题叠加，而不是单纯的模型质量问题：

- 图路由覆盖不完整：具体业务意图绕过 RAG。
- 证据门槛粒度错误：用最高分代表整个候选集合的质量。
- 会话状态更新顺序错误：二次分类改变了意图，但 `unresolved_count` 沿用了旧计算结果。

### 3.4 修复

- 建立 `_RAG_PREFETCH_INTENTS`，让退款、物流、优惠券、发票、地址、售后等政策类意图使用固定 RAG；商品搜索、真实订单查询和明确转人工不做无意义预取。
- 给专用业务提示词注入经过 XML 转义的 `<knowledge_context>`，并明确知识内容是不可信外部数据，不能覆盖系统规则。
- 将证据过滤改为逐条判断；`candidateCount` 表示召回候选数，`sourceCount` 只表示真正注入回答的证据数。
- 缓存命中后重新执行有效期、目录和证据门槛过滤，防止旧缓存继续传播噪声。
- Worker 在二次意图识别后重新计算未解决计数；FAQ、正常降级回答和基础设施异常不再错误累计。
- 强制自动转人工从连续第 2 次低置信度延后到第 3 次；用户明确说“还是没解决”仍立即转人工。

### 3.5 回归与边界

最终非精确退货问题的真实轨迹为：`intent=REFUND_STATUS`、`candidateCount=6`、`sourceCount=1`、有效证据分数 `0.581698`，回答准确且没有转人工。

“支付方式有哪些”仍然没有具体答案，但这是知识覆盖缺口：知识库中没有支付渠道规则，重排最高分只有 `0.358`。此时拒绝编造是正确行为，不能把“没有业务知识”误判为“RAG 又坏了”。这也是面试中值得强调的质量边界：先区分检索故障、低相关证据和知识缺失，再决定修代码还是补内容。

### 3.6 可复述亮点

> 我没有因为某个推荐问题成功就判断 AI 链路整体正常，而是按路由分支对比 trace。最终发现具体售后意图反而绕过 RAG，并进一步定位到证据集合只看最高分的污染问题。修复后把候选数和实际引用数拆开，使可观测数据能表达真实证据质量。

## 4. 案例二：Spring Data 查询对象看似正确，最终 DSL 却错误

### 4.1 现象

数据库和商品页面中存在索尼降噪耳机，直接查询 Elasticsearch 也能返回 2 件商品，但 `/search/products` 对相同中文关键词返回 0。

### 4.2 错误假设与排除过程

一开始最像中文分词或索引同步问题。实际检查发现：

- ES 索引有对应文档。
- IK 分词正常。
- 直接执行 `match productName=降噪耳机` 返回 2 件。
- 分类字段和价格字段也存在。

因此问题只可能出现在 Java 搜索服务生成的最终查询。旧代码使用 Spring Data Elasticsearch `Criteria`，中间对象打印出来似乎包含多个条件，但其组合方式生成了不符合预期的最终 DSL。这个案例的关键经验是：不要只检查查询构造器的中间状态，要查看真正发给搜索引擎的语义，并与最小可用 DSL 做对照实验。

### 4.3 修复

改用类型化 `NativeQuery` 明确表达查询意图：

- `match productName`，boost 3。
- `match_phrase productName`，boost 5。
- `match productDesc`。
- 三个文本条件使用 `should`，并设置 `minimum_should_match=1`。
- 分类和价格放入 `bool.filter`，不影响文本相关性评分。
- 无筛选条件时显式使用 `match_all`。
- 保留综合、价格、销量排序和稳定的 `productId` 次级排序。

### 4.4 回归

- “降噪耳机”：2 件。
- “索尼”：2 件。
- “耳机”：2 件。
- “降噪耳机”加 `categoryId=20003`：2 件。
- 再加 3000–4500 元：1 件 XM6。
- 浏览器桌面页显示“「降噪耳机」共 2 件”，两张商品图均成功加载。

### 4.5 可复述亮点

> 我通过“直接 ES 成功、服务接口失败”的差分实验把范围收敛到查询翻译层。最终放弃容易产生隐式语义的 Criteria 组合，改成类型化 NativeQuery，并把评分条件与过滤条件分离；这既修复了中文漏召回，也让 DSL 可测试、可解释。

## 5. 案例三：Redis 旧快照覆盖 MySQL，分类树看起来像前端 Bug

### 5.1 现象

首页能看到商品，但点击任意分类都是空页。MySQL 已经导入新分类和商品，分类接口却可能继续返回旧树。

### 5.2 根因

旧服务逻辑先查 MySQL，又在后面读取一个没有版本号的 Redis 分类快照，并用缓存值覆盖数据库结果。只要 Redis 里残留过旧数据，重新导入数据库也不会修复页面。

同时还发现一处独立风险：递归删除分类时使用 `children != null || !children.isEmpty()`。当 `children == null` 时仍会计算右侧表达式并触发空指针；正确条件应为 `&&`。

浏览器端还有第二层缓存。如果只修后端，已打开过页面的浏览器仍可能继续使用旧 key，因此需要一起升级缓存版本。

### 5.3 修复

- 明确 MySQL 是分类事实源，读取数据库后刷新 Redis 快照，不再让无版本缓存覆盖最新目录。
- `/product/loadCategory` 显式加载父子树和属性。
- 前端分类缓存键从旧版本升级为 `product:category:v2`。
- 将递归删除条件修为 `children != null && !children.isEmpty()`。

### 5.4 回归

- 分类树包含 9 个根分类，父子结构正常。
- 无分类筛选时第一页共 33 件商品。
- 父分类 `10001`：12 件。
- 子分类 `20003`：3 件。
- Chromium 中父、子分类页面分别渲染 12 和 3 张商品卡，没有失败请求。

### 5.5 设计取舍

本地演示数据量很小，因此读取 MySQL 并刷新 Redis 的一致性优先级高于缓存收益。若进入高流量生产环境，更合理的演进是带版本的 cache-aside、变更事件主动失效或双缓冲目录切换，而不是每次读取都重建快照。

## 6. 案例四：双滚动容器造成管理端侧栏漂移

### 6.1 现象与根因

管理端某些长页面既能滚动整个文档，又能滚动右侧内容区。侧栏使用 `100vh`，页面内部又使用多组 `calc(100vh - ...)`，当 `body` 和内容容器同时具备滚动能力时，侧栏会随文档移动，看起来像定位漂移。

### 6.2 修复

- 根布局固定为 `100vh` 和 `100dvh`，并设置 `overflow: hidden`。
- 左侧栏固定视口高度，只允许 `.left-side-content` 独立滚动。
- 右侧容器设置 `min-height: 0` 和 `overflow: hidden`。
- `.right-body` 成为唯一主内容滚动容器，并使用 `overscroll-behavior: contain` 防止滚动链传递。
- RAG 和客服记录页移除重复且不准确的视口高度计算。

### 6.3 回归

在 1440×900 视口验证 RAG、客服记录和商品管理页面：`htmlHeight=900`、`bodyHeight=900`、`window.scrollY=0`。商品页主内容从 `scrollTop=0` 独立滚到 `138` 后，侧栏 `top` 仍为 0。

这个问题不能只靠截图验证；必须同时读取 `window.scrollY`、各容器的 `scrollTop` 和侧栏边界坐标，才能证明滚动所有权真的正确。

## 7. 案例五：数量 1 再减是删除，不是禁用

### 7.1 现象

旧购物车在数量为 1 时直接禁用减号，页面又没有明显的桌面删除入口。虽然移动端支持滑动删除，但桌面用户无法发现，业务语义也与主流电商不一致。

### 7.2 修复

- 数量大于 1 时，减号继续执行增量更新。
- 数量等于 1 时，减号语义切换为“移出购物车”，并弹出二次确认。
- 每行增加始终可见的垃圾桶图标，保留移动端滑动删除。
- 使用 `Set<string>` 维护行级请求锁，避免对一行操作时把所有购物车项一起禁用。
- 删除成功后同步本地列表、选中集合、数量输入快照、滑动状态和全局购物车角标。

### 7.3 回归

使用演示用户的 4 行真实购物车验证：数量 1 的减号和垃圾桶按钮都会弹出标题为“移出购物车”的确认框。测试中选择取消，4 行数据保持不变；4 张商品图全部成功加载。

这项修复的重点不是一个 `if`，而是把“库存数量状态”和“购物车条目生命周期”衔接起来，同时处理并发点击和多个前端状态源。

## 8. 案例六：Qwen3 Rerank 不能只改模型名

### 8.1 现象与根因

项目旧代码按 DashScope native 协议发送嵌套的 `input` 和 `parameters`，并从 `output.results` 解析结果。百炼 `qwen3-rerank` 的 compatible 端点要求顶层 `model`、`query`、`documents`、`top_n` 和可选 `instruct`，结果也位于顶层 `results`。因此只把模型名改成 `qwen3-rerank` 会稳定失败并回退 RRF。

另一个隐藏问题是旧分数解析使用 Python 的 `or` 链。合法的 `relevance_score=0.0` 是假值，会被错误替换成旧分数。

### 8.2 修复

- 增加 `RERANK_API_FORMAT=compatible`，同时保留 `dashscope_native` 兼容旧模型。
- 专用 `RERANK_API_KEY` 优先于通用 `DASHSCOPE_API_KEY`。
- 增加电商知识检索用 `RERANK_INSTRUCT`，并把模型、地址、协议和指令加入 RAG 缓存指纹。
- 按协议分别构造请求和解析响应，过滤越界索引、布尔索引、重复索引和非法分数。
- 用显式 `is None` 判断保留 `0.0`。
- 无 Key、超时、熔断或无效响应时保留原顺序/RRF 安全降级。
- 配置了 Key 后拒绝空地址、Workspace 占位符和空模型，避免“看似配置完成、实际永远失败”。

### 8.3 可复述亮点

> 接第三方兼容 API 时，我会对照请求体、响应层级、错误码和边界值，不把“OpenAI compatible”理解成所有端点完全同构。零分被 `or` 吞掉是一个典型的语言真值陷阱，也专门增加了回归用例。

## 9. 案例七：WSL 崩溃后重构启动策略

### 9.1 真实踩坑

完整项目同时包含多个 Docker 中间件、十余个 Java 服务、两个 Python 进程和两个 Vite 前端。曾出现 Maven 构建、容器启动和多个 JVM 并发进行，导致 WSL 内存压力过大并直接崩溃。

另一个不直观的问题来自启动互斥锁：`start.sh` 用文件描述符 9 持有 `start-stop.lock`。后台子进程如果继承该描述符，即使父启动脚本退出，锁仍不会释放，后续 `start.sh` 或 `stop.sh` 会误判为仍有操作进行。

### 9.2 修复策略

- 中间件、构建、Java 服务、Agent 和前端按阶段串行启动。
- Maven 使用受控堆和 Serial GC；Java 服务默认使用较小的 `Xms/Xmx`、元空间、直接内存和线程栈。
- 只在源码比构建产物新时重建，避免每次启动都执行全量 Maven package。
- 各服务逐一做端口占用检测，冲突时向后顺延，并把最终端口写入 `run/runtime.env`。
- 后台 Java、MCP、Agent、Worker 和前端启动时统一执行 `9>&-`，显式关闭继承的锁描述符。
- 测试、构建和重启保持单进程；只重启受影响服务，不整体停止可用环境。

### 9.3 面试表达

不要把这段描述成“做了高并发优化”。准确说法是：在资源受限的 WSL 开发环境里，通过启动编排、内存上限、增量构建和文件描述符治理降低峰值资源，并使一键脚本可重复执行。这体现的是工程稳定性和故障恢复意识。

## 10. 一套可迁移的排障方法

这次问题可以归纳为一条可迁移的方法：

1. 先按真实请求路径拆分系统，不因为一个分支成功就推断同类功能都正常。
2. 在每层构造对照实验：直接 ES 与 Java 接口、接口与浏览器、MySQL 与 Redis、候选数与实际引用数。
3. 优先寻找“数据在哪一层发生变化”，而不是先修改参数或提高模型能力。
4. 对状态机问题检查更新顺序、清零条件和重试/转人工阈值。
5. 对缓存问题明确事实源、版本、失效机制和旧客户端缓存。
6. 对 UI 滚动问题验证滚动所有权和几何数据，不只看静态截图。
7. 对第三方模型接口验证完整协议和边界值，不只验证模型名和 Key。
8. 修复后同时保留单元测试、真实接口回归、浏览器交互和日志审计四类证据。

## 12. 客服锁行语义与 WebSocket 终态一致性

### 时间与 commit

- 发现与修复：2026-08-06。
- 整改基线和当前 HEAD：`f639599e335b97f6156cc41923d53948bcbf6549`；本次改动未提交。
- 性质：基线源码审计发现的并发缺陷，不伪装成已经发生的生产事故。

### 业务现象

基线中的 `claim/activate/reply` 用带状态条件的 `UPDATE` 和 `rowcount` 同时表达权限、状态迁移和幂等。合法重复操作可能因为“值没有变化”被解释为失败；并发认领时也难以向调用方区分“同一客服重复请求”和“其他客服已占有”。AI、FAQ 快路径和人工回复的持久化/推送顺序又不统一，存在客户端先看到 DONE、历史接口暂时还没有终态的窗口。

### 错误假设

错误假设是“`rowcount == 1` 就等价于业务前置条件成立”。`rowcount` 是数据库执行结果，不是领域状态；其语义还会受连接的 affected-rows/found-rows 配置影响。另一个错误假设是“WebSocket 是实时链路，所以应先推送再落库”，但 WebSocket 不能承担事实源职责。

### 证据链与根因

基线 `support_service.py` 把状态、归属和更新结果压在一条条件 UPDATE 上。Worker 的普通回答、FAQ 和人工回复也有不同的终态顺序。前端则按数组位置和 fallback 消息合并，HTTP/WS 乱序时可能覆盖另一条正在生成的回答。根因是事务事实、传输事件和 UI 视图没有共同使用 `messageId` 作为稳定聚合键。

### 修复与取舍

- 事务内先 `SELECT ... FOR UPDATE`，只根据锁定行的状态和客服归属决定幂等、越权或非法迁移，再执行必要 UPDATE。
- 所有终态先持久化，再发送 DONE；DONE 携带与历史接口相同的 `sourceRefs`。发布失败保留数据库事实，由历史加载恢复。
- Web 端按字符串化 `messageId` 幂等 upsert；PARTIAL 只追加对应消息，空 DONE 不覆盖内容，人工新消息可直接插入，迟到分片不能复活终态。
- 引用区只展示真实 title/heading/snippet/version/source/retrieval；数据没有 URL 就不制造链接。

取舍是允许 WebSocket 发布失败时用户需要依靠刷新/历史恢复，而不通过“先发成功帧”制造虚假的实时成功。

### 当时验证与当前回归

修复过程增加/更新 `test_support_session_race.py`、`test_stream_service.py`、`agent-message-reducer.test.ts`。当前 Agent 为 `490 passed, 3 skipped`，被跳过的三条真实 MySQL migration/事务用例已另跑为 `3 passed`。默认 Playwright 的桌面和移动端乱序帧用例此前总结果为 `6 passed, 2 intentional skips`；本轮相关 mock E2E 又复跑 `4 passed`。

### 残余边界

本地测试覆盖锁行、重复帧和乱序，不代表生产 WebSocket 网关在长连接风暴、跨机房或大规模重连下的容量结论。消息历史是恢复面，不等价于可靠推送系统。

### 60 秒面试复述

> 我把客服并发问题拆成数据库事实、WebSocket 事件和前端聚合三层。数据库不再用 rowcount 猜业务状态，而是锁行后判断归属；终态统一先落库再推送；前端用字符串化 messageId 做幂等 reducer。这样 HTTP 先到、WS 先到、重复 DONE、迟到 PARTIAL 和人工消息都收敛到一个终态，推送失败时也不会污染数据库真相。

## 13. RAG 与商品搜索评测从“能跑”变成硬门禁

### 时间与 commit

- 发现与修复：2026-08-05 至 2026-08-06。
- 基线：`f639599e335b97f6156cc41923d53948bcbf6549`；当前仍为未提交工作树。

### 业务现象

原 RAG golden 的 `relevantIds` 含占位 ID，无法稳定对应知识版本和 chunk；商品搜索的 graded 层在 ES、标签或某路召回缺失时可以跳过，runner 仍可能成功。这样的分数不能证明检索有效，也无法判断是代码提升还是数据被悄悄改了。

### 错误假设

错误假设是“脚本退出 0 且有一个总分，就等于评测可信”。如果标签不是仓库真实实体、数据集和知识目录没有 SHA、缺依赖时选择 skip，总分只证明脚本走完了。

### 证据链与根因

对照知识数据库、FAQ questionId 和 47 件商品目录后，发现运行时 chunk ID 带 release/version，不适合直接冻结；但 FAQ questionId、文档 `source + heading` 和商品 productId 是稳定业务标识。根因是评测契约冻结了实现 ID，而没有冻结数据来源、映射规则和缺依赖行为。

### 修复与取舍

- RAG 改用 FAQ `questionId` 和文档 `source + heading` 的 `relevantRefs`，运行时再映射到实际 chunk；锁文件同时校验知识 release、知识内容 SHA 和数据集 SHA。
- 阈值扫描先约束 Recall/MRR，再在合格阈值中选择拒答 F1；输出逐 case、placeholder 检测、citation rate 和 no-answer P/R/F1。
- 搜索集人工冻结 30 条 graded query、47 件真实目录和目录 SHA；keyword/vector 任一路为空、ES/标签缺失时硬失败。
- 门禁不是追求满分。保留 RAG 两个失败 case和搜索两个 zero-hit case，作为下一轮 badcase。

### 当时验证与当前回归

RAG 34 条：threshold `0.65`，Recall@K `0.9167`，MRR `0.9167`，citation rate `0.9167`，no-answer F1 `0.9524`，placeholder 为空。失败 case 是“会员等级怎么升级”和“订单生成以后收货地址填错了怎么办”。

搜索查询理解 127 条全通过；graded 30 条为 Recall@10 `0.9333`、MRR@10 `0.8250`、NDCG@10 `0.8411`，两路召回健康。zero-hit 是“蒸烤一体机”和“100W车载充电器”。冻结会话集当前为 `134/134`，含两条确定性候选选择多轮，但仍不是线上端到端准确率。

### 残余边界

这些是本地小规模、人工冻结数据，不是公开行业 benchmark，也不是线上搜索转化。生成答案的事实性和语气仍没有稳定 LLM judge 门禁；知识覆盖缺口不能靠调阈值消除。

### 60 秒面试复述

> 我发现旧评测最大的问题不是分低，而是标签和运行时实体对不上，缺 ES 时甚至能跳过成功。我把 FAQ questionId、文档 source+heading、真实 productId 作为稳定标识，并用知识 release、内容 SHA、数据集 SHA 和商品目录 SHA 锁住口径。runner 缺任何真实召回就失败，同时保留逐 case badcase，所以分数能复现，也不会靠修改标准拿高分。

## 14. 结构化意图、强制工具与可核算的模型指标

### 时间与 commit

- 源码审计与修复：2026-08-06，基线同上。
- 性质：安全和可观测性缺口，未声称已经造成线上错单。

### 业务现象

意图分类依赖模型输出文本 JSON；schema 不合法时可能落到过宽的执行分支。订单、物流、优惠券等事实问题若模型跳过工具，回答仍可能继续生成。token 指标缺 model/fallback 维度，字符流量还容易被误当 token；没有人民币成本和未定价口径，阶段时延也不足以定位慢在排队、意图、RAG、工具还是生成。

### 错误假设

“Prompt 里要求 JSON”和“Prompt 里要求必须调工具”都不是运行时约束。模型遵循指令是概率行为，交易事实和写操作授权必须由代码节点兜底。没有价格的模型成本也不能用猜测单价补齐。

### 证据链与根因

基线分类器优先解析自由文本，工具调用是否发生主要依赖模型；指标标签无法区分模型和 fallback。根因是把协议正确性、业务事实性和观测口径都委托给了生成模型。

### 修复与取舍

- provider 支持时优先 `with_structured_output(IntentDecision)`；不支持、校验失败或异常才回退文本 JSON，并记录 `schema_success/fallback/invalid`。
- 非法输出进入确定性安全意图，不直接执行写工具。
- 订单、物流、优惠券和写提案缺少必需工具时，deterministic forced-tool 节点补齐；工具失败明确降级，不允许模型编造状态。
- token/cost 使用 `kind/model/fallback` 低基数标签；价格来自 `LLM_PRICING_CNY_PER_MILLION_JSON`，未配置只累计 `unpriced` token。
- 时延只允许 `queue_wait/intent/rag/first_token/tool/generation/total` 七个固定阶段，禁止 query/userId/messageId label。

### 当时验证与当前回归

新增结构化输出成功、provider 不支持、schema 失败、安全 fallback、强制工具、工具失败、定价/未定价和阶段标签契约测试。当前 Agent 全量 `490 passed, 3 skipped`，三条 MySQL 用例另跑 `3 passed`，Ruff 通过；Prometheus/Grafana/告警静态契约包含成本和七阶段指标。

### 残余边界

本次没有使用生产 provider 流量统计 schema 成功率或真实人民币账单。只有 provider 返回 usage 才能核算 token；未配置准确价格时保持 unpriced 是设计行为，不是成本为零。

### 60 秒面试复述

> 我把“请模型按格式输出、请模型记得调工具”改成可执行协议。先走 structured output，失败才解析文本，非法结果进入安全意图；必需事实工具由图节点检查并补调。指标只用固定低基数标签，token、人民币成本和未定价量分开，阶段时延固定为七类。这样模型不稳定不会直接变成业务事实不稳定，成本口径也不会靠猜。

## 15. 同一业务动作绕过 token 与未知结果处理

### 时间与 commit

- 审计、迁移和回归：2026-08-06。
- 相关历史基础：`b4a1044` 已引入 Java 幂等账本；本次在其上补业务键和有界对账。

### 业务现象

token 只能防同一 token 重放，用户仍可能为同一个订单退款、确认收货或评价生成第二个活跃 token。网络超时又不能证明 Java 写失败：立即标失败会允许新 token 再执行，永久停在 EXECUTING 则无法收敛。

### 错误假设

错误假设是“唯一 token 等于唯一业务动作”，以及“HTTP 超时等于远端没有提交”。跨服务写操作中，响应丢失和提交失败不可由客户端单方面区分。

### 证据链与根因

基线 Agent 以 action token 作为唯一去重键，缺少 `user + actionType + 资源 ID` 维度；不确定结果主要依靠悬挂状态。根因是传输幂等键和业务唯一性被混为一谈，也没有给不确定状态设置次数/时间边界。

### 修复与取舍

- `business_key = userId + actionType + 业务资源 ID`；规范 JSON 排序后计算 `args_fingerprint` SHA-256。
- 生成列 `active_business_key` 只在 PENDING/EXECUTING/INCONCLUSIVE/MANUAL_REVIEW 占唯一索引。相同指纹复用 token，不同指纹返回冲突；旧数据用 `legacy:<token>` 回填。
- HTTP 未知结果进入 INCONCLUSIVE，只查询 Java 幂等账本和领域状态，绝不重发副作用；次数或 deadline 到边界后进入 MANUAL_REVIEW，继续占用业务键。
- Java 账本同步这些状态和对账字段。项目承诺是“幂等账本 + 有界对账 + 人工复核”，不是 exactly-once。

### 当时验证与当前回归

Agent 业务键、同指纹复用、异指纹冲突、未知结果和人工复核测试通过；真实 MySQL 8 旧库迁移 gate `2 passed`。Java 的 `AgentActionStatusServiceTest` 和 `OrderRequestIdempotencyServiceTest` 包含 INCONCLUSIVE/MANUAL_REVIEW 路径；最终 Java Reactor `133 passed, 0 skipped`。

### 残余边界

人工复核目前是项目内检索接口和状态，不是企业工单系统。网络分区时仍可能长时间未知；系统避免自动重放，但不能证明物理世界只发生一次。

### 60 秒面试复述

> 原来 token 只能防同一个请求重放，挡不住为同一订单重新生成 token。我增加业务键和参数指纹，活跃状态通过生成列唯一索引占位。同业务同参数复用，参数不同直接冲突。HTTP 超时进入 INCONCLUSIVE，只查 Java 幂等账本和领域状态，达到次数或时间边界转 MANUAL_REVIEW，整个对账路径绝不再次发送副作用。

## 16. 推荐点击不能只靠客户端 token

## 18. Seata 复合主键锁长度与旧容器挂载

### 时间与 commit

- 真实下单故障、迁移与恢复：2026-08-06。
- 涉及基线脚本 `sql/15_seata.sql` 和本地 `aishop-seata` 容器。

### 业务现象

首轮下单的库存分支注册失败，Seata 报 `Data too long for column 'pk'`。同时遗留 Seata 容器重启返回 exit 127，OCI 报 bind mount 的文件/目录类型不匹配。

### 错误假设

官方示例 `lock_table.pk VARCHAR(36)` 看似够 UUID，但本项目 `sku_stock` 是 `product_id varchar(15) + property_value_id_hash varchar(32)` 复合主键，Seata 序列化后的锁键更长。容器问题也不是业务数据损坏，而是 Docker Desktop/WSL 留下的旧 bind mount 元数据。

### 证据链与根因

Seata 日志直接给出 pk 截断错误；schema 核对确认复合主键。遗留 XID `192.168.1.139:8092:2729990257713659928` 的 global/branch/lock 和四库 undo_log 随后均核对为 0。容器 inspect 显示 exit 127 和 application.yml mountpoint 类型错误。

### 修复与取舍

- 将 `lock_table.pk` 扩为 `VARCHAR(128)`，并加入幂等 ALTER；执行元数据初始化后实库核验长度 128。
- 只移除无法启动且已停止的 `aishop-seata` 容器，用同一配置重建；没有删除数据卷。
- 对遗留事务先做只读核对和正常回滚，再确认库存、订单、支付、购物车 undo_log，无需手删 Seata 行。

### 当时验证与当前回归

`seata-pk-migration.txt` 记录实库长度 128；`seata-recovery-consistency.txt` 记录 branch/lock/undo 均为 0。修复后真实订单完整走过创建和取消，最终 active Seata transactions/locks 均为 0。

### 残余边界

128 是按当前键长度和 Seata 序列化留余量，不是对未来任意主键的证明。容器重建解决本机 WSL 挂载元数据，不代表生产容器编排已有高可用或自动修复。

### 60 秒面试复述

> Seata 官方表的 pk 是 36，但我们的库存表是 15 加 32 字符的复合主键，序列化锁键超过 36，分支注册直接失败。我先核对 XID、锁和 undo，确认没有残留副作用，再把 schema 幂等扩到 128。另一个 exit 127 是旧 bind mount 元数据，不是库坏了，所以只重建停止容器、不删卷。修复后完整下单取消，事务和锁都归零。

## 19. 启动端口竞态、日志污染与运行中替换 JAR

### 时间与 commit

- 多轮完整栈启动排查：2026-08-06。
- 证据：`start-stack*.txt`、Search bind diagnostics 和 `start.sh` 差异。

### 业务现象

Search/MCP 重启时会在旧进程退出和新进程 bind 之间发生短暂竞态；旧日志中的 `APPLICATION FAILED` 又可能让新一次启动被误判失败。构建脚本还可能在 JVM 正运行时替换 executable JAR，Spring Boot 懒加载嵌套类后会出现延迟的类加载错误。完整栈中还遇到 Elasticsearch 容器健康但宿主 `9201` 未发布。

### 错误假设

“启动前端口空闲”不能保证几百毫秒后仍空闲；“日志里出现过失败”不能证明当前进程失败；“JAR 已经被 JVM 打开”也不代表后续不会再从压缩包懒加载类。

### 证据链与根因

精确端口 strace 和多轮启动日志显示目标端口短暂冲突；Search 在 Agent/MCP 同时启动时更易暴露。旧日志未清空会混合多次进程输出。Docker 端口检查则显示 Elasticsearch 没有 host binding。根因是启动脚本把端口检查、进程身份、日志代际和构建产物生命周期当成静态状态。

### 修复与取舍

- 只对日志明确命中“目标端口已占用”、且端口随后真实释放的情况做 0-3 次有界重试；其他启动失败仍立即暴露。
- 每个托管服务新启动前清空自己的本轮日志；重建 Java JAR 前停止本脚本管理的 Java 进程。
- Elasticsearch 缺宿主端口时按 Compose 配置重建容器，保留数据卷。
- Worker 初次连接 RabbitMQ 增加有界退避式持续等待；API 发布仍 fail-fast 并落 PENDING_RECOVERY。

### 当时验证与当前回归

启动脚本单测和多轮全栈启动通过；最终 Agent health 的 MySQL、Redis、RabbitMQ、Worker、Gateway、MCP 和 ES vector mapping 均为 ready。商城 `6001`、Admin `6002`、Gateway `8081`、Agent `7050` 和 Worker metrics `7051` 可访问。

### 残余边界

这是本地进程编排脚本，不是 Kubernetes readiness/liveness 或滚动发布方案。有界重试只处理已识别的 bind 竞态，不能掩盖配置错误和未知进程占端口。

### 60 秒面试复述

> 我没有简单把所有启动失败都重试，而是要求日志明确是目标端口冲突，并确认端口已经释放，才做最多三次有界重试。同时每轮清日志，避免旧失败污染新判断；重建 JAR 前先停受管 JVM，避免 Spring Boot 后续懒加载读到被替换的压缩包。最终完整栈健康检查通过，但这只定位为本地编排能力。

## 20. 前端乱序、刷新缓存竞态与 Transition 多根节点

### 当时验证与当前回归

15 秒是异步可见状态的最大断言窗口，不是性能 SLO。默认 Playwright 跳过的两条是显式 live-ai 测试，真实完整栈已单独执行 1 条并通过。

### 60 秒面试复述

## 21. 审计 SQL collation 与 RabbitMQ 集成测试端口

### 时间与 commit

- 发现与修复：2026-08-06 12:26 至 12:52。

### 业务现象

推荐完整漏斗已经成功，但最初跨库审计 JOIN 报 `Illegal mix of collations`。随后 Java 全量测试显示 RabbitMQ 集成测试被环境开关跳过；开启后又在 `127.0.0.1:15673` AMQP 握手超时。最后检查新环境安装时还发现 Agent 实际使用 Python 3.13.5，而 `pyproject.toml` 的 `<3.13` 声明会拒绝该解释器。

### 错误假设

审计查询失败不等于业务链路失败，因为业务通过 HTTP，不做跨库 JOIN。另一个错误假设是 RabbitMQ “端口能连”就说明协议正确：`15673` 是管理端 HTTP，项目 AMQP 端口是 `5673`。包元数据也不能只看当前 venv 能否 import，必须用目标解释器执行 editable install。

### 证据链与根因

`aishop_agent` 与业务库使用不同 utf8mb4 collation，直接比较字符串触发 MySQL 1267。Rabbit 测试源码则硬编码 `15673`，只有设置 `RUN_RABBIT_INTEGRATION=1` 才会执行，因此错误长期被 skip 隐藏。Python 3.13.5 与 `<3.13` 的 packaging metadata 也确实不一致。

### 修复与取舍

- 审计 SQL 对 requestId/orderId 等稳定标识使用 `BINARY` 比较，不修改业务库 collation，也不把跨库 JOIN 引入运行链路。
- Rabbit 集成测试读取 `RABBIT_HOST/RABBIT_PORT/RABBIT_USER/RABBIT_PASSWORD`，默认对齐 Compose 的 `127.0.0.1:5673` 和 `aishop/aishop`。
- `pyproject.toml` 放宽为 `>=3.11,<3.14`，与已实测 Python 3.13.5 对齐；安装契约由 `pip install -e . --no-deps` 验证。

### 当时验证与当前回归

最终 SQL 成功查出曝光、点击、订单项和支付记录。Rabbit 测试首次真实运行复现 timeout，改端口后 `1 passed`；随后开启该开关完整 Reactor 为 `133 passed, 0 skipped`，临时 exchange/queue 在 finally 中清理。Python 3.13.5 editable install 成功；当前 Agent 回归 `490 passed, 3 skipped`，三个 skip 由真实 MySQL gate 单独覆盖。

### 残余边界

`BINARY` 适合稳定标识审计，不应拿来替代面向用户文本的排序/比较。Rabbit 集成测试证明本机 broker round-trip 和转换协议，不是消息系统吞吐或集群容灾验证；Python 版本范围也不是所有 3.13 平台依赖都兼容的承诺。

### 60 秒面试复述

> 完整漏斗成功后，审计 SQL 反而因跨库 collation 不同失败。我区分了业务链路和审计链路，只对稳定 ID 用 BINARY 比较。又发现 Java 的 Rabbit 集成测试一直被 skip，开启后才暴露把管理端 15673 当 AMQP 的硬编码；同轮 packaging 检查还暴露 Python 3.13 与 `<3.13` 声明冲突。改为环境变量、默认 5673 并放宽到 `<3.14` 后，完整 Reactor 133 条无跳过、editable install 成功。这是验证工具和发布元数据也需要测试的例子。

### 时间与 commit

这是单机 Docker、确定性负载的隔离演练，没有覆盖网络分区、MySQL 主从切换、RabbitMQ 集群、长时间压力或第三方 LLM 故障，不能外推生产可靠性或 exactly-once。

### 60 秒面试复述

> 我没有只展示状态机单测，而是做了独立 Compose 故障演练。真实 kill Worker 验证租约接管，停 Rabbit 验证 PENDING_RECOVERY，重复投递验证 fencing，停 checkpoint Redis 验证不能误报成功。每个场景都查 attempt、effect、SQL 和队列，最终 6 条业务断言通过并清理隔离资源。但我只把它表述为本地故障证据，不等同于生产容灾。

### 业务现象

用户输入“没发货的耳机我要退款”时，系统已经把意图判为 `REFUND`，却没有主动查询本人订单并解析“没发货 + 耳机”，最终显示“未能生成有效确认卡片。请确认订单号/订单项、评价星级与内容后重试”。用户只有再次输入 `SM202608050002号订单我要退款`，才得到 `SMITEM202608050002` 的退款确认卡。

这不是单纯的文案不友好。用户已经提供足够的业务约束，系统却把订单定位责任推回用户；更严重的是，退款、确认收货、评价等写操作如果只靠模型拼 ID，还可能出现错单风险。

### 整改前证据链

1. `aishop_agent.agent_message` 消息 `30`：`user_message=没发货的耳机我要退款`、`intent=REFUND`、终态文本为无效确认卡提示。
2. 消息 `31`：补充订单号后得到 `ACTION_CONFIRM`，其中 `orderId=SM202608050002`、`orderItemId=SMITEM202608050002`、金额 `3999.0` 元。
3. 演示订单事实：该订单属于用户 `9000000001`，`order_status=1`，订单项名称为“索尼 WH-1000XM6 无线降噪耳机”，`order_item_status=1`。因此“没发货的耳机”在当时数据中可以唯一定位。
4. 整改前采样的 Worker 轨迹显示意图已经是 `REFUND`，失败发生在订单目标和写工具参数补齐阶段，而不是意图完全没识别。

### 错误假设与根因

旧实现叠加了六个错误假设：

1. 提示词曾规定写意图不要主动查订单，默认用户或模型会直接提供完整订单 ID。
2. 写工具强制兜底只能从原文取 ID；自然语言商品、状态和时间线索没有确定性订单解析层。
3. 演示 ID `SM.../SMITEM...` 不在原订单号解析契约内，规则和真实种子数据不一致。
4. 终态选择把“尝试过失败的 `PROPOSE_*`”放在有效订单候选之前，容易用技术失败文案覆盖可继续澄清的结果。
5. 商品页上下文曾无条件优先于用户新说出的品牌，从索尼页说“退苹果耳机”仍可能锁到索尼；taxonomy 只匹配大类也无法区分同类品牌和规格。
6. 多轮评价只识别阿拉伯数字星级；“五星，音质很好”会依赖情感词偶然推成 5 星，正文还可能残留“五星”。

### 修复与取舍

- 在意图完成后、LLM/ReAct 和写工具之前新增确定性的 `OrderReferenceResolver`。默认查本人最近 90 天最多 30 单；显式订单号跳过时间窗，但仍用 `userId + orderId` 验证归属。
- 固定按归属、显式 ID、业务资格、状态词、时间词、商品线索解析。只有最终唯一候选或“最近/上次”等明确时间关系才能自动确定；同订单多订单项或多笔同类订单均返回最多 5 项 `ORDER_SELECTION`。
- 商品线索复用搜索 taxonomy，并补商品名、品牌、型号和规格的确定性包含匹配。明确品牌/型号优先于旧商品页；只有“这个/这款”等指代或没有商品线索时才使用商品页 `productId`。
- 退款、确认收货、评价和追评只调用 `PROPOSE_*` 生成确认卡；确认前绝不执行副作用。取消、地址、发票、催发货和破损错漏发没有真实写工具时，只定位订单、解释当前状态并引导订单页或人工。
- 新增持久化 `ORDER_SELECTION`、`POST /agent/selectOrderCandidate` 和 Web 候选卡。选择目标作为结构化 `selectedOrderReference` 随任务传递，不再依赖重新拼一句自然语言碰运气。
- 候选选择使用 `SELECT ... FOR UPDATE`，在一个 MySQL 事务内创建 `agent_message`、`agent_task` 并更新 `CONSUMED`；MQ 发布在提交后执行，失败由现有 `DISPATCHING/PENDING_RECOVERY` 扫描恢复。同目标重复点击返回原消息，改选其他目标冲突。旧版遗留 `PROCESSING` 只有超过 120 秒才允许恢复。
- 选择卡 TTL 只授权点击；消费成功后，结构化目标有效期改为任务 deadline，避免临近过期点击后排队导致目标丢失。Worker 执行时仍重新查询最新订单状态，状态变化时拒绝生成写提案。
- 增加 `QUERY_REFUND_STATUS` 及 Java 内部归属校验接口；返回公开退款状态和金额，不暴露内部错误。
- 修正写工具终态优先级、MCP 结构化失败、中文一至五星解析和评价/追评短轮次延续。
- 增加低基数 `agent_order_reference_total{intent,outcome}`、解析时延和 `agent_order_selection_total{intent,outcome}`；label 不放用户、订单或商品文本。

### 本轮真实踩坑

1. MySQL migration 测试第一次若不显式传测试连接参数，会被开发 `.env` 的账号配置影响；最终命令显式传入 host/port/user/password 后，三个临时库用例全部通过。
2. 候选选择最初采用 `ACTIVE -> PROCESSING -> 普通 send_message -> CONSUMED`，进程若在中间退出会永久卡在 `PROCESSING`。最终改为单事务消息/任务/消费，并只保留有界的旧状态恢复。
3. 启动当前完整栈时，第一次 MCP 重启遇到旧监听端口尚未释放，日志为 `address already in use`；端口释放后再次运行幂等启动脚本，MCP、Agent、Worker 和全部 Java 服务恢复健康。这是开发启动竞态证据，不包装成生产事故。
4. 第一版候选 E2E 只验证卡片、幂等和冲突，点击到待付款订单后仍能技术通过。将真实订单状态纳入断言后，才暴露“收到的”只参与文本匹配、没有限定可收货状态，以及破损意图资格过宽两个根因；修复后候选首项和最终目标均为状态 `3` 订单。
5. 两条 live 用例首次一起复跑时并发复用同一演示用户，候选请求被真实发送频控以 `code=600` 拒绝。live 测试组改为串行后两条均通过；这是共享状态测试隔离问题，不是通过调大频控阈值掩盖。

### 残余边界

- 订单解析是确定性规则和仓库现有 taxonomy，不是训练出的实体链接模型；新品牌、新语言和复杂组合表达仍要靠 badcase 运营扩充。
- 地址、发票、催发货、破损错发漏发目前没有真实办理或工单写工具，系统只能定位订单并引导订单页/人工。
- 候选卡事务保证本地 MySQL 事实一致和 MQ 可恢复，不等于网络分区下 exactly-once。
- 冻结 runner 的多轮是确定性 fixture，不代表线上生成质量；本轮只对精确退款和候选选择两条场景做了真实完整栈 E2E。
- 没有真实客服成功率、退款转化率、线上流量或生产 SLO，不能把 `134/134` 表述为线上准确率 100%。
