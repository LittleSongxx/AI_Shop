结论:本项目选型与 2026 年业界共识高度一致。两个最容易被面试官挑战的选择——用 RabbitMQ 而非 RocketMQ、用 Elasticsearch 兼任向量库而非专用向量库——在项目当前规模下反而是更理性的决策,但需要准备好在「生产口径」下的完整解释(见第三节)。

两个核心问题,先给答案

消息队列:RabbitMQ,合理三选一对照:电商核心交易链路业界倾向 RocketMQ(原生事务消息/延迟消息/顺序消息);Kafka 属于日志与埋点管线;RabbitMQ 定位中小规模灵活路由。本项目是演示规模、Java×Python 双栈,且已用「本地消息表 + 补偿 + 死信」补齐可靠消息短板——这是 RabbitMQ 生产实践的标准组合,当前选择成立;若核心交易流量起来,RocketMQ 是平滑演进方向。

向量库:都不是,ES 兼任更优四选一对照:pgvector 因项目主库是 MySQL 而直接出局(为向量单养一个 PG 实例不划算);Qdrant/Milvus 的价值在 50 万~亿级向量,对千级规模是过度设计;ES 9.2.1 本来就要承担商品搜索,复用同一集群做 1024 维 RAG 检索 + 视觉检索,是「已有 ES 基础设施时优先 ES」业界建议的教科书式落地。

二、逐项评估

重点展开两个核心问题(消息队列、向量检索)的完整对比;其余选型给出判定依据与注意点。

2.1 消息队列:RabbitMQ 合理

项目现状:RabbitMQ 3.13 单实例(端口偏移 5673);manual ack + prefetch=1;7 类交换机(秒杀/支付/退款/RAG/浏览/通知/成长值);延迟队列 + 死信队列;可靠性靠本地消息表 local_message_outbox + mq_compensation_log 补偿重放;Python 侧经 aio-pika 消费视觉索引任务。

三选一的事实基础,2026 年公开资料的共识口径:

维度RabbitMQ 3.13RocketMQ 5.xKafka
核心定位 灵活路由的消息代理 金融级交易消息中间件(阿里双 11 验证,峰值 17.6 万 TPS) 高吞吐流式数据平台(日志/埋点)
吞吐量级 万级 TPS 十万级 TPS 百万级 TPS
事务消息 无原生支持,靠 outbox 模式补齐 原生(半消息 + 事务回查) 仅消息发送原子性,不解决跨系统事务
延迟消息 TTL+DLX 或插件(有队头阻塞/Mnesia 丢失风险) 原生(4.9+ 任意时间延迟) 无
顺序消息 单队列内有序 原生强顺序(库存扣减刚需) 分区内有序
Python 生态 aio-pika 成熟 弱(主要为 Java/C++) 中等(confluent-kafka)
运维负担 低(单节点可跑,本项目 mem 768M) 中(NameServer+Broker,内存占用高) 高(集群调优,KRaft 演进中)

判定依据:①演示规模下吞吐差异无意义,选型的真实约束是「16G 宿主机内存预算 + 双栈语言生态」——RabbitMQ 是唯一能 768M 内存单机跑、且 Java/Python 生态都成熟的选择;②可靠性短板已用 outbox + 补偿 + 死信兜住,这正是 RabbitMQ 生产实践的标准答案;③本项目并无「下单后必须毫秒级扣库存」的强实时链路,事务消息的价值没有用武之地。

两个注意点(面试高频追问):
  • 「为什么不用 RocketMQ?」标准答法:本项目用 outbox 换掉了对事务消息的依赖,当前规模不需要 RocketMQ 的事务/延迟/顺序能力;若核心交易链路流量上来,RocketMQ 接手交易域、RabbitMQ 退守 RAG/通知等旁路,是平滑演进而非推倒重来。
  • 延迟队列实现需自查:若用的是 delayed_message_exchange 插件,存在 Mnesia 暂存丢失与长延迟漂移风险;若用 TTL+DLX,存在队头阻塞(长延迟消息卡住后续短延迟消息)。订单超时取消类场景,生产口径应补「定时扫描对账」兜底。

2.2 向量检索:Elasticsearch 兼任 合理

项目现状:ES 9.2.1(含 IK 中文分词插件)单节点一石三鸟——①商品全文搜索;②RAG 向量检索(索引 aishop_vectorstore,embedding 1024 维,Spring AI 自动管理 schema);③视觉商品检索(alias aishop_visual_products)。混合检索 = BM25 + 向量 + RRF/rerank,同栈完成。
维度pgvectorQdrantMilvusElasticsearch 9.x
架构 PostgreSQL 扩展 Rust 单二进制 多组件分布式(etcd/对象存储/Pulsar) 分布式搜索引擎 + 向量字段
规模甜区 < 1000 万(已用 PG 时零成本) 50 万 ~ 5000 万(生产 RAG 默认之选) 千万 ~ 亿级 全谱,取决于集群规划
延迟 1M 向量下 p50 ≈ 8.5ms p50 ≈ 1.8~4ms(最低) p50 ≈ 2.5~6ms 与 Qdrant 同量级;纯向量高并发下弱于专用库
混合检索 需拼 PG FTS,组合最弱 原生(Query API + BM25) 原生(sparse vector) 最强:BM25+向量+RRF 单查询融合,9.2 起 ES|QL 支持
运维负担 复用 PG 运维 低(单二进制) 高(≥3 节点起步) 已有集群则零新增
对本项目适配 ✗ 主库是 MySQL,需单养 PG △ 需新增一个存储组件 △ 过度设计 ✓ ES 本来就在做商品搜索

判定依据:四个选项里,ES 兼任是当前定位下的最优解。pgvector 出局的原因不是性能而是「主库是 MySQL」——为向量检索单独引入 PostgreSQL 实例违背零新增基础设施原则;Qdrant/Milvus 的价值门槛在 50 万~亿级向量,项目千级商品/文档规模下无差别;而 ES 9.x 的 BBQ 量化(向量内存压缩最高 32 倍)、ACORN 过滤剪枝、ES|QL 混合检索,让「搜索 + 向量 + 融合」在一条查询内完成,正好覆盖本项目的 BM25+向量+RRF 混合检索需求。

容量与演进提醒:单节点 1G 内存同时扛全文 + 1024 维向量 + 视觉向量三负载,是演示级配置——生产口径需 3 节点集群并按负载分索引规划。若未来向量检索成为独立主负载(百万级以上),演进方向是 Qdrant(低延迟 + 原生过滤 + 单二进制易运维);Milvus 仅在亿级才值得承担其运维复杂度。另注意:qwen3-vl-embedding(1024 维)与 text-embedding-v4(1024 维)维度相同但语义空间不同,务必分索引存储,不可混用。

2.3 分布式事务:Seata AT + 本地消息表并存 基本合理

项目现状:Seata 2.2.0 AT 模式(@GlobalTransactional,自建镜像,注册到 Nacos)+ 本地消息表 outbox + 补偿日志,两套机制并存。

为什么「基本合理」而非满分:对求职项目,同时展示「准强一致(AT)」与「最终一致(可靠消息)」两种主流范式是加分的广度展示,Seata 2.2 + Nacos + SB 3.5 也是新一代搭配;但对演示规模,outbox 一套其实已足够,Seata 属于「展示型组件」——需要在复盘/文档中写清两者的边界,否则评审时会显得堆砌。

边界写法(生产口径 + 面试考点):
  • AT 用于「短事务、多服务写同一流程、不容许中间态」:下单扣库存类;但高并发抢同一行数据时 AT 全局锁会使 QPS 下降约 15~20%,秒杀场景必须前置 Redis 预扣减。
  • 资金类链路禁用 AT,业界共识是 TCC 或对账补偿。
  • outbox 用于「允许短暂不一致的旁路」:积分、优惠券、通知、RAG 索引刷新等,消费者幂等 + 死信兜底。
  • 两者并存时的口径:AT 管「跨服务写的一致性」,outbox 管「本地事务与消息的原子性」,不是重复建设。

2.4 Java 17 + Spring Boot 3.5.4 合理

项目现状:Java 17;SB 3.5.4 + Spring Cloud 2025.0.0 + SCA 2025.0.0.0 + Spring AI 1.1.2;MyBatis 3.0.5 + Flyway + Testcontainers。

版本组合是「最新一代且互相配套」,方向完全正确:Spring Boot 2.x 已停止安全维护(商业支持 2024-11 终止),新项目选 3.5.x 是唯一解;SCA 2025 系适配 SB 3.x,无版本错配。JDK 17 满足 3.x 最低要求,2026 新项目首选 21(虚拟线程、GC 收益),但演示项目 17 完全可接受——「JDK 21 + 虚拟线程提升订单处理吞吐」可作为面试演进储备答案。ES 9.2.1 + Spring AI 1.1.2 属于激进组合(近期 git log 里有 ES 9 mget 兼容补丁),踩坑成本存在但已被记录与修复,可控。

2.5 服务治理:Nacos + Sentinel + Gateway 合理

项目现状:Nacos 2.4.3(standalone + MySQL 存储,仅用 discovery);Sentinel dashboard 1.8.8;网关显式路由表 + 双层限流(default-qps 200 / auth-qps 30 / agent-send-qps 10)+ 429 fallback + Feign 熔断。

这套组合是 2026 年国内微服务的事实标准:Eureka/Hystrix/Ribbon/Zuul 均已退役,Spring Cloud Alibaba 的 Nacos(注册+配置)+ Sentinel(限流熔断)+ SCG(网关)是替代它们的默认答案。两个小注:①Nacos 单机演示合理,生产需 3 节点集群;②Sentinel dashboard 1.8.8(第三方 bladex 镜像)版本偏旧——dashboard 只是可视化面板,实际 client 由 SCA 2025 引入,功能无碍,面试被问可如此解释。网关的「QPS 分级限流 + 熔断降级 + 内部 Token 鉴权」是真实工程亮点,不是摆设。

2.6 LLM / Embedding 全家桶 合理

项目现状:主 LLM DeepSeek(deepseek-chat);Embedding 阿里百炼 text-embedding-v4(1024 维);Rerank 百炼 qwen3-rerank(未配 Key 时回退 RRF);VLM qwen-vl-plus(知识文档图片,默认关);视觉搜索 qwen3-vl-plus(grounding)+ qwen3-vl-embedding-1024-v1 + qwen3-vl-rerank。

全 API 化、零 GPU 运维,对个人/演示项目是成本最优解;且所选模型都在中文第一梯队:qwen3-rerank 是中文 rerank 上限之一,text-embedding-v4 是中文 API embedding 主流,视觉三件套形成完整多模态链路。项目里「rerank 缺失回退 RRF」「VLM 默认关」的降级链设计是加分项。

注意点:①fallback LLM 与主 LLM 同为 deepseek-chat,是「伪降级」——若面试讲高可用,可补一个真正的异构 fallback(如通义 API);②API embedding 模型不可控,供应商改版/下线会破坏向量空间——项目已有 eval runner(aishop-eval/v1)做检索回归,这是正确姿势,但需写明「换 embedding 必须全量重建索引」;③「私有化/降本」叙事可用自托管 BGE-M3(电商场景下混合召回 + bge-reranker-v2-m3 是开源主流组合);④多供应商耦合偏阿里生态(百炼 Workspace),属可控风险。

2.7 Agent 编排:LangGraph + MCP 合理

项目现状:FastAPI + LangGraph 0.2.76;监督者 + 至多 2 个受限专家(shopping_advisor / order_fulfillment_specialist / after_sales_policy_specialist,管理端另有 data_analyst + inventory_ops);确定性流程走 Workflow、开放决策才进专家;写操作 Propose→用户确认→Java 执行;含 guardrails、双窗口限流、双层记忆(Redis+MySQL)、episode 轨迹、独立 Worker(租约制)。

这套设计与 2026 生产共识完全对齐:LangGraph 已 1.0,是多智能体编排的事实标准(Uber/JPMorgan 等在生产使用),其 checkpoint、HITL、显式状态机正是本项目 harness 所依托的能力;MCP 双向(对外暴露 Streamable HTTP server、对内消费工具)踩在 2026 生态热点上;「监督者 + 受限专家 + 单智能体回退」的降级链、写操作确认制、轨迹持久化,都是教科书级的多智能体治理实践。小注:langgraph 0.2.76 是 2025 年的版本线,1.x 的 durable execution 更成熟,可评估升级(属「顺手升级」,非架构改动)。

2.8 存储层:MySQL / Redis / 本地磁盘 合理

项目现状:MySQL 8.3 单实例、一域一库共 10 库(无分表、无读写分离);Redis 7(Redisson 4.0.0):Lua 原子秒杀、分布式锁、Bitmap 签到、MQ 幂等键、Agent 短期记忆/语义缓存、限流计数;文件存储为本地磁盘(/data/aishop/upload),无 OSS/MinIO。

域拆库清晰、Redis 用途全部正统(没有滥用),演示定位下合理。唯一需要主动准备解释的是本地磁盘文件存储:生产口径下图片/文件必须外迁 OSS + CDN(面试必问),迁移叙事现成——直传 OSS、回源 CDN、挂接内容审核(项目已预留百度图片审核),架构上只需替换存储适配层。

2.9 可观测性与前端 合理

项目现状:Prometheus v2.54.1 + Grafana 11.2.0 + Tempo 2.6.1 + OTel Collector(0.113.0);Java 侧 actuator + Micrometer,Python 侧 OTel 插桩 fastapi/httpx/redis/sqlalchemy;前端 Vue 3.5 + Element Plus(用户端与管理端)。

可观测栈是 2026 标准组合,且做到了 Java×Python 双栈指标/链路打通(Agent worker 独立指标端口),这对一个双语言异构项目是超出多数同类作品的完成度。前端选型是国内电商/中后台默认答案,无争议。
