# 决策文档：身份字段层次与委托信道

本文只记录已经由源码、测试或运行日志支持的事实，不把本地演示数据包装成生产结论。

## 问题：模型可见的字段不能是权威身份

Agent 调用 Java 订单服务时，`userId` 出现在请求 body 里——这个 body 是**模型可见信道**：它由 LLM 的 tool-call 参数生成，模型可以改写、编造、或从注入话术里捡到别人的 ID。把业务归属校验建立在模型可见字段上，等于让身份判定和受检内容共用同一条信道，任何 Prompt 注入都直接变成越权通道。

同类问题还出现在管理端：浏览器前端字段（如 adminId）也可能被篡改，必须以认证会话为准。

## 方案：身份分层，系统信道是权威

### 1. 两个信道，两个职责

| 信道 | 载体 | 谁填充 | 谁可见 | 用途 |
|---|---|---|---|---|
| 系统信道 | 请求头 `X-Agent-User-Id` | 网关 / Agent 运行时（模型不可触碰的传输层） | 模型不可见、不可改 | **权威委托身份** |
| 模型信道 | body 内 `userId` | LLM 工具调用 | 模型可见 | 业务参数，仅供参考 |

### 2. fail-closed 校验，而不是"可信时启用"

Java 侧在每次涉及用户数据的内部接口上：

- **缺失委托头 → 401**：fail-closed，不降级回退到旧信任模型（没有头 = 不再按老逻辑放行）。
- **body userId 与委托头不一致 → 403**：模型想用别人的身份做事，直接拒绝。
- **归属校验**：取到的订单/退款请求必须属于委托用户，否则 403——即使模型头身一致，也只能访问自己名下的数据。

拒绝的语义是"拒绝这笔请求"，不是"记录后放行"：注入者得不到任何可观察到的成功信号。

### 3. 与内部 token 的关系

跨服务调用仍以内部 token 证明"这是系统内部调用"（身份来源可信）；`X-Agent-User-Id` 在内部 token 之上再声明"这笔调用为哪个用户代办"。两层缺一不可：token 证明调用者，委托头证明被代办者。

## 取舍与未采用方案

- **不在 body 里加签名/时间戳防篡改**：body 本来就是模型生成的，对它做完整性校验没有意义——模型信道的内容天然可被模型改变，解决方式不是加固 body，而是让权威身份根本不经过 body。
- **不在网关层对所有路由统一强制**：不同接口的信任需求不同（管理端走会话，Agent 内部走委托头），在服务内按接口粒度校验，避免一刀切破坏既有调用方。
- **不引入 OAuth/JWT 用户令牌链**：委托场景只需要"谁代办"的轻量断言，令牌体系属于另一层职责，会在接口间引入不必要的密钥分发成本。

## 测试与验证

`OrderAgentInternalControllerTest`：委托头与 body 一致返回数据；body 换成他人身份 → 403；委托头缺失 → 401（fail-closed）；查询不属于委托用户的订单/退款 → 403；退款状态字段不泄漏 `lastError` 等内部字段。Agent 侧对写命令的同一套思路（`order_request_idempotency` 归属校验）由既有契约测试覆盖。

## 60 秒面试复述

Agent 生成的 body 是模型可见信道，把 userId 的归属校验建立在 body 上等于把身份判定和受检内容放在同一条信道上，注入话术可以同时伪造两者。我的做法是身份分层：网关在传输层填充 `X-Agent-User-Id` 系统信道头，模型不可见不可改；Java 侧 fail-closed 校验——头缺失 401、body 与头不一致 403、数据归属不符 403，拒绝后不给任何成功信号。跨服务内部 token 证明"调用者是系统"，委托头证明"为谁代办"，两层缺一不可。
