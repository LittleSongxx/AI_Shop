# 数据集合理性审计与重构建议（2026-08-25）

## 结论

**需要重构，但应做“数据治理与生命周期重构”，不应删除、覆写或把历史数据重标后冒充新结果。**

当前数据集可以支撑以下用途：可复现的开发诊断、已知缺陷回归、固定输出的答案审计、客服路由/风险/槽位输入 gold，以及小范围的定向修复验证。它不能单独支撑“未见数据泛化”“线上质量”或“生产 SLO”的主张，主要原因是 historical final 已暴露、主线样本与商品快照规模有限、不同评测目的的资产虽在实现上已有部分隔离但缺少一个统一的治理 registry。

截至 2026-08-26，v25 的 10 条 frozen-output answer review 已完成两人盲评：10/10 完全一致、0 分歧，因此不需要第三人仲裁。v27 又在同一部署指纹下完成了客服 v1 全部 60 条的新输出回放，并完成两份独立随机顺序、运行时 fixture 对齐的盲审表；案件级双评一致 `58/60`，2 条分歧已由第三人仲裁，最终答案正确 `59/60`、可计分引用支持 `35/36`、转人工适当 `60/60`、unsafe `0/60`、联合质量 `59/60`。源 report 的生成时字段仍为 `PENDING_HUMAN_REVIEW`，但外部人工 evidence 已为 `HUMAN_REVIEWED_ADJUDICATED`；结果只绑定这次冻结输出且 `releaseGateEligible=false`。这些进展不改变“需要治理重构”的结论，也不补足客服 v2 输入 gold 或外部 future final。

本审计不改变任何历史 evidence，也不重算或重命名已发布分数。v9 final、v2 旧 final、旧 RAG、行为契约和已封存人工评审均保留为不可变历史输入。

## 审计口径

检查了以下不可变或已锁定输入：

| 资产 | 记录数 | 当前用途 | 审计结论 |
|---|---:|---|---|
| development v3 | 43（Search 18 / RAG 18 / Agent 7） | 开发诊断 | 有效，但小样本、开发者可见 |
| regression v3 | 51（20 / 26 / 5） | 已知缺陷回归 | 有效，但不能替代未见 final |
| historical v9 final | 125（50 / 50 / 25） | 历史强回归与追溯 | 已失去 holdout 资格 |
| 本地 visible v2 final | 50（21 / 21 / 8） | 已消费历史输入 | 不应继续放在 future-final 语义下 |
| 客服 v1 | 60 | 路由、风险、槽位、转人工 input gold | HUMAN_VERIFIED，可复用但不能代表生产准确率 |

development 和 regression 分别受 `development.lock.json`、`regression.lock.json` 哈希锁定。客服 v1 的 SHA-256 为 `112dfd6ba7546b7cbad317597d944e3ab4dc02627d4ca6018733031d8eddc527`，客服 v2 additions 的 SHA-256 为 `7110835813e32f6ed3823bd22c2e1487f7e9c2c62bb31d4eac92fb61f9bf4353`。

输入重复检查采用 Unicode 归一化后的精确匹配，并额外以字符二元组 Jaccard >= 0.78 标记高度相似模板；它只能发现明显重叠，**不能证明语义独立性**。开发与回归之间没有精确匹配；v9 与 regression 有 3 对高相似模板，旧 v2 final 与 v9 有 2 对。客服 v1 与 v2 additions 在标准化和订单/数字掩码后的精确匹配均为 0，也没有达到 0.80 的高相似模板；这说明 candidate v2 不是机械复制，但不能替代人工语义去重。

## 已确认的合理部分

### 可复现工程回归

1. development、regression 使用一致的 v3 schema、数据锁和 provider/fixture 声明，职责清楚：前者用于开发调试，后者用于防止已修复缺口回归。
2. Search case 都具有显式 qrel，且当前主集标注为 `EXHAUSTIVE_CATALOG`，因此在固定 catalog snapshot 内的 Recall、MRR 和正确实现的 NDCG 可以复算。
3. 客服 v1 的 60 条 gold 已经过双人盲标和仲裁，manifest 明确禁止把它解释为生产准确率。这个边界是正确的。
4. 固定 HTTP 输出的人工答案标签、HTTP 行为契约、订单 fixture 与输入 gold 已经有不同 artifact/reuse policy。例如 60 条 frozen answer labels 只能审计同一 source-report 和 answer hash，不能作为新模型 gold；这防止了最危险的标签误用。
5. 客服 v2 additions 采用 20 个 intent 各 3 条的均衡构造，并显式标为 `DRAFT_NEEDS_HUMAN_REVIEW`，没有偷偷并入 v1 的 `HUMAN_VERIFIED` 分母。

## 主要缺口

### 1. historical v9 final 不再是未见数据

`final-v9-source-exposure-audit-20260825.json` 在排除本地 replay 副本后，仍发现 125 条中的 120 条可从当前开发者可见文本恢复，共 220 个定位、21 个来源文件；报告 SHA-256 为 `53d5992460c808f151ea51a4bc18af56b407b7f8c592819c8da70cb52bc6c6a2`。

此外，工作区保留了已消费的 raw historical final：`evaluation/.holdouts/` 有 v3-v9 原始 JSONL，`evaluation/.runs/final-20260822-ai-quality-v9/` 有完整 cases/trials，`evaluation/datasets/final-inputs/` 还有一个被 `.gitignore` 忽略但开发者可读的 50 条 v2 final。保留历史证据本身没有问题，但它们说明这些数据只能是 `CONSUMED_HISTORICAL`，不能被重新叫作 final 或 holdout。

`consumed-final.json` 已记录消费历史，这是正确的第一道保护；未来仍必须由仓库外保管人生成、冻结和交付新的 final。词法 source-exposure scan 只能发现可恢复文本，不能证明语义未见，因此不能替代外部保管和一次性消费。

### 2. Search/RAG/Agent 的有效样本量和分层不足

主线的最小 domain 分母很小：Agent development 只有 7 条、regression 只有 5 条；Search regression 20 条；RAG regression 26 条。即使观察到全通过，Wilson 95% 下界也只有 `5/5 -> 56.55%`、`7/7 -> 64.57%`、`20/20 -> 83.89%`、`26/26 -> 87.13%`。这些数字适合门禁和诊断，不适合高精度泛化率。

Search 全部绑定同一 v2 catalog snapshot（47 个商品，canonical SHA `6b1e...f659d57de0cb`）。development、regression 与 v9 final 的 qrel 合并后只涉及 21 个商品，即 `21/47 = 44.68%`；大量单商品类目从未成为 relevant target。v9 Search 虽有 18 条显式约束、11 条多 relevant qrel、6 条 no-result，但这些覆盖仍都在同一个静态目录中，不能证明对新商品、不同属性完整度、库存变化或真实长尾搜索的能力。

RAG 的 slice tags 与真实期望发生冲突：historical v9 的 50/50 条都打了 `answerable` tag，但其中 21 条 `expected.noAnswer=true`，8 条是 pure injection。任何按 tag 聚合的“answerable 指标”都可能错误，必须改以可验证的 `expected.noAnswer`、`expected.attack.type` 和独立 slice 字段作为唯一派生来源。v9 只引用了 73 条 fact metadata 中的 25 个 distinct fact ID，事实空间覆盖也不完整。

Agent final 的 25 条中只有 1 条期望 HANDOFF，2 条 WRITE_CONFIRMED，3 条 FAILED；development/regression 更少。它足以防止固定状态机和幂等契约退化，但不足以代表多轮、跨工具、不同失败序列下的 agent 成功率。

### 3. 客服 gold 的质量可用，但覆盖结构不均衡

客服 v1 的 60 条覆盖 20 个 intent，但分布高度不均衡：`PAYMENT_ISSUE` 和 `DAMAGED_OR_WRONG_ITEM` 各 7 条，8 个 intent 只有 1 条，另有若干 intent 只有 2 条。v1 有高风险 10 条、应转人工 14 条、有槽位 34 条。单例 intent 不能支持可靠的 intent-level 质量结论，应在报告中显示分层分母和置信区间，而不是只展示总 Macro-F1 或总正确率。

candidate v2 的 intent 已均衡到各 3 条，并含高风险 9 条、应转人工 16 条、hard 35 条，但有槽位 case 只有 26 条，少于 v1 的 34 条。若实体/订单/金额解析仍是重点，应补足复杂槽位、跨句指代、多个订单和不完整订单号的配额；先完成双人标注与第三人仲裁，再讨论和 v1 合并。

### 4. 数据资产的“目的”仍缺统一 registry

当前目录已有 README 和 manifest，但以下资产都位于 `customer_service/adjudicated/` 附近，仍容易在汇总时混淆：

| 资产 | 数量 | 正确用途 | 绝不能作为 |
|---|---:|---|---|
| v1 input gold | 60 | intent/risk/slot/handoff 回归 | 新模型最终答案正确率 |
| frozen answer labels | 60 | 同一冻结 HTTP 输出的人工答案审计 | 新输出的 gold 或线上质量 |
| HTTP behavior contracts | v1 10 / v2 11 | 确定性安全行为回归 | 人工答案质量 |
| HTTP fixtures | 19 | 运行隔离 | 标签或数据分母 |
| v25 targeted observation/review | 10 | 已完成双评的已知修复定向审阅 | 60 条整体质量、未来输出或泛化 |

这不是数据内容错误，而是治理结构还不够强：汇总器应从 registry 的 `purpose`、`lifecycle`、`denominatorPolicy` 决定是否计入任何指标，不能只按路径或文件名猜测。

## 重构原则

1. **保留，不改写。** 已消费 final、历史 badcase、旧输出审查和 immutable evidence 永远不删除、不原位重算、不回填成新 gold。
2. **按目标分层。** input understanding gold、retrieval qrel、frozen-output answer review、behavior contract、capacity/load scenario、candidate draft 和 future final 必须有互斥 `purpose`。
3. **final 在仓库外。** future final 不存入 Git、工作树、可搜索文档、测试、fixture、prompt 或历史 replay；交付后只保存 hash、签名、统计与 sealed evidence。使用一次后标记 consumed。
4. **由 schema 派生切片。** `answerable/noAnswer/attack/risk/handoff/constraint` 等关键切片从单一结构化 truth 产生，禁止平行的、可冲突的自由 tags 进入门禁分母。
5. **先分层，再汇总。** 每个总分必须列出每个 slice 的分子、分母、缺失覆盖和 Wilson 区间；不允许用大量低风险或 no-result case 掩盖高风险薄弱切片。
6. **人工质量独立。** 自动 verifier、引用结构、行为契约和模型 judge 均不能替代双人盲审、分歧仲裁和答案/引用语义审查。

## 建议的 v10+ 治理模型

不需要立即搬动所有历史文件。先新建一个版本化 dataset registry，并把既有资产登记为不可变 records：

```text
DEVELOPMENT_DIAGNOSTIC      开发可见；允许调试；不可做泛化结论
LOCKED_REGRESSION           开发可见；已知缺陷门禁；不可做 holdout
HUMAN_VERIFIED_INPUT_GOLD   双评+仲裁；仅评输入理解/路由
FROZEN_OUTPUT_REVIEW        绑定 report/answer hash；仅评完全相同输出
BEHAVIOR_CONTRACT           确定性安全/状态机断言；独立分母
PERFORMANCE_SCENARIO        到达模型和环境绑定；不等同质量
CANDIDATE_DRAFT             未完成双评；禁止 release gate
CONSUMED_HISTORICAL_FINAL   历史追溯/强回归；禁止再次称未见 final
EXTERNAL_FUTURE_FINAL       仓库外保管；claim 前零暴露；一次性消费
```

每个 registry record 至少包含 `datasetId`、`version`、`purpose`、`lifecycle`、`caseCount`、`sha256`、`owner`、`visibility`、`generationSource`、`allowedMetrics`、`forbiddenClaims`、`stratification`、`overlapAudit`、`sourceExposureAudit`、`parentEvidence` 和 `consumptionPolicy`。汇总和 release gate 只能读 registry 声明，而不能扫描目录自动拼分母。

## 执行优先级

### P0：现在冻结并完成当前人工审阅

1. 把 v9 和 visible v2 final 在 registry 中登记为 `CONSUMED_HISTORICAL_FINAL`；保留文件和 hash，但从“current final”以及任何泛化报告中移除。
2. **完成双评、只对分歧仲裁：** v25 两份 10 条答案盲审已封存，案件级完全一致 10/10、分歧 0，因此没有第三位评审数据；结果已作为 `TARGETED_REGRESSION_OBSERVATION` 登记，并排除普通质量分母。v27 的完整 60 条新输出已执行，双评案件级一致 58/60，2 条分歧由第三人仲裁，最终答案正确 59/60、可计分引用支持 35/36、转人工适当 60/60、unsafe 0/60、联合质量 59/60；最终 evidence 已封存且仍标记 `releaseGateEligible=false`，不能迁移到其他输出。
3. 导出客服 v2 candidate 的两份 input-label 盲审表，完成双评和仲裁后生成一个新的 `HUMAN_VERIFIED_INPUT_GOLD` package；在完成前继续禁止进入主分母。

### P1：新数据而不是把旧数据重新命名

1. 从仓库外创建新的 Search/RAG/Agent final。构造者与开发者隔离，题目和 qrel 不写入测试、docs、prompt、fixture 或 replay；claim 前运行 zero-exposure audit，并保留语义去重审计。
2. Search 至少覆盖多个 catalog snapshot、未被当前 21 个 qrel product 覆盖的商品/类目、真实 no-result、属性缺失、库存变化、预算/排除/多意图及长尾口语；已知 badcase 只进入 regression。
3. RAG 以事实 catalog 和风险域做配额抽样，将 `answerability`、attack type、temporal state、citation requirement 等设为结构化且互斥/可组合字段，不再依赖自由 tags。
4. Agent 增加独立的多轮、跨工具、失败恢复、权限边界和确认写入序列；报告 READ_ONLY、PROPOSE_ONLY、WRITE_CONFIRMED、HANDOFF、FAILED 的分层结果。
5. 客服扩充时设置高风险、转人工、复杂槽位和 intent 的最低样本配额，并给出每个 slice 的独立分母。样本量应由要保证的最小 slice 精度决定，而不是只追求总 case 数。

### P2：把数据治理接入发布门禁

1. release scorecard 读取 registry，拒绝 `DRAFT`、`CONSUMED_HISTORICAL_FINAL`、`TARGETED_REGRESSION_OBSERVATION` 和 `PERFORMANCE_SCENARIO` 进入普通质量总分。
2. future-final claim 除 hash 未消费检查外，要求外部保管声明、开发期不可访问证明和零 source exposure；词法扫描通过不能单独放行。
3. 每次新增 candidate 都运行精确、标识符掩码和人工抽样的语义去重；相似样本保留为变形测试或移入同一 cluster，不能跨 split 制造独立性假象。

## 本次不做的事

- 不删除 `evaluation/.holdouts`、`.runs`、历史 evidence 或 legacy 数据。
- 不修改 125 条 v9、60 条客服 v1 或现有 frozen-output labels 的内容/哈希。
- 不将 v25 10 条人工审阅结果外推为完整客服质量，或将同集回放称为新 holdout。
