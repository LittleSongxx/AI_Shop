## 一、项目现在真正做什么

Git 历史显示项目已从普通电商演示逐步收敛为两条受治理的 AI 主线，而不是通用聊天机器人或 Text2SQL 产品：

```text
用户问题
  ├─ AI 导购：文本/视觉约束 -> 商品检索/推荐 -> Java 权威价格与库存 -> 点击/加购/支付归因
  └─ AI 客服：意图/槽位 -> 发布版政策 RAG / Java 订单事实 -> 只读回答或写操作提案
                                                         -> 用户确认 -> 幂等执行/人工接管
```

关键边界是：LLM 负责受约束的检索编排、解释、澄清和提案；商品、订单、价格、库存、支付及最终写入状态由 Java 服务和持久化 Episode 掌握。Text2SQL 只是带权限和扫描预算的治理实验，不是第三条质量主线。

## 二、评测体系设计是否正确

### 总体判断

当前设计方向正确，且经过本轮修复后能够 fail-closed；成熟度可评为“强开发/回归评测体系，尚未达到发布级总体质量证明”。它适合定位回归、验证交易安全边界和管理证据生命周期，但当前数据与人工流程不足以让任何单一总分代表项目总体性能。

### 已设计正确的部分

| 层次 | 当前做法 | 判断 |
|---|---|---|
| 输入理解 | 独立评 intent、risk、slot、人工接管，并保留逐指标 badcase | 正确；比只报最终回答通过率更可诊断 |
| 生产路径 | HTTP -> Agent -> Worker/MCP -> Java/MySQL/RAG/Provider，并保存 Episode、tool、终态、state diff | 正确；能发现离线规则回放看不到的编排和依赖问题 |
| 写安全 | 提案与执行分离，检查确认、幂等、终态、零意外副作用 | 正确；这是电商 Agent 的核心质量面 |
| 行为契约 | fixtures 与确定性 contract 独立于答案语义评分 | 正确；安全不变量可要求 100%，但不冒充答案正确率 |
| 答案语义 | 双人盲审、封存、分歧仲裁、答案/来源/report 哈希绑定 | 方法正确；v43 尚未完成人工填写，所以保持 `null` 正确 |
| 统计 | 分子/分母、Wilson 区间、paired McNemar、分层 bootstrap、badcase | 正确；小样本不再只给好看的点估计 |
| 证据治理 | 不可覆盖 package、`SHA256SUMS`、数据锁、source fingerprint、source freeze | 正确；能区分“代码变了”与“模型变好了” |
| 未知值 | 未定价费用为 `null/UNPRICED`，HTTP 脱敏槽位为 `UNAVAILABLE` | 正确；没有把未知偷换成 0 或成功 |

### 本轮发现并已修复的评测缺陷

1. **执行成功口径错误**：旧口径把“评测器捕获到 observation”当作生产 episode 成功。现在分为 `observationCaptureRate` 与 `adapterStatus=PASSED` 的生产执行率，真实失败会进入 `errorCaseIds`。
2. **转人工口径污染**：旧口径会把 multi-agent 内部 specialist handoff 算成人工接管。现在只认生产 `nextAction=HANDOFF`、根级 HANDOFF 或显式 HUMAN 事件，指标定义为 `HUMAN_SUPPORT_ONLY_V2`。
3. **行级状态冒充数据有效性**：120 行虽写有 `HUMAN_VERIFIED`，但这只是行声明。HTTP 和离线报告现在必须继承独立 label/provenance audit；任一阻断存在时自动降为开发诊断。
4. **行为契约与答案质量混淆**：契约通过率现明确 `normalQualityDenominatorExcluded=true`；人工答案正确、引用语义支持和 unsafe 保持独立且不可由 verifier 自评填充。
5. **目标集合数量硬编码**：HTTP 报告不再把新增集固定写成 60 条，定向/120 条运行按实际集合说明限制。
6. **评测器假阳性**：免责声明中的“不能断言平台无货”不再被正则误判为“平台无货”断言；历史 observation 保留，修复只记作评测器修复。
7. **源码/进程漂移**：API、Worker、MCP 的 source fingerprint 与 preflight fail-closed，避免旧 MCP 进程让新代码测试产生伪结果。

### 仍未覆盖或不能由当前设计回答的问题

| 质量问题 | 当前是否能回答 | 原因/所需证据 |
|---|---|---|
| 已知客服场景的路由回归是否改善 | 能，开发诊断 | 同 120 条 paired 对比、逐 case 变化和统计检验已完成 |
| 当前代码能否走完整生产路径 | 能，本地隔离环境 | v43 保存 HTTP/Episode/tool/state diff；不等于线上可用性 |
| 关键写操作是否未绕过确认 | 能，覆盖到的契约内 | 22 条确定性契约；尚不是所有未来输入的形式证明 |
| 当前 120 条答案是否正确且有语义依据 | 不能 | v43 人工答案评审覆盖 `0/120` |
| 对新用户表达是否泛化 | 不能 | 当前 120 条已用于多轮诊断和实现优化，不再 unseen |
| 高风险/关键转人工是否稳定 | 只能弱证 | 当前高风险 `15`、关键接管 `11`，零 miss 的区间仍较宽 |
| 生产吞吐、可用性和 SLO | 不能 | 只有共享本机短时 read-only 观察，无独占 steady/stress/soak |
| 实际单请求成本 | 不能 | Provider 调用存在，但价格合同未绑定，费用保持未定价 |
| CSAT/FCR、CTR/CVR/GMV | 不能 | 没有真实用户曝光、解决、购买和随机对照数据 |

### v2 具体有效性问题

当前 120 条不是“假数据”，但其证据等级被旧文档高估：

- 两位 additions 评审的 sealed hash、60 条覆盖、26 条分歧仲裁及最终合并哈希都能复核，故结构上可用。
- 独立性声明缺失；reviewer-a 填写后的原始 OPEN bytes 不可得；A/B 的 export hash 字段语义均不正确。来源审计状态因此是 `HUMAN_VERIFIED_PROVENANCE_REVIEW_REQUIRED`，不是 release-grade human evidence。
- 两位评审与构造 draft 的 intent/handoff 高度对齐；这只是泄漏风险信号，不证明抄写，但必须由独立复审消除疑义。
- `RECOMMENT` 在旧标注说明中被解释为“重新推荐”，而生产代码一直把它映射为订单追评写提案。`112/113/114` 因此不是模型路由失败，而是 gold 与生产动作 taxonomy 冲突。
- amount 原始 span、budget 是否独立标注、次数是否 quantity、复合 productName/feature 的政策跨 case 不一致。严格 slot EM 在重仲裁前没有统一语义。

因此最准确的结论是：**当前 v2 对已知问题的开发诊断有效，对 release/final 质量结论无效；它能体现改动是否修好这些样本，不能体现项目对未来样本的总体性能。**

## 五、当前可以和不可以对外陈述什么

### 可以陈述

- 项目已有真实本地 full-stack 生产路径评测，而非只跑 prompt 或规则单测。
- 当前代码在暴露的 120 条客服开发集上实现生产 episode `120/120`，22 条预定义安全契约全部满足，未观察到意外写入或硬约束违规。
- 同集 paired 证据显示路由、人工接管和槽位抽取相对修复前显著改善；具体分子、分母、区间和回退 case 均可追溯。
- 历史 v27 的 60 条冻结回答已完成人工双评/仲裁，答案 `59/60`、可计分引用 `35/36`；它仍是历史暴露集人工基线，不是 v43 或 unseen 质量。
- 现有体系会在标签、来源、人审、价格或生产环境证据缺失时保持 false/null/unavailable，而不是自动晋升。

### 不可以陈述

- “v43 答案正确率 100%”“引用支持 100%”或“unsafe=0”：v43 尚无一条人工答案标签。
- “项目泛化率 97.5%/100%”：同一 120 条已被用于实现优化。
- “v2 是可靠独立人工 final”：来源独立性和标签一致性门禁均未通过。
- “生产 P95 为 6.16 秒”或“系统支持 2 QPS”：现有数据只来自共享本机短时只读观察。
- “线上客服成功率、CSAT/FCR、CTR/CVR/GMV 已提升”：没有真实用户或随机对照数据。
- “无风险/绝对安全”：零观测事件在小样本下仍有非零统计上界，且契约覆盖不等于开放世界证明。

### 发布级最低门槛

```text
标签一致性通过
  AND 来源独立性通过
  AND v43/后继输出双人答案评审完成
  AND 新 external unseen 一次性评测完成
  AND 关键安全契约无违例
  AND 生产容量/错误预算有独立证据
  -> 才可讨论 release-quality；仍不能自动推导业务收益
```

在这些门槛完成前，当前权威状态应保持：

- `qualityClaimStatus=DEVELOPMENT_DIAGNOSTIC_LABEL_AND_PROVENANCE_BLOCKED`
- `evidenceValidity.status=BLOCKED_HUMAN_READJUDICATION`
- `releaseGateEligible=false`
- `finalUnseenEligible=false`
- `answerQuality.status=PENDING_HUMAN_REVIEW`

这不是评测失败，而是正确地把“已经证实的工程能力”和“尚未取得的人类/线上证据”分开。
