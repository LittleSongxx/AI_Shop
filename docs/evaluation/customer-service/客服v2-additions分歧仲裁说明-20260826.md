# 客服 v2 additions 仲裁判定规则（2026-08-26）

> **历史文件，已被 v2.1 口径取代，不得用于新的标注或仲裁。** 本文曾把 `RECOMMENT` 解释为“重新推荐”，但生产动作一直将该枚举用于订单追评/追加评价写提案，形成 taxonomy 冲突。现有历史标签和本文保持原样用于追溯；新的 25 条重仲裁必须使用 `customer-service-taxonomy-contract-v2.1` 与[当前人工交接总清单](../人工标注交接总清单-20260826.md)。冲突与指标影响见[全面审计](../AI-Shop评测体系全面审计与执行结果-20260826.md)。

本文只说明分歧案件的判定标准。仲裁时以用户原话和冻结的客服 taxonomy 为准；两位评审的标签只能作为待解释的候选，不能把任一方标签、候选集中的预置标签、模型输出或历史 gold 当作答案。

## 一、统一判定顺序

每个案件按以下顺序判断，不能先看风险或转人工再倒推意图：

1. 先读完整原话，识别用户当前真正要完成的动作、要查询的状态或正在发生的问题；同时识别“不想……”“不是……”“只想……”等否定和范围限制。
2. 在冻结的 intent 中选择一个最具体、最能直接描述当前诉求的值。用户最后明确的可执行诉求优先于前面的背景叙述。
3. 独立判断 `riskLevel`。风险描述的是原话所涉及的后果，不是意图名称本身，也不是金额大小本身。
4. 再判断 `shouldHandoff` 和 `handoffSeverity`。转人工是处置决策，不用来替代已经能够确定的业务意图。
5. 最后只从用户原话提取与当前诉求有关的 `slots`，不补充后台或常识推断出的实体。
6. 在 `reason` 中引用决定性原话，说明最终选择及排除的近邻标签；不能只写“同意 A”或“同意 B”。

### 关键优先级

- 原话同时包含具体业务事件和“转人工/找真人”时，先保留具体业务事件的 intent，人工请求只影响 `shouldHandoff` 和严重度。例如“发票金额错了，帮我转人工更正”判为 `INVOICE`，“退款页面成功但未入账，请转人工核账”判为 `REFUND_STATUS`。
- 只有没有可归类的具体业务事件，或用户的主要诉求本身就是找真人（如“不要机器人，找真人处理”），才使用 `HUMAN_REQUEST`。
- 高风险事件仍保留其业务 intent：隐私泄露投诉归 `COMPLAINT`，危险商品归 `DAMAGED_OR_WRONG_ITEM`，支付扣款异常归 `PAYMENT_ISSUE`，退款账户或退款到账异常分别归 `REFUND`/`REFUND_STATUS`；不能因为出现“转人工”就全部改成 `HUMAN_REQUEST`。
- 被否定的动作不是当前意图。例如“不是取消，只改地址”判为 `ADDRESS_CHANGE`；“不是要退款，先查漏发”判为 `DAMAGED_OR_WRONG_ITEM`。

## 二、intent 判定

下表中的枚举和值均为冻结值，`RECOMMENT` 的拼写按 taxonomy 保留。

| intent | 判定标准 |
|---|---|
| `ADDRESS_CHANGE` | 修改收货地址、地址簿，或询问下单/发货后的地址能否变更。 |
| `AFTERSALES_UNKNOWN` | 已明确是售后问题，但原话不足以归入破损、错发、漏发、退款等更具体类别。 |
| `CANCEL_ORDER` | 请求取消订单，或询问取消条件、规则、流程；仅查询订单是否存在或状态不归此类。 |
| `CHAT` | 问候、感谢、闲聊或不涉及具体购物任务的对话。当前 taxonomy 没有独立“支付方式咨询”项时，一般支付方式闲问也归此类；出现支付失败、扣款异常则改判 `PAYMENT_ISSUE`。 |
| `COMPLAINT` | 主要诉求是投诉服务、客服处理、商品或履约体验，或投诉隐私泄露等高后果事件；若原话主要是在查询/处理一个具体业务事件，优先使用该事件 intent。 |
| `CONFIRM_RECEIPT` | 确认收货、签收状态或发起确认收货操作。 |
| `DAMAGED_OR_WRONG_ITEM` | 破损、质量异常、错发、颜色/型号不符、少件/漏发等收货异常；危险设备鼓包、发热等也保留该事件 intent。 |
| `HUMAN_REQUEST` | 用户只提出转人工、找真人、找安全专员等请求，且没有更具体的业务事件可作为主要诉求。 |
| `INVOICE` | 开票、发票抬头/税号、电子发票，或发票金额、内容更正。 |
| `PAYMENT_ISSUE` | 支付失败、重复扣款、已扣款但订单/支付状态异常、未授权支付等支付问题；退款到账问题归 `REFUND_STATUS`。 |
| `PRODUCT_CONSULT` | 询问商品参数、材质、功能、兼容性、适用场景、续航或两个明确商品的差异，不要求列出候选商品。 |
| `PRODUCT_REVIEW` | 发布评价、追评、评价入口、评价星级或评价内容规范。 |
| `PRODUCT_SEARCH` | 要求查找、筛选或购买商品，带有品类、型号、品牌、预算、属性或排除条件。 |
| `QUERY_COUPON` | 查询优惠券领取、使用、面值、门槛、有效期，或优惠券状态异常。 |
| `QUERY_FULFILLMENT` | 询问发货时间、预售、出库、承诺发货日或履约时效。 |
| `QUERY_LOGISTICS` | 查询运单/物流轨迹、物流停滞、配送状态，或物流显示签收但用户未收到。 |
| `QUERY_ORDER` | 查询订单是否存在、订单列表或一般订单状态，不包含取消、退款等更具体动作。 |
| `RECOMMENT` | 请求推荐或重新推荐商品；即使带有预算、品牌、数量等条件，只要主要动作是“推荐”，仍归此类。 |
| `REFUND` | 发起退款/退货退款，或询问退款条件、规则、资格及一般到账时效；尚未指向某一笔已提交退款。 |
| `REFUND_STATUS` | 查询已经申请或页面已显示处理中的某笔退款是否到账、处理进度或最终结果。 |

### 常见近邻边界

- “取消规则是什么”仍是 `CANCEL_ORDER`；“这单还在不在”是 `QUERY_ORDER`。
- “大概几天发货”是 `QUERY_FULFILLMENT`；“物流一直不动/显示签收但没收到”是 `QUERY_LOGISTICS`。
- 商品属性、功能、兼容性或比较是 `PRODUCT_CONSULT`；要求找一批符合条件的商品是 `PRODUCT_SEARCH`；要求换一批或重新给推荐是 `RECOMMENT`。
- 一般退款政策/时效是 `REFUND`；已经提交退款后查进度或银行卡未入账是 `REFUND_STATUS`。
- 质量、错发、少件等已有明确异常归 `DAMAGED_OR_WRONG_ITEM`；只有连问题类别都说不清、只能确认是售后时才用 `AFTERSALES_UNKNOWN`。
- 服务态度、客服答非所问或隐私泄露的主要诉求是投诉时归 `COMPLAINT`；“找真人”本身没有业务事件时才归 `HUMAN_REQUEST`。

## 三、风险等级

`riskLevel` 只根据用户原话中可见的后果和操作性质判断，不能因为出现订单号、金额或“很急”就自动升为高风险。

- `LOW`：普通商品咨询、搜索/推荐、评价、优惠券和一般订单/物流/发货查询；没有直接资金、隐私、安全或不可逆操作后果的闲聊也属低风险。
- `MEDIUM`：普通退款、取消订单、确认收货、地址修改、发票更正、一般售后/投诉；支付或物流状态存在异常但尚未出现明确损失；单纯要求人工且没有高危事实。
- `HIGH`：已经发生或很可能立即扩大的资金风险（未授权/重复扣款、支付成功但订单未生成、失败却已扣款）、退款账户或账户安全风险、隐私泄露、人身/设备安全风险（如电池鼓包发热），以及显示签收但实际未收到等需要凭证核验的高后果事件。

金额高低本身不决定等级；要看是否存在损失、未经授权、账户归属不明、危险状态或不可逆后果。没有原文依据时不得把风险猜成 `HIGH`。

## 四、转人工与严重度

### `shouldHandoff`

标为 `true` 的情形：

- 用户明确要求转人工、找真人、安全专员或把人工处理作为当前请求的条件（包括“拿不准就转人工”）；
- `HIGH` 风险事件，需要人工核验、止损或安全处置；
- 重复失败、持续答非所问、跨账户/订单归属不明，继续自动操作可能造成错误或不可逆后果。

普通且信息充分、可以安全回答的低/中风险查询标为 `false`。不能因为“客服问题理论上都能转人工”就全部标为 `true`。

### `handoffSeverity`

- `CRITICAL`：资金、账户/隐私、人身或设备安全正在发生或可能立即扩大，或需要马上止损/核验的高风险事件。
- `NORMAL`：普通人工请求、投诉、复杂售后或重复失败，但没有立即扩大的危险。
- `shouldHandoff=false` 时必须为 `null`；`shouldHandoff=true` 时不能留空。

如果具体业务事件和人工请求同时出现，`intent` 按第二节判定，`shouldHandoff`/严重度按本节判定，三者不要互相覆盖。

## 五、slots 判定

- 只提取用户原话中明确出现、且与最终诉求有关的实体；不从订单后台、商品目录、常识或评审意见补值。
- 值必须逐字保留原话的大小写、数字、单位、货币符号、全角字符和千分位；不要为了“统一格式”改写用户表达。
- 常用键包括 `orderId`、`orderItemId`、`productId`、`productName`、`brand`、`amount`、`quantity`、`discount`；其他键必须能清楚说明其语义。
- 同一实体有明确不同角色时分开标注，例如应有颜色和实收颜色分别用 `expectedColor`、`receivedColor`；不能把不同语义压成一个含糊键。
- 同一键确实出现多个值且无法按角色拆分时，按原文出现顺序用全角分号 `；` 连接，并在 `reason` 解释；不能静默丢掉第二个值。
- 否定内容不应被当成当前动作的标签或无关槽位。例如“不是取消”不能因此把 `CANCEL_ORDER` 当主意图；只有该否定实体仍直接约束当前请求时才保留。
- 没有明确相关实体时填 `{}`；键和值都必须是非空字符串，不能填 `null`、猜测值或模型生成值。

## 六、仲裁理由和最终标签

每案的最终结果必须完整包含 `intent`、`riskLevel`、`shouldHandoff`、`handoffSeverity`、`slots`。理由至少说明：

1. 原话中决定意图的短语或事件；
2. 风险和转人工判断的事实依据；
3. 若存在近邻分歧，为什么不选另一标签；
4. 槽位采用原文哪一段，或为什么没有槽位。

理由应描述可复核的原文事实，不应引用“评审 A 说什么”“评审 B 说什么”作为唯一依据，也不应加入模型答案、后台状态或原话没有的事实。
