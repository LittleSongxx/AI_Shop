# 决策文档：消息可靠性与退款人工复核闭环

本文只记录已经由源码、测试或迁移脚本支持的事实，不把本地演示数据包装成生产结论。

## 背景：写命令的可靠投递与"重试耗尽后怎么办"

AI 售后让用户确认退款后，Java 侧通过 `TransactionalMqSender`（事务提交后发送）向 RabbitMQ 投递退款指令，消费者侧以业务键幂等去重。但这只保证了"指令送达且不重复"，没有回答：**指令反复失败时，系统如何收敛？**

消息可靠性的三层保障（本地消息表 + 事务后发送 + MQ 补偿扫描）解决"送达"；幂等台账解决"不重复"；但自动重试不是无限预算——`refund_request` 的 `retry_count` 到达上限后进入 `MANUAL_REVIEW`，此前这个状态没有任何转出路径：

- `requestRefund` 对 MANUAL_REVIEW 抛"请勿重复提交"；
- `reconcile()` 只处理 PENDING_PAYMENT / PAYMENT_CONFIRMED / STOCK_PENDING 三个自动阶段；
- `queueStockRestore` 对 MANUAL_REVIEW 直接返回 false。

重试耗尽 = 死路。任何只做"重试 + 幂等"的系统都会在这里停下来；闭环的差别在于**停下来的地方有没有人工出口，以及人工决定之后系统是否自动续跑**。

## 修复方案：审批闭环，而不是把人工写进自动路径

### 1. 进入人工复核时记录原阶段

`recordPaymentFailure` / `recordStockRetry` 的重试耗尽分支在状态翻转为 MANUAL_REVIEW 的同时，把进入前的阶段写入 `review_origin_status`（PENDING_PAYMENT 或 STOCK_PENDING）。审批通过后按原阶段恢复，Saga 从断点续跑，而不是从头重来。

### 2. 审批动作的幂等与并发单次生效

- **幂等**：审批编号 `review_id` 由调用方生成，重试必须复用；`refund_review_ledger` 按 `review_id` 唯一约束，重复提交被台账吸收，审批动作只执行一次。这与订单写命令的 `order_request_idempotency` 台账是同一套模式——**幂等键由写入方生成、结果落账、重试查账**。
- **并发**：状态翻转用 CAS（`UPDATE ... SET status = ? WHERE refund_request_id = ? AND status = 'MANUAL_REVIEW'`），两个管理端同时审批同一笔时只有一个 affected=1，另一方收到"审批冲突，请刷新后重试"。

### 3. 审批语义三态

| 动作 | 状态迁移 | 语义 |
|---|---|---|
| APPROVE | MANUAL_REVIEW → review_origin_status（retry_count 清零，next_retry_time=NOW） | 恢复 Saga，定时器自动接管 |
| REJECT | MANUAL_REVIEW → REJECTED（终态，保留 review_origin_status） | 本次申请作废 |
| 用户重开 | REJECTED → COALESCE(review_origin_status, 'PENDING_PAYMENT')（CAS，用户重新发起时） | 驳回不封死；重开回到驳回前阶段——STOCK_PENDING 驳回的行直接续跑库存恢复，不重走支付（资金已退过，再走支付是重复退款风险） |

### 4. 冻结字段重新校验：人工窗口期的数据漂移防护

审批通过恢复推进前，把落库时冻结的金额 / 数量 / 属性与订单项当前值重新比对（`revalidateFrozenFields`）。人工复核可能跨越数小时到数天，期间业务侧可能改价、改属性、退订——按冻结值推进会退错钱。任一字段漂移或订单项状态不再是 NORMAL，审批停在 MANUAL_REVIEW 交由管理端核实，绝不盲目恢复。驳回路径不需要校验（终止语义不产生资金动作）。

例外：`review_origin_status = STOCK_PENDING` 的请求跳过状态与冻结值校验（只保留明细存在性防御）——该阶段资金已退回、订单项已被 `finalizeOrderRefund` 翻为 REFUND(0)，剩余动作只有库存恢复，冻结值校验失去对象，要求 NORMAL 会误拦一切可恢复的审批。

## 取舍与未采用方案

- **不引入审批流引擎**（Activiti/Flowable）：本地业务只需要"通过/驳回"两个决策 + 幂等台账，工作流引擎的模型库、部署、流程实例是远超需求的重型依赖。
- **不把人工写进自动路径**：不用"重试耗尽后继续重试"（无界预算）、不用"重试耗尽自动成功/自动退款"（资金动作必须有人确认）。
- **恢复不重走全流程**：用 `review_origin_status` 从断点续跑。重走全流程会重复已成功的支付步骤，违反 Saga 的补偿语义。
- **驳回不封死**：REJECTED 是"本次申请作废"，用户重新发起即重开。MANUAL_REVIEW 才是用户无法自行绕过的状态。

## 测试与验证

- `RefundReviewServiceTest`：审批恢复 / 驳回终态 / review_id 幂等命中 / review_id 跨单冲突 / CAS 竞争失败 / origin 缺失防御回落 / 冻结字段四种漂移（金额、数量、属性、订单项状态）全部拦下 / 驳回跳过校验。
- `RefundSagaServiceTest`：requestRefund 对 MANUAL_REVIEW 拒绝、对 REJECTED 重开；`reconcileDrivesApprovedRefundToCompletion` 端到端走完"审批恢复 → 支付 → 库存确认 → COMPLETED"。
- 管理端三个接口（loadDataList / approve / reject）与 statusName 映射（含 REJECTED"退款申请已驳回"）有对应测试。

## 残余风险

- 冻结字段校验在审批事务内完成，批准后到实际推进之间的极小窗口仍有理论漂移可能；当前 CAS + 行锁使其趋近于零，但没有做分布式锁级别的强保证。
- 审批管理端权限沿用现有 admin 网关约定，未在服务内做二次校验。

## 60 秒面试复述

自动重试和幂等解决"消息不会丢、不会重"，但重试耗尽后系统必须有一个收敛点。我把收敛点设计成人工复核闭环：重试耗尽时记录进入前的 Saga 阶段，管理端通过（APPROVE）就从断点恢复让定时器自动续跑，驳回（REJECT）则终止本次申请、用户可重新发起；审批动作本身用客户端幂等键 + CAS 条件更新保证并发下只生效一次，台账落账。恢复推进前我还重新校验申请时冻结的金额、数量、属性与订单项当前值，防止人工窗口期的数据漂移导致退错钱——人工决策和自动化恢复之间必须有一个可验证的交界。
