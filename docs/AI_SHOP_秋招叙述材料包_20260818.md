# AI_Shop 秋招叙述材料包

> 版本：2026-08-18
>
> 适用主轨：AI 后端 / Agent 开发；第二入口：Java 电商后端。
>
> 使用规则：只讲当前分支已实现、可定位到代码或测试的内容；确定性、回放和真实 Provider 结果必须分开。没有采集到的指标直接说“未采集”，不把门槛、单元测试或旧结果包装成线上收益。

## 1. 先记住项目定位

### 1.1 一句话

AI_Shop 是一个 Java 电商业务底座上的受控 AI 应用：推荐侧把文本/图片检索、模型排序和 Java 权威报价库存串成可归因闭环；客服侧把政策 RAG、订单权威事实、用户确认和幂等执行串成可恢复工单闭环。

### 1.2 两条正式主线

1. **推荐导购**：Java 商品/库存/优惠权威域 → 文本或视觉召回 → 混合融合与 rerank → 约束过滤 → Java 权威报价/库存核验 → 曝光、点击、加购、支付、复购归因。
2. **AI 客服**：自然语言订单定位 → 多订单澄清 → 发布版政策 RAG → MCP/Java 查询权威订单 → 结构化操作提案 → 用户确认 → Java 再校验 → 幂等执行；远端写结果未知时进入 `INCONCLUSIVE`，对账达到边界后进入 `MANUAL_REVIEW`。

视觉搜索归入推荐主线。Text2SQL 目前是有权限、只读、扫描/结果预算、分页和异步导出的后台分析实验，尚未达到第三主线准入条件。

### 1.3 不要这样讲

- 不说“已经上线并提升 CTR/CVR/GMV”；当前没有 `REAL_USER`、CTR、CVR、GMV 或生产 SLO 证据。
- 不说“Agent live TSR 已达到门槛”；Agent v2 当前 `resultStatus=NOT_COLLECTED`。
- 不把 deterministic、replay、rescore 或单元测试称为真实模型质量。
- 不把 RAG 的 `39/60` 或 Search 首次 `Recall@10=0.3778` 隐瞒为成功；它们是正式失败并按 `FAILED_RETAINED` 保留的 badcase 入口。

## 2. 90 秒 AI 后端 / Agent 开场

> 我做的是 AI_Shop，一个 Java 电商底座上的 AI 后端项目，主线不是“让模型直接改订单”，而是把模型放在受约束的检索、解释和提案层，把商品、库存、订单、支付和最终写入留给 Java 权威服务。
>
> 推荐链路支持文本和视觉找同款：请求先带 `requestId/runId`，图片先做资产校验和主体选择，再进行关键词/向量召回、RRF 融合、rerank 和约束过滤，最后通过 Java Gateway 核验价格、库存和可购买性；曝光、点击、加购、支付和复购都用统一事件模型归因。客服链路则是自然语言定位订单、处理多订单歧义、检索发布版政策、通过 MCP 查询 Java 订单事实，再生成需要用户确认的结构化提案。
>
> 我重点解决的是可靠性：用户确认后 Java 会重新校验归属、状态、参数和幂等键，远端写超时不自动重放，而是进入 `INCONCLUSIVE`，对账仍无法确定才转 `MANUAL_REVIEW`。每次评测和关键请求保留 Episode、工具参数、模型版本、token、成本和终态，并用统一 Runner 区分 `PACKAGED/COMPLETE`、`FAILED_RETAINED` 和 `BLOCKED`。
>
> 当前真实质量结论也保持诚实：Search 和 RAG 的正式门禁仍有失败，Agent v2 live 还未采集，所以我把重点放在可复现的评测锁、badcase 分类、Provider 完整性和故障闭环，而不是虚构业务收益。

## 3. 90 秒 Java 电商后端开场

> 如果从 Java 后端角度讲，AI_Shop 的核心是商品、库存、订单、支付、优惠券和消息链路。Java 服务负责领域事实和最终写入，Gateway 负责内部边界，Redis 负责短期状态和幂等辅助，RabbitMQ 加本地事务消息表保证事件可靠投递，订单/退款等高风险操作用状态机、CAS、唯一业务键和补偿/对账任务保证最终收敛。
>
> AI 只是上层调用方：它不能直接读写业务表，也不能把模型生成的文本当作订单事实。客服提案在用户确认后再次走 Java 鉴权、订单归属、状态和幂等校验；远程执行超时不等于失败，未知结果会保留为 `INCONCLUSIVE`，由对账或人工复核处理。推荐同样不使用模型里的价格和库存，商品卡片必须绑定 Java 权威报价快照。
>
> 因此这个项目既能讨论 Spring Cloud、MySQL、Redis、RabbitMQ、一致性和恢复，也能讨论 Agent 的工具边界、RAG、评测和可观察性；我会把两套指标和证据分开，不用 AI 结果替代交易系统正确性。

## 4. 一张可讲清的架构图

```text
用户端 / 管理端
        │ requestId + runId + W3C traceparent
        ▼
Agent API / v1 Contract
        │
        ├── Recommendation Facade
        │     ├── 文本召回 / 视觉主体选择 / VLM+Embedding
        │     ├── 混合融合 → Rerank → 约束过滤
        │     └── Java Gateway：商品、报价、库存、优惠
        │
        └── Support Workflow / Agent
              ├── 政策 RAG（发布版知识 release）
              ├── MCP Tool Router（权限、参数、脱敏）
              ├── 提案 → 用户确认 → Java 再校验
              └── Outcome Ledger / INCONCLUSIVE / MANUAL_REVIEW

RabbitMQ → Worker → LangGraph → MCP → Java Gateway → Java Domain → DB/ES
                         │
                         └── Episode / OTel Trace / Metrics / Eval Evidence
```

### 4.1 一条完整 Trace 应该怎么讲

以“昨天买的蓝色手机壳，符合政策就申请退款”为例：

1. 前端生成 `requestId`，沿 `traceparent` 进入 Agent API；Episode 绑定 `runId/episodeId`。
2. Agent 先调用订单定位工具，返回多个候选时只进入 `CLARIFICATION_REQUIRED`，不猜订单。
3. 用户选中候选后，RAG 只从固定知识 release 取政策证据；引用不足就拒答或转人工。
4. MCP 查询 Java 权威订单事实，并记录工具名、参数摘要、返回状态和订单归属校验。
5. 模型只输出结构化 `ActionProposal`，前端展示金额、商品、政策引用和风险提示。
6. 用户确认后携带提案 token 和幂等键；Java 再校验状态、归属、冻结字段和幂等冲突。
7. 明确成功才进入 `SUCCEEDED`；超时/未知进入 `INCONCLUSIVE`，对账边界后转 `MANUAL_REVIEW`。
8. Episode 同时写入结果、成本、延迟、Provider 完整性和 Outcome Ledger，管理端可复核整条链。

## 5. 六个面试故事

每个故事固定按“症状 → 错误假设 → 证据 → 根因 → 取舍 → 实测 → 限制”回答。不要先讲框架名。

### 故事一：推荐归因不是最后才补埋点

- **症状**：推荐卡片能展示，但点击、加购和支付无法稳定关联到同一次请求和同一商品位置。
- **错误假设**：只要记录商品 ID，后面再从日志推断来源即可。
- **证据**：相同商品可能出现在不同请求、不同位置和不同模型版本；缺少幂等键会重复记账。
- **根因**：推荐结果缺少不可变的 serving identity，展示数据和业务事件没有共同主键。
- **取舍**：事件统一携带 `requestId`、`runId`、`productId`、`position`、`modelVersion`、`eventId`、`idempotencyKey`；新 v1 事件优先，旧 reportClick 保留短期兼容。归因失败不阻断交易。
- **实测**：契约测试覆盖事件字段、位置从 1 开始、重复幂等和旧卡片兼容；前端用户端 33 项测试通过。
- **限制**：目前只有合成/本地链路证据，没有真实用户 CTR、CVR 或 GMV uplift。

### 故事二：视觉找同款先解决主体和购买事实

- **症状**：一张图可能有多个商品，视觉召回还可能命中已下架或无库存商品。
- **错误假设**：直接把整张图丢给向量检索，返回相似度最高的几条就够了。
- **证据**：多主体图片会产生歧义；索引里的价格/库存可能过期；低 cosine 候选会制造跨类误召回。
- **根因**：主体选择、召回、排序和交易事实混在一起，且没有显式的无结果路径。
- **取舍**：图片资产先由 Java 校验，多个主体先让用户选择；文本/视觉候选做加权 RRF 和 rerank，再加载 Java 权威商品快照；低相似度和无可购买商品返回 `NO_RESULT`/澄清，不用静态分类表误杀未知品类。
- **实测**：`visual-v1` 锁定 25 条，覆盖 exact、裁剪、视角、相似类别和 no-match；验证要求 Recall、MRR、NDCG、拒答准确率、跨类误召回、不可购买率和 fallback 证据同时满足。
- **限制**：没有真实 VLM/Embedding/Rerank 完整运行时，正式 live 结果必须是 `BLOCKED`，不能用 deterministic 结果代替。

### 故事三：订单事实必须回到 Java 权威域

- **症状**：模型能根据自然语言找到“像是”某个订单，但商品、金额、状态或归属可能不准确。
- **错误假设**：把订单摘要放进 Prompt，模型就可以直接回答和操作。
- **证据**：订单状态会变化，用户可能有多个相似订单；自然语言中的金额和商品名不能作为授权事实。
- **根因**：把解释层的文本和领域事实混成了一个数据源。
- **取舍**：Agent 只通过内部 Gateway/MCP DTO 查询 Java 订单；订单候选带选择会话和过期时间，多订单必须澄清；模型不可直接读表或拼接写 SQL。
- **实测**：订单选择、委托身份、工具参数和归属校验有契约/安全测试；管理端和 Episode 能查看候选、选择和终态。
- **限制**：完整 Agent v2 真实 Provider 任务尚未采集，不能声称自然语言定位准确率已达目标。

### 故事四：提案确认与幂等执行如何避免重复退款

- **症状**：远端写接口超时后，重试看起来能提高成功率，却可能把一次退款执行两次。
- **错误假设**：所有工具调用都使用通用指数退避重试。
- **证据**：超时只说明客户端不知道结果，不说明服务端没有执行；退款是副作用，不是幂等查询。
- **根因**：把“执行失败”和“结果未知”压成同一个失败状态。
- **取舍**：模型只能生成 `PROPOSE_*`；用户确认后 Java 再校验；以规范化业务参数生成幂等键，远端未知进入 `INCONCLUSIVE`，只允许查询幂等账本/领域状态，对账达到边界后 `MANUAL_REVIEW`，禁止自动重放。
- **实测**：Java 侧有幂等、CAS、退款库存恢复和人工复核路径；Python 侧统一终态契约覆盖 `PROPOSED`、`CONFIRM_REQUIRED`、`SUCCEEDED`、`INCONCLUSIVE`、`MANUAL_REVIEW`。
- **限制**：本轮不把本地集成测试写成生产可用性或真实退款成功率。

### 故事五：RAG 失败后先修口径和证据，再修模型

- **症状**：早期 RAG 结果看起来不错，但 fresh/回放、公开集/holdout 和人工审核口径混杂，无法判断真实提升。
- **错误假设**：把暴露后的 replay 高分当作模型已经变好，或者只换 Prompt 就能解决。
- **证据**：Search 首次 ProductService `Recall@10=0.3778`；RAG v4 fresh `Recall@5=0.8056`，生成正式结果 `39/60`，都未过门槛；人工盲评仍为 `HUMAN_REVIEW_PENDING`。
- **根因**：数据集锁、fresh/replay 标记、Provider 完整性和失败结果保留不够严格，badcase 没有按检索/生成/安全切片。
- **取舍**：固定 dataset lock、knowledge release、prompt/model/provider 指纹；正式 live 禁止 fallback 冒充真实 Provider；质量失败保留为 `FAILED_RETAINED`，依赖不可用为 `BLOCKED`；先按证据不足、召回错、引用错、生成错和安全污染分类。
- **实测**：统一 Runner 成功走 `PACKAGED/COMPLETE`，失败保留 `FAILED_RETAINED`，阻塞为 `BLOCKED`；新增 visual/text2sql suite 校验生命周期和锁。
- **限制**：当前没有可对外宣称的 Agent live TSR，也没有真实用户满意度或成本曲线。

### 故事六：可观察性不是“打了几个日志”

- **症状**：前端看到完成，但 Worker、MCP 或 Java 是否真正执行、哪里丢失、是否重复很难复盘。
- **错误假设**：在 Agent API 打一个 traceId，其他服务以后再补。
- **证据**：请求会跨前端、API、MQ、Worker、LangGraph、MCP、Gateway、Java、DB/ES 和 Outcome Ledger；只记录入口无法回答队列堆积、工具参数和业务终态问题。
- **根因**：没有统一的 `traceparent/runId/episodeId` 和跨层结果契约。
- **取舍**：W3C `traceparent` 贯通请求；Episode 保留评测和关键流量；OTel 记录节点、工具、Provider、token、成本和错误；业务终态先落账再推送，普通流量可采样但暴露采样率、丢弃数和写入失败告警。
- **实测**：测试和 manifest 校验 Trace/Episode 字段、PII/密钥脱敏和结果状态；评测结果包含 Provider 完整率和证据等级。
- **限制**：本地 P99 小样本不作生产 SLO；真实用户 Pilot、线上容量和人民币成本仍未采集。

| 证据 | 当前能说的结论 | 不能说的结论 |
|---|---|---|
| E0 源码/契约/测试 | 主线边界、状态机、权限和失败规则存在 | 真实模型质量已达标 |

### 6.1 当前硬事实

- Search v2 覆盖中文 600 商品/240 查询；首次 ProductService fresh `Recall@10=0.3778`，正式失败保留。
- RAG v4 fresh `Recall@5=0.8056`；生成正式结果 `39/60`，正式失败保留，人工状态 `HUMAN_REVIEW_PENDING`。
- Visual suite：25 条锁定任务，包含 5 条 no-match；真实 Provider 不可用必须 `BLOCKED`。
- Text2SQL suite：40 条锁定任务；SQL 安全、结果正确、叙述一致、Trace/成本完整均达门槛后才可升级第三主线。
- Agent v2：当前 `resultStatus=NOT_COLLECTED`；不得用 deterministic 或旧 Runner 补齐。

## 7. 常见追问的短答

### 为什么不是多 Agent 越多越好？

确定性流程先用 Workflow，单域开放任务用单 Agent，只有跨域复杂任务才启用受限多 Agent。多 Agent 增加状态同步、预算、权限和评测复杂度，本身不是价值指标。

### 为什么模型不直接查 Java 数据库？

数据库是 Java 领域事实源，直接暴露会绕过归属、权限、事务和审计。Agent 只能拿版本化 Gateway/MCP DTO，写操作必须经过 Java 再校验。

### Provider 401/403/quota/timeout 怎么处理？

正式 live 评测立即 `BLOCKED`；不回退 deterministic，也不把 fallback 结果写成真实质量。普通业务流量可以受控降级，但要显式记录 `fallbackUsed` 和降级原因。

### 你怎么证明一次退款没有执行两次？

看业务幂等键、唯一约束、Java 领域状态、Outcome Ledger 和对账结果，而不是看模型回复。未知结果期间不自动重放，确认边界后才人工接管。

### 如果指标变差，下一步怎么做？

先固定 run manifest 和 dataset lock，按 badcase 切片确认是数据、召回、rerank、引用、生成、工具参数还是执行终态问题；一次只改变主要变量，known 集选方案，fresh 集只做一次正式验证。

## 8. 现场展示顺序

1. 展示 README 的两条主线和限制声明。
2. 演示一条推荐请求：文本/图片 → 商品卡片 → Java 报价库存 → 点击事件。
