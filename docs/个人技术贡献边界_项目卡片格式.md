## 项目定位

AI_Shop 不是训练、推理优化或 Agent Infra 项目，而是“Java 交易底座 + Python 受控售后 Agent”的单商户电商应用。模型负责理解、规划和解释；RAG 提供售后政策；MCP/Java 内部接口提供订单权威事实；任何退款写操作必须经过提案、用户确认和 Java 领域校验。

当前前端技术栈是 Vue 3、Vite、Element Plus；LangGraph Checkpoint 持久化在 Redis，不是 PostgreSQL。框架能力属于开源复用，项目价值在业务边界、失败语义和可验证证据。

## 90 秒叙述

> 我把 AI_Shop 收敛成了一条受控售后闭环。用户可以用“昨天买的蓝色手机壳”这类自然语言定位订单；系统先处理多订单歧义，再按任务复杂度选择确定性 Workflow、单 Agent 或受限多 Agent。退款资格由 RAG 查询已发布政策，订单状态由 MCP 调 Java 权威接口，模型只能生成退款提案。用户确认后，Java 再校验身份、订单归属、业务状态和幂等键；远端结果明确才进入成功，超时或结果未知进入 INCONCLUSIVE，并在自动核对达到边界后转 MANUAL_REVIEW。每次运行都落 Episode、工具参数、编排决策、token、成本和终态。项目还冻结了 37 条真实全栈任务契约，但目前没有伪造 live TSR：正式 Agent 模型结果要等完整服务、真实 Provider 和等价业务快照就绪后采集。

## 可深挖的闭环

```text
自然语言诉求
  -> 订单引用解析与歧义澄清
  -> RAG 售后政策 + MCP/Java 订单事实
  -> 结构化退款提案
  -> 用户显式确认
  -> Java 鉴权、归属、状态与幂等执行
  -> 已知结果：CONFIRMED/FAILED
  -> 未知结果：INCONCLUSIVE -> 对账 -> MANUAL_REVIEW
  -> Episode/任务集/消融/脱敏 Trace 形成证据
```

### 1. 自然语言订单定位

- 支持订单号、相对时间、金额、商品描述等线索，不在模型中拼 SQL。
- 候选为零、多个候选、无可操作项和依赖失败分别建模，多个候选会持久化澄清上下文。
- 解析后的订单仍需 Java 权威接口确认归属与状态。

### 2. 自适应编排，而不是默认多 Agent

- `workflow`：边界清楚、参数完整的权威查询或写提案。
- `single_agent`：开放问答、RAG、缺参澄清等单域任务。
- `multi_agent`：订单事实与售后政策等跨域复合任务，专家只返回有界 artifact。
- `adaptive/workflow/single_agent/multi_agent` 可固定配置，用于同一冻结任务集的真实配对消融。
- 只解释退款资格的请求，即使识别到真实订单，也不得生成 `PROPOSE_REFUND`。

### 3. RAG 证据与 Provider 完整性

- 生产路径包含 Exact FAQ、BM25/Vector、RRF、Qwen3 Rerank、证据选择、引用和注入检疫。
- Trace 区分真实 embedding/rerank 请求、成功、失败和缓存命中，不能把调用封装或缓存命中冒充 Provider 请求。
- live 任务判分要求每个 RAG 事件都有 Runtime Trace；真实调用必须成功，出现缺失 Trace 或 fallback 时该样例 fail-closed。

### 4. 受控写操作与未知结果

- 模型工具只创建带过期时间的 pending action，不直接退款。
- 用户确认后，Java 内部接口重新检查用户身份、订单归属、状态和幂等请求账本。
- 通用重试不会重放未知写结果；仅 MCP session lost 允许单次会话重建，Worker 依赖持久任务状态退避。
- 远端结果未知时保持 `INCONCLUSIVE`，自动核对达到边界后进入 `MANUAL_REVIEW`，不能向用户误报成功。

### 5. 运行时护栏和可验证证据

- 预算守卫按一次运行隔离 token、人民币成本、节点步数和 monotonic deadline，并提供 80% 预警与受控终态。
- 熔断器实现 CLOSED/OPEN/HALF_OPEN 及并发 probe 限制；它保护 Provider 调用，但不替代业务幂等。
- 37 条冻结任务通过真实 API、RabbitMQ、Worker、LangGraph、MCP、Java 和数据库执行，不存在模拟器或 in-process 快捷路径。

## 框架与个人贡献边界

| 范围 | 正确口径 |
|---|---|
| LangGraph | 使用其 StateGraph、conditional edge 和 checkpoint 接口；业务状态、路由、安全边界与 Redis 持久化适配属于项目代码 |
| Spring Cloud Alibaba | 使用现有微服务、注册配置与交易领域能力；不要把框架能力说成自研 |
| MCP | 使用协议与 SDK；工具白名单、内部身份、参数和 Java 权威事实边界属于项目集成 |
| Testcontainers | 使用官方测试框架与镜像；并发业务断言和 fixture 属于项目测试 |
| Vue/Element Plus | 使用组件库；不要说成 Vant，也不要把组件库能力算作个人算法实现 |
| AI 辅助开发 | 可以说明 AI 用于调研、样板和审查；必须能独立解释关键状态机、失败语义、测试与取舍 |

## 高频追问

1. **为什么模型不能直接退款？** 模型输出具有概率性，退款是不可逆业务写。提案和执行分离后，用户确认与 Java 领域约束成为确定性授权边界。
2. **为什么未知结果不能重试？** 超时不代表远端失败，自动重放可能重复退款。先用同一幂等键查询权威状态，仍未知则人工复核。
3. **为什么不全部走多 Agent？** 简单任务的拆分会增加 token、延迟和故障点。当前策略仅在跨域复合请求使用多 Agent，且正式 live 消融尚未采集。
4. **预算超限算失败吗？** 运行会进入明确受控终态并留下预算事件；评测中按任务契约判分，不能把超限隐藏成成功。
5. **如何证明不是模拟评分？** Runner 只调用对外 API，并从持久 Episode、消息和 pending-action MySQL 行判分；依赖、fixture 或 Provider 证据不完整就中止或失败。
6. **目前最弱的地方？** 没有 Agent 真实模型全栈 TSR、三模式 live 消融和真实用户数据；RAG v4 正式质量门禁也未通过。

## 禁止表述

- “Agent TSR 已达到 80%”或“37 条全部通过”：正式结果尚未采集，80%只是当前 lock 中的门禁。
- “多 Agent 显著提升成功率”：旧确定性消融没有成功率增益，live 消融未采集。
- “通用指数退避保证工具可靠”：项目已删除未接入生产路径的通用重试装饰器。
- “Checkpoint 使用 PostgreSQL”或“前端使用 Vant”：实际分别是 Redis 和 Element Plus。
- “生产就绪”“真实用户指标”“线上 SLO”：当前证据最高为本地 E3，且 Agent E3 未采集。
