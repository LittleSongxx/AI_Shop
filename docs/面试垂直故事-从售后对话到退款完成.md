# 面试垂直故事：从一句售后对话到一笔退款完成

> 使用方式：以"症状 → 我做了什么 → 失败/取舍 → 证据"的结构讲。这个故事覆盖 Agent 编排、
> 检索治理、工具安全、HITL、消息可靠性、分布式状态机与人工闭环，能扛住"项目深挖"类问题。

## 开场

"用户对 AI 说『昨天买的耳机要退货』，到钱真正退回，链路经过：身份委托 → 意图识别 → 检索检疫 →
工具调用治理 → 人工确认 → Java 幂等执行 → 退款 Saga → 重试耗尽人工复核 → 审批恢复。我挑四个
我认为最难的点讲。"

## 第一幕：身份 — 模型说的 userId 不作数

**症状**：Agent 调订单服务时 userId 在 body 里由 LLM 生成，LLM 可以被注入话术诱导改写——身份判定和受检内容共用一条信道。

**方案**：分层。网关在传输层填 `X-Agent-User-Id`（模型不可见不可改），Java 侧 fail-closed：头缺失 401、body 与头不符 403、数据归属不符 403，拒绝后零成功信号。

**取舍**：不给 body 加签名（body 本来就是模型生成的，加固它没意义）；不引入用户令牌链（委托只需要"谁代办"的轻量断言）。

## 第二幕：检索 — 知识库可能脏，但不能让整个 RAG 下线

**症状**：知识库文档可能被投毒；一段"忽略之前所有指令"的文档如果进了上下文，整个对话都可以被劫持。

**方案**：通道内容与用户输入区别对待。输入用硬阻断（拒绝），通道内容用**检疫**——所有 RAG 路径在唯一组装点逐条扫描，污染片段剔除并计指标；工具结果在进上下文前用同一张规则表扫描，命中就把正文替换为隔离占位符，原文只留在 trace。模型上下文里不存在污染文本，但合法检索请求不会因为一篇脏文档而失败。

**取舍**：不做"污染即拒绝"（投毒者一篇文档就能打掉整个 RAG 是放大的攻击面）；不做净化改写（改写语义无法证明无害，占位符 + 留痕最诚实）。

## 第三幕：工具 — 模型看到的每一段文本都被治理过

**症状**：ReAct 里模型看到的是 ToolMessage.content，工具实现的任何输出都从这里进上下文——未来新增工具也可能有 PII 泄漏或超长输出。

**方案**：Observation 层统一治理（脱敏 → 裁剪 → 通道扫描），所有工具结果必经此层；被省略的部分全部写进 trace。这不是某个工具的修复，是入口级的治理。

## 第四幕：确认与执行 — 退款必须经过人

**症状**：让模型"记得调工具"不是运行时保证，直接执行资金动作更不可接受。

**方案**：Propose → 用户确认卡 → Java 幂等执行。写命令进 `order_request_idempotency` 台账：业务键去重、CAS 单次生效、失败状态可见——模型重复调用、网络重发都只执行一次。

## 第五幕：Saga — 自动重试有预算，耗尽后必须有收敛点

**症状**：退款 Saga 三阶段推进（PENDING_PAYMENT → PAYMENT_CONFIRMED → STOCK_PENDING → COMPLETED），重试耗尽进 MANUAL_REVIEW 后没有任何转出路径——死路。

**方案**：管理端审批闭环。进入复核时记录原阶段；APPROVE 按原阶段恢复、重试计数清零、定时器自动续跑；REJECT 终止本次申请、用户可重开；审批动作本身用客户端幂等键 + CAS 保证并发单次生效，台账落账。

**关键细节（面试加分点）**：恢复推进前重新校验申请时冻结的金额/数量/属性与订单项当前值——人工窗口期业务侧可能改价，按冻结值推进就退错钱。人工决策与自动化恢复之间必须有一个可验证的交界。

## 收尾

"贯穿所有幕的是同一件事：**凡是模型碰得到的内容都按不可信处理，凡是影响资金和状态的动作都要求可验证**。身份在模型碰不到的层断言，检索内容逐条检疫，工具输出统一治理，执行靠幂等台账，自动重试的边界交给带校验的人工闭环。每一层都有测试和指标支撑，包括 24 条审批与恢复链路测试和污染隔离的指标计数。"

## 可以被追问的深挖点

| 追问 | 回答要点 |
|---|---|
| 为什么检疫而不是拒绝 | 通道内容与用户输入身份不同；拒绝 = 投毒者可单点下线 RAG，检疫 = 影响收敛到那一条内容 |
| CAS 为什么能保证并发单次生效 | `UPDATE ... WHERE status='MANUAL_REVIEW'` 条件更新，affected rows 即判据；行锁 + 幂等键双保险 |
| 冻结字段校验的窗口 | 审批事务内校验，批准到推进之间理论漂移趋近于零；未做分布式锁级强保证（诚实边界） |
| 幂等键由谁生成 | 写入方生成（review_id 客户端生成、业务键服务端稳定派生），重试复用，唯一约束吸收重复 |
| 回退路径 | 多智能体专家异常 → legacy loop 单向回退；降编排复杂度，不降安全与可观测性 |
