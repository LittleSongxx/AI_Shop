# AI-Shop 关键问题、优化与面试叙事

> 日期：2026-08-31（Asia/Shanghai）
>
> 主线：AI 购物导购、AI 客服 Agent
>
> 使用原则：只讲可复核事实；明确区分自动探索、人工质量、unseen 和生产 SLO

## 1. 30 秒项目介绍

AI-Shop 不是一个只会聊天的电商 Demo，而是把 LLM 放进真实交易边界：商品检索负责候选和
硬约束，RAG 解释发布政策，Java 服务持有订单、库存、价格和资格真相，Agent 只在可核验证据
上生成回答。写操作采用 `PROPOSE_* → server actionToken → 用户确认 → Java command`，并用
Episode、state diff、幂等账本、双盲人工评审和不可变 evidence 验证执行与答案质量。

## 3. STAR 叙事一：动态业务事实防幻觉

### Situation

旧 verifier 只要看到工具名或 `factPath` 就可能放行。模型即使把订单状态、金额、数量、支付
方式写错，或用订单 A 的证据支持订单 B，也可能被算作成功。

### Task

不新增数据库或复杂架构，在 Agent 所有路径共享的 verifier 根节点一次性 fail-closed。

### Action

- 把回答拆成 assertion clause，逐句识别动态事实和 capability。
- 只接受 Java-owned、authoritative、`matched != false` 且工具成功的 business ref。
- 同时校验 orderId/orderItemId、字段和值，而不是只检查路径存在。
- 每句只能绑定本句对象；冲突 snapshot、跨订单借证据、前句正确后句反转全部拒绝。
- 通用政策只由发布版 RAG 支持，不能替代用户当前订单或优惠券状态。

### Result

动态 verifier 的正反回归覆盖了跨订单、错值、失败工具、冲突快照和反转后句。包含 canonical
fallback、RAG claim 合同和动态事实校验在内的 A2 批次整体，使 generation/claim/citation
自动指标从 `0.62` 到 `0.98`，RAG 人工抽样答案为 `23/25`、引用 `13/13`；这些综合结果不能
单独归因于动态 verifier。结构化合同可审计且确定性强，但不冒充通用自然语言蕴含证明。

### 可追问的取舍

高风险交易事实宁愿保守拒绝，也不错误放行；代价是存在 fail-closed 假阴性，开放文本仍需
独立 judge 或人工复核。

## 4. STAR 叙事二：自动高分、人工低分的评测纠偏

### Situation

Agent 自动结果曾是 `21/25`，完整双盲+仲裁却只有 `14/25`。交叉矩阵显示自动过、人工未过
11 条，自动未过、人工过 4 条。两者测量对象并不完全相同；进一步逐项诊断才定位出产品回答、
evaluator 漏检和契约漂移，不能把全部分歧直接叫作自动假阳性/假阴性。

### Task

让 task success 更接近“执行完整且最终答案有证据”，又不把旧人工标签迁移到新输出刷分。

### Action

- 将根 Episode 的 response verifier 纳入 Agent `taskSuccess`。
- 空 `outputPatterns` 只表示未声明语义模板，不再等于“答案无需检查”。
- 推荐理由绑定同商品的当前快照；区分通用券政策和用户具体券状态。
- 保留自动/人工交叉矩阵，并为新输出重新制作 A/B 盲评包。

### Result

自动 gate 的定义更可信；新人工包 A/B 已回传，但 11/25 存在分歧、仍待独立第三人仲裁，
因此当前只声称 evaluator/task-contract 改善，不提前声称最终答案质量已经提高。

### 面试亮点

真正困难的不是把分数做高，而是发现“评测器也会错”，并拒绝用旧标签证明新输出。

## 5. STAR 叙事三：handoff/safety 从 0/12 到 12/12

### Situation

一部分请求已经安全转人工，但旧 gold 要求不存在的 `HANDOFF_TO_HUMAN` 工具和 `GRAPH_END`；
前置安全拒绝本来就没有图执行，又被误判失败。同时三类复合攻击确实没有在输入边界稳定拒绝。

### Task

区分产品安全缺口、运行事实和 evaluator 假阴性，且不通过放宽 gate 提分。

### Action

- 同一 root 内按事件顺序证明 handoff，禁止跨 Episode 拼接 decision/event。
- runtime terminal 由实际 root 终态判断，不借 gold 标签证明 provider complete。
- 安全 REJECT 必须是唯一响应、精确的 guard 文案、无 run/message identity、无 Episode、
  state unchanged 且无重复副作用；任意业务 `600` 不能冒充安全拒绝。
- input/channel guard 只拦“外带动作+受保护资产”“元工具操控”“隐藏命令要求人工直接写”等
  高置信复合模式，同时用正反回归保护正常政策否定、商品内部配置和合规人工确认。
- action token 只接受当前 turn、当前 user/run/action 的 pending row；旧 token、错 owner、缺 token
  全部 fail-closed。

### Result

handoff/safety `0/12 → 12/12`，strict `49/75 → 61/75`，pass³ `16/25 → 20/25`；75 次
执行中 terminal/state diff 100%，无重复副作用、runtime error 或 severe safety violation。

### 必须主动说明

这 12 个新增通过主要是安全边界和评测合同对齐，不是模型文本推理突然增强；RAG-policy 仍只有
`7/21`。

## 6. STAR 叙事四：RAG 显式事实路由与生成稳定性

### Situation

用户明确提到发布版事实 alias 时，普通语义检索不能稳定路由；即使命中正确文档，模型仍会
漏 claim、错引用或在 repair 后继续生成不受支持的句子。

### Task

不改 qrel、不降阈值、不新增依赖，提高来源覆盖与 claim 可追溯性。

### Action

- 从发布版 fact metadata 解析 alias/完整 fact ID；歧义 alias 不扩张 `factHints`，普通未标记
  提及继续走原有语义规划，而不是被拒绝。
- `factHints` 进入 query plan 和 cache key，避免错误复用缓存。
- canonical claim 按 clause 绑定 citation；repair 失败只允许自校验的 deterministic fallback。
- 将 retrieval、generation、claim completeness、citation support 分开度量。

### Result

source coverage `0.586 → 0.966`，随后 generation contract `0.62 → 0.98`。同时诚实保留 A1
NDCG@5 的下降，不把局部改善包装成“RAG 全面提升”。

## 7. STAR 叙事五：unseen 与证据治理

### Situation

历史 final 绝大多数能从开发者可见源码恢复；继续称为 unseen 会产生数据泄漏和虚假质量主张。

### Task

在无法真正角色隔离时，仍建立可信、可复核的评测生命周期。

### Action

- 做 source exposure/overlap audit，锁 candidate、dataset 和 source hash。
- 正式 unseen 冻结；外部模型调用明确标为 post-hoc、non-release-gate。
- 使用 detached worktree，执行前后校验正式哨兵；runner 完成后 verify、SHA256、0700/0600、
  hidden staging 和原子封存。
- 将 exit code 2 解释为“运行完整但门失败”，继续封存失败证据，避免 `set -e` 丢失信息。
- 最终答案质量由双盲、分歧比较和第三人仲裁承担，不由自动 gate 代替。

### Result

项目主动拒绝不可信的 formal unseen 主张，同时保留可追溯的外部模型诊断。这不是“没做成
unseen”，而是发现前提不成立后守住了评测可信度。

## 8. 高频面试追问

### 为什么不用 Prompt 解决幻觉？

Prompt 是软约束，无法证明模型真的使用了正确订单、字段和值。交易事实必须由程序化 verifier
绑定权威业务 ref；Prompt 只负责表达。

### 为什么工具调用成功还不够？

工具名只证明发生过调用，不证明调用成功、不证明返回属于当前用户/订单，也不证明答案中的值
与返回值相同。必须验证 success、authority、matched、对象、字段和值。

### 为什么要 `pass^k`？

单次通过会掩盖随机失败。`pass^k` 要求同一 case 的 k 次都通过，适合观察可靠性；但它仍不
证明答案语义正确，所以必须与人工质量分开。

### 为什么自动 hard gate 通过，仍有 RAG 失败？

本次 post-hoc k=3 探索 runner hard gate（`releaseGateEligible=false`）重点保护六个 critical
写流程以及 terminal/state/idempotency/safety；总体 25 条中仍有 5 个 RAG-policy case 未达到
pass³。gate 的分母和策略必须展开，不能只报一个绿色结果。

### 为什么接受 fail-closed 假阴性？

订单、退款、支付、库存属于高风险事实，错误放行的代价高于一次澄清或转人工。开放文本部分再
用人工评审补足，而不是降低安全 gate。

### 项目最大的失败教训是什么？

自动 task success 不等于人工答案正确；工具调用不等于事实成立；已见集高分不等于 unseen；
目录名不等于 reviewer 身份。每个结论都必须回到 manifest、authority 和分母。
