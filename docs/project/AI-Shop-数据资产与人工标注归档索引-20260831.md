## 5. 已发现但不能原地改写的治理问题

### 5.1 历史 blank-package 封套异常

`reviews/a2-v5-semantic-20260830/PACKAGE-SHA256SUMS` 中一份 reviewer blank zip 与封套声明
不一致。两个 reviewer 的 sealed 表、comparison、adjudication 和 final SHA 均仍有效，所以最终
人工结论不受影响。

不可原地重写历史封套。若要修复，只能新增 versioned receipt/envelope，说明旧包现状、当前
实际 hash、影响范围和 successor；这属于 custody 变化，需用户批准。

### 5.2 Git 内“0444 即不可变”不可持续

中央 evidence checker 当前还有多类失败：声明 immutable 的 tracked 文件在 checkout 后为
`0644`、部分 ignored visibleRuns 缺失、受保护的根目录 tracked 删除造成链接/claim 缺失，以及
旧路径漂移。Git 不保存普通文件的只读位，因此把 `0444` 当 Git 资产硬完整性条件会反复失败。

推荐长期口径：

- Git 内资产：SHA/manifest 是硬完整性约束，文件权限只告警。
- 外置 custody 的目标策略：SHA + `0700/0600`（final 可再设 `0444`）同时为硬约束。当前敏感
  叶目录多为 `0700`、文件多为 `0600/0444`，但 custody 根和若干一级目录仍为 `0755`，尚待
  用户决定是否统一收紧；不能写成当前已全部满足。
- 不为让 checker 变绿而恢复用户删除、伪造 visibleRuns 或重写历史证据。

改变该策略属于证据治理路线选择，需用户批准。

## 6. 安全整理规则

- 任何人审文件先验证 schema、来源绑定、labels 完整性和 reviewerId，再看目录名。
- 原始回传只进入 `returned/`；sealed、comparison、adjudication、final 必须新建，不覆盖来源。
- 外部模型运行必须标 `EXPLORATORY_NON_GATE`，并保留 source commit、dataset/candidate hash、
  runner verify、正式哨兵和权限结果。
- `.env`、token、runtime.env、日志、PID、cookie 和私有正文不得进入 Git 或聊天。
- Text2SQL 的 tracked/untracked 历史证据均继续原地冻结。
- 根目录历史 intake 已按用户授权删除；恢复时只能从 custody `returned/` 复制，不从旧目录名
  猜 reviewer 身份。

以后根目录收到人工标注时默认执行同一流程：

1. 以 manifest reviewerId/source hash 识别身份，不信目录名。
2. 校验 schema、不可编辑投影、labels、负向 comment 和独立声明。
3. 先原子复制到 `returned/`，权限收紧为 `0700/0600`，并新增外层 `SHA256SUMS`。
4. 从 returned 生成 sealed；A/B compare 后，零分歧直接 final，有分歧只生成 pending 和第三人包。
5. 根目录副本只有在 returned/sealed/pending 或 final 全部验证后才删除，并新增 cleanup receipt。
6. 全程不输出私有 query、answer、caseId、snippet 或 comment，不覆盖历史 manifest/package。
