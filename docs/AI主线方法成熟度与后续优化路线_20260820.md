# AI 主线方法成熟度与后续优化路线（v9 current）

> 本文基于源码、配置、数据库表、运行入口和 v9 证据包判断方法成熟度；旧说明和旧运行只作为历史线索。
>
> 当前发布：`release-20260822-ai-quality-v9`；Python 评测使用 Conda `shop` 环境。

## 1. 结论先行

AI_Shop 的两条 AI 业务主线采用的是成熟的“受控检索 + 证据回答 + 权威交易执行”架构，而不是让模型直接生成商品事实或订单写操作：

```text
自然语言需求
  -> 结构化任务与硬约束
  -> BM25 + 向量并行召回
  -> RRF/rerank
  -> Java 商品/库存/报价快照
  -> 硬约束过滤与 slate 排序
  -> 候选集内解释
  -> 用户确认
  -> Java 权威写入、幂等与终态校验
```

对于当前 47 商品目录和动态库存/报价，这条路径比纯向量或 LLM 直接生成商品 ID 更容易审计，也更符合电商系统将搜索、交易
事实和模型解释分层的工程实践。v9 的 Search/RAG/Agent final（`50/50/25`）和 Agent `pass^8=1.0` 证明冻结数据上的闭环门禁通过，
但项目仍不能称为工业级个性化推荐平台：缺少足量行为序列、曝光偏差校正、训练型 ranker、线上实验、生产压测和真实转化数据。

## 2. 真实代码边界

### 2.1 AI 推荐导购

源码中的实际链路包含任务理解、受控 query expansion、BM25/向量召回、RRF、rerank、Java offer snapshot、硬约束过滤、slate 排序和
候选集内解释。预算、品牌、排除词、品类和库存不是由模型自由决定，而是由结构化计划和 Java 快照再次校验。推荐归因事件接口存在，
但没有真实用户量和因果实验，不能写成 CTR、加购率、CVR 或 GMV 已提升。

### 2.2 可信 RAG

FAQ exact path、查询规范化、BM25/向量混合、RRF、版本/分类/有效期过滤、rerank、evidence gate、最小充分证据、引用和 bounded repair
形成生产路径。事实来自 canonical knowledge/fact metadata；证据不足、过期、矛盾或被污染时可以拒答/隔离。lexical、fact ID、citation 和
grounded faithfulness 是审计下界，不能替代独立人工语义校准。

### 2.3 受控 Agent

supervisor + specialist、intent allowlist、有限轮次/Token budget、只读查询与写提案分离、确认后 Java 执行、Episode/step 持久化、lease/
retry/deadline/idempotency 和终态校验形成了接近 tau-bench 思路的业务 Agent。v9 final 的 25 个任务 x 8 trial 全部通过，关键取消提案/
确认流程无重复副作用；这仍是声明任务集证据，不是开放世界成功率。

## 3. 与主流搜推范式的对比

| 范式 | 候选/事实来源 | 优势 | 主要风险 | 对 AI_Shop 的结论 |
|---|---|---|---|---|
| 关键词/BM25 | 倒排、字段、过滤 | 型号、数字、品牌和否定精确 | 口语同义泛化弱 | 必须保留作精确底座 |
| 纯向量 | embedding 近邻 | 同义表达和语义泛化 | 数字、否定、专名和 OOD 易错 | 并行召回，不独占交易决策 |
| 工业混合搜索 | 多路召回 -> rerank -> filter | 兼顾精确和语义，便于分层评测 | 需要 qrel、索引治理、延迟预算 | 当前主链合理 |
| 传统推荐 | CF、two-tower、DIN/DeepFM、LambdaMART | 利用长期行为优化排序 | 冷启动、偏差、训练和 A/B 成本 | 需真实行为后再引入 |
| 生成式检索 | LLM/semantic ID 生成 item | 统一理解，研究有吸引力 | ID 幻觉、标识歧义、时变库存耦合 | 只做离线 ablation，不替代 allowlist |
| 生成式导购 | LLM 澄清、比较、解释 | 交互自然，可解释 | 幻觉、引用、成本、越权 | 适合叠加在受控候选集 |
| Agentic commerce | discovery -> checkout -> order management | 可以跨步骤完成任务 | 授权、责任、幂等和生态协议 | 当前确认 + Java 终态是稳妥起点 |

### 为什么不让 LLM 直接生成商品 ID

商品语义匹配、候选合法性和动态交易事实是三个不同问题。模型即使生成了看似正确的 ID，也不能证明 SKU 在售、库存足够、报价有效或
用户券可用；直接生成还会把幻觉变成可执行交易。当前“候选集内生成理由 + Java snapshot 校验”保留 BM25 的型号优势，也把写入责任留在
可审计服务。

### 何时值得引入生成式搜推

需要先积累稳定 item identifier、足量曝光/点击/购买序列、hard negative、离线 catalog 版本、独立 serving 和离线对照指标。即使语义
ID 实验有效，线上交易仍要回到 item allowlist、库存/报价快照和幂等 checkout。当前高性价比生成式能力是 query expansion、澄清问题、候选
比较和 grounded explanation。

## 4. v9 质量证据对方法判断的支持

| 能力 | 方法成熟度 | 当前实现/证据 | 仍缺什么 |
|---|---|---|---|
| 传统商品检索 | 高 | 真实目录、混合召回、7 类 Search slice、硬约束 0 违规 | 更大目录、线上流量和规模曲线 |
| 混合检索 + RRF | 高 | BM25/向量/RRF/rerank 与 qrel | 权重、窗口和成本-延迟对照 |
| 硬约束与事实门 | 高且必要 | Java snapshot、metamorphic、v9 zero violation | 更多属性缺失、库存波动 slice |
| slate 多样性 | 中高 | slate-level 排序和单测 | taxonomy、xQuAD/DPP 对照、长期指标 |
| 个性化推荐 | 工业方法成熟 | profile/归因接口存在 | 行为序列、偏差校正、训练 ranker、A/B |
| 可信 RAG | 高 | lexical/fact/citation gate，semantic shadow `50/50` 可追溯 | 人工校准、更多时间/矛盾样本 |
| 业务 Agent | 高但难 | Episode、Java 终态、`200/200` trials、state diff、fault matrix | 更长多轮、并发、真实用户和支付授权 |
| 评测/发布 | 方法成熟 | v3 suite、slice、Wilson/bootstrap、repeat、fault、usage、archive | 人工盲评、压测、长期趋势和成本价格表 |

“高”描述行业方法成熟度，不表示本项目达到同等规模；“中/中高”只描述当前可复核实现。

## 5. 已实施优化及有效性

| 优化 | 解决问题 | 当前证据 | 不能外推 |
|---|---|---|---|
| 统一排除词/品类硬门 | fallback 绕过过滤 | visible/final slice 与变形检查通过 | 线上点击收益 |
| slate-level MMR | 用 recall rank 冒充多样性 | 单测和候选排序证据 | 长期公平/多样性 |
| 批量 offer/feature 访问 | 候选逐项 N+1 | 隔离 MySQL 1/10/50/100，batch 恒 1 round trip | 生产吞吐/SLO |
| provider timeout/partial/deadline | 单路故障拖垮全链 | 12 场景 recovery contract | 未覆盖的开放世界故障 |
| 确认 + Java authoritative write | 模型越权写入 | Agent state diff、幂等、重复副作用 0 | 支付合规和跨商户授权 |
| v3 评测与证据生命周期 | 旧分母、旧数据、无 trace | v9 current/archive/hash/lifecycle 全校验 | 人工真值和真实用户收益 |

这些结果证明工程约束有效，不等于“质量提升了某个线上百分比”。同一冻结数据、Provider、预算和统计方法下的对照实验才可以支持改进幅度。

## 6. 后续自动化路线

### P0：保持当前主线

1. 每次代码、模型、索引或知识变更先跑 visible development/regression 全切片，再跑 Agent `pass^5` nightly。
2. 保持 lexical/fact/citation 硬门禁和 semantic shadow 并列；对 disagreement 生成 bad-case replay，不把 judge 变成硬真值。
3. 保持故障矩阵、usage unknown、DB batch benchmark 和 archive/current hash 校验，禁止静默 fallback 或费用归零。
4. 继续补充精确型号、数字、否定、时间版本、矛盾证据、重复确认和远程未知结果 case。

### P1：自动收益高

1. 建立固定的 candidate recall -> rerank -> hard-filter ablation，报告每个 slice 的质量/延迟/Provider 成本，而不是只报总平均。
2. 增加 catalog mutation replay：价格、库存、券和版本在检索与执行之间变化时，验证快照失效和重新确认路径。
3. 增加并发 Agent repeat：相同幂等键、不同 request ID、lease 失效、worker 重启和 MQ redelivery 的终态 diff。
4. 给 semantic judge 建立少量独立人工盲评校准集，报告 judge-human agreement、abstain 和覆盖，不把校准集回灌 final。
5. 建立趋势表：每个 release 的 slice failure、state diff mismatch、duplicate side effect、provider recovery、usage missing 和 DB round trips。

### P2：暂不抢主线

端到端生成式检索、复杂协同过滤、在线 RL、跨商户自动支付、生产级个性化和大规模压测都需要新的数据、权限或基础设施；在真实行为和
授权条件到位前，它们只应作为离线研究，不替代当前受控主链。

## 7. 需要人工或外部条件的证据

- 独立人工盲评和 semantic judge 校准；
- 真实曝光/点击/加购/购买序列、偏差校正和线上 A/B 或 interleaving；
- 生产容量、并发、长时间稳定性、灾备和成本预算；
- 支付授权、退款责任、隐私和合规审计；
- 更大且版本化的商品目录、库存波动和跨商户协议。

这些工作不能由本地 synthetic/final case 自动替代，也不能从 v9 点估计推断。

## 8. 调研来源与证据等级

方法判断参考了可复核的公开资料：

- [TREC QA guidelines](https://trec.nist.gov/data/qa/2005_qadata/qa.05.guidelines.html)：评测集、判定和可复核报告纪律；
- [RAGAS](https://arxiv.org/abs/2309.15217) 与 [RAGChecker](https://arxiv.org/abs/2408.08067)：RAG 检索、claim 和 faithfulness 分层；
- [tau-bench](https://arxiv.org/abs/2406.12045)：真实 API、业务规则和最终状态驱动的 Agent 评测；
- [NIST Wilson interval](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)：小样本二项比例区间。

论文和公开 benchmark 只能说明方法成熟度，不能替代本项目的源码、Provider trace、Java state diff 或真实用户证据。

## 9. 面试表达边界

推荐表述：“我把 LLM 放在需求理解、澄清和候选集解释层，用 BM25/向量混合召回和 Java offer snapshot 保证商品事实；Agent 写操作先提案、
用户确认，再由 Java 幂等执行，并用 state diff、pass^k 和故障矩阵做发布门禁。”

不要表述为：“已经有工业级个性化推荐、线上 CTR/CVR/GMV、生产 SLO、人工语义准确率或支付合规证明。”
