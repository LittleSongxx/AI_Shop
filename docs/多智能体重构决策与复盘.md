# 多智能体重构决策与复盘

本文只记录已经由源码、测试、迁移脚本或运行日志支持的事实，不把本地演示数据包装成生产流量、GMV、压测或 SLO 结论。

当前统一证据入口为 [AI应用求职项目证据总览.md](AI应用求职项目证据总览.md)，机器口径见 [evidence-manifest.json](evidence-manifest.json)。

## 基线与主线

- 时间、分支与 commit：2026-08-08，`feat/multi-agent-harness`，基于 `feat/ai-app-agent-quality` 的 HEAD。
- 业务现象：原图只有一个 `agent_loop`，LLM 绑定全量 MCP 工具，无法从运行模型上说明“专家负责什么、权限边界是什么”。
- 初始错误假设：增加几个 prompt 名称就等于多智能体。
- 证据链：`app/graph/builder.py` 原先只有 `agent_loop` 与 `tools`；`build_mcp_tools()` 原先不接收权限范围；旧 `agent_run.message_id` 有唯一索引。
- 根因：没有 Agent Registry、handoff contract、父子 Run 和策略校验，所谓专家无法被独立评测。
- 修复方案：Supervisor 根据已解析意图创建最小 `HandoffEnvelope`，专家使用静态 allowlist 和最多 2 轮预算，产出 `AgentArtifact`，最终由 Supervisor finalize。
- 取舍与未采用方案：不拆 Python 服务、不引入 A2A、不做自由群聊 swarm；保持同一 LangGraph 服务和 legacy fallback。
- 测试与运行验证：Harness contract、路由、权限和 SQL Guard 单元测试；现有基线测试继续运行。
- 残余风险：真实 LLM 专家效果、生产数据库只读账号和跨库 VIEW 权限仍需部署环境验证。
- 60 秒面试复述：我把单 Agent 改成“Supervisor + 三个 bounded specialist”。交接只带摘要和已验证上下文，工具权限在 LLM bind 和执行节点双重校验，专家只返回 artifact，根 Run 和子 Run 通过 handoff 可观测；开关关闭时完全走旧路径。

## 工具范围与 fallback

当前专家工具 scope 由 `registry.py` 固定声明，`tools_node` 再次拒绝越权工具。专家 LLM 异常时记录 `SPECIALIST_FALLBACK` 并切回 Supervisor 的 legacy loop，避免静默成功；专家不直接调用客户端流式接口。

## Run 唯一约束

根 Run 继续携带 `message_id`，专家 Run 的 `message_id` 为空，使用 `parent_run_id` 与 `handoff_id` 关联。MySQL 唯一索引允许多个 NULL，因此不需要删除旧索引或修改业务表。

## RAG 定位

RAG 保留原有证据门禁和来源引用，作为共享 `KnowledgeGrounding` 能力出现在允许该能力的专家工具 scope 中，而不是再创建一个重复检索 Agent。

## DataAnalyst SQL Guard

DataAnalyst 只接受三个语义 VIEW，执行前检查单条 SELECT、LIMIT、时间窗口、列数、系统表和 DML/DDL；随后 EXPLAIN，再使用超时和只读查询。`sqlglot` 是正式 AST 依赖，本地缺依赖时只允许简单 allowlist SELECT 兜底并返回可观测警告。

## 管理端身份与降级

Java `/admin/agentMessage/dataAnalyst/ask` 从认证会话派生 `adminId`，不信任浏览器字段，再通过内部 Token 调 Python。空数据、超时、数据库异常分别返回结构化状态，前端显示 SQL、Run ID、结果和告警。

## 2026-08-12：如何证明多 Agent 的取舍

单元测试和 Trace 能证明“隔离存在”，但不能回答“多 Agent 是否比单 Agent 更好”。本轮新增独立进程消融 Runner：

- 主实验固定同一 27 条 Commerce 数据、确定性上下文、工具接口和预算，比较 legacy single-agent 与 multi-agent。
- 次实验只在适用的 21 条确定性子集比较 multi-agent 与 workflow，避免让 workflow 承担开放式商业排序或专家协作问题。
- 每个变体由新进程启动，进程缓存不跨实验复用；输出配对成功率差、bootstrap 置信区间、延迟差和严重安全违规。
- 当前确定性实跑的两个成功率差值均为 0、严重安全违规为 0。该结果只能说明这些锁定 case 上没有功能退化，不能证明真实模型下质量更高或成本更低。
- 本轮没有显式接受消融性能 baseline，因此 stub 的 P95/P99 毫秒值不用于求职叙事。真实模型、token 和每成功任务成本仍需 online workflow 才能回答。

## 2026-08-12：管理身份与试用证据升级

旧设计中的内部 Token 只回答“请求来自受信服务”，不能回答“是哪位管理员、具有什么权限”。当前链路升级为数据库五角色 RBAC，Redis 会话保存主体版本；Java 调 Python 时用 HMAC-SHA256 管理员断言覆盖 method、path、body hash、管理员、角色、权限、时间戳和 nonce。Python 接口不再相信裸 `adminId` 或浏览器传入角色，并对过期、篡改、重放和 previous key 轮换做定向测试。

试用指标也不再从普通用户流量自动抽取。只有显式进入 pilot batch 的 run/outcome 才标记 `SYNTHETIC`、`LOCAL_PILOT` 或 `REAL_USER`；匿名导出使用批次内伪名，小于 5 个样本的细分被抑制，没有真实用户时固定显示“未采集”。这使多 Agent 的产品效果讨论有了正确的数据入口，但当前仓库仍没有可声称的 REAL_USER 结果。

## 2026-08-13：Search/RAG 消融对 Agent 叙事的约束

本轮成熟评测给出了一个对多 Agent 设计同样适用的结论：组件更多不等于质量必然更高。中文 Search 中，结构化过滤相对 RRF 的 NDCG@5 增益为 0.2346，95% CI [0.1858, 0.2835]；过滤后 Rerank 再增加 0.0855，95% CI [0.0497, 0.1248]。WANDS 外部 judged-pool 上，Rerank 的 NDCG@5 增益为 0.0471，95% CI [0.0184, 0.0766]，但 Recall@5 的 CI 跨 0。相反，当前查询归一化在中文集上显著退化，RAG Rerank 对 RRF 也没有统计支持的排名增益。

因此，项目叙事不再使用“多一步模型调用就更智能”。Search/RAG 只保留有任务边界、可配对评测和安全/成本理由的组件；多 Agent 也继续只在职责隔离、并行或独立审查时启用。当前真实模型在线 Agent 消融仍未采集，不能用 Search/RAG 的局部组件收益替代多 Agent 效果证明。

## 当前面试结论

多 Agent 是本项目的一个受约束执行策略，不是项目价值本身。能被证据支持的结论是：上下文和工具权限已隔离，写操作保持 root-only，失败可回退，确定性锁定 case 没有退化。尚不能支持的结论是：真实模型准确率显著提升、成本下降、P95 改善或线上业务 uplift。
