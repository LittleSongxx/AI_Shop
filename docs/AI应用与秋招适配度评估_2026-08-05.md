## 0. 结论先行

AI_Shop 的 AI 部分已经超过“给电商系统接一个聊天模型”的课程项目形态。它形成了从意图识别、异步任务账本、RabbitMQ 分级调度、LangGraph ReAct、RAG/MCP 工具调用、写操作确认、人工客服接管，到 WebSocket 输出和 badcase 回流的一条较完整链路；Java 微服务与 Python Agent 的边界也比较清晰。

但它目前仍是**工程完成度较高、生产证据不足的校招项目**，不是已经证明业务收益的生产 AI 系统。最准确的定位是：

- AI 应用开发 / LLM Agent 工程方向：**较强适配，约 80/100**。
- Java/Python AI 业务集成方向：**强适配，约 84/100**。
- Agent Infra / Harness 初级岗位：**中上适配，约 76/100**。
- RAG / 智能客服应用方向：**中上适配，约 73/100**。
- 搜索推荐工程方向：**基础适配，约 57/100**。
- 大模型预训练、后训练或强算法搜推岗：**不宜作为主投方向，约 37/100**。

这里的分数是“项目与岗位能力模型的匹配度”，不是录用概率，也不包含学历、实习、论文、竞赛、算法题和面试表达等因素。

项目最有竞争力的部分不是“用了 LangGraph、RAG、MCP”这些名词，而是以下可解释、可追问的工程闭环：

1. `agent_message + agent_task` 持久任务账本、RabbitMQ 分级队列、租约和恢复扫描组成的异步执行链。
2. 高风险写操作不由模型直接执行，而是先生成服务端提案，再经用户确认、持久幂等账本和领域状态对账。
3. RAG 同时包含 BM25、向量召回、RRF、Cross-encoder rerank、证据门控、引用与知识发布目录。
4. AI 转人工客服已经打通用户端、管理端、数据库和 WebSocket，而不仅是一个“转人工”按钮。
5. 自动化测试覆盖面较大，并且已有浏览器级真实链路证据。

当前最影响秋招可信度的缺口也很明确：

1. 人工客服回复能到达用户 WebSocket，但当前页面不会追加新消息；这是浏览器 E2E 已证实的用户可见缺陷。
2. `activate -> reply` 在同一秒内可能因 MySQL changed rows 为 0 被误判为会话冲突；这也是 E2E 已证实的问题。
3. RAG 黄金集仍使用占位相关文档 ID，当前 Recall/MRR 为 0 没有评价意义；另有真实抽样发现误拒答和误召回。
4. 用户端没有展示已有的 `sourceRefs`，因此“可溯源”停留在后端数据层。
5. 推荐仍是启发式规则与在线查询组合，没有有效标注集、训练模型、完整成交归因或线上 uplift。
6. 没有生产流量、SLO、CSAT、CTR/CVR/GMV、成本收益或故障演练证据，不能以“企业级”“生产验证”包装。

综合看，当前项目足以成为 AI 应用开发校招的主项目，但需要在投递前把**客服实时缺陷、RAG 有效评测、引用展示、成本/时延基线和搜推归因**补齐。若继续堆叠更多框架或模型名，边际收益会低于修复这些可验证缺口。

## 2. 真实系统形态

### 2.1 AI 主链路

当前 Agent 的主路径可以还原为：

```text
用户端 Vue
  -> Java Gateway / 登录态
  -> Python FastAPI Agent
       -> 输入注入检测、敏感词、限流
       -> 规则 + LLM 混合意图识别
       -> agent_message + agent_task 持久化
       -> RabbitMQ 分级队列
  -> Python Worker
       -> 二次意图精判
       -> LangGraph ReAct
       -> 固定 RAG 预取 / MCP 工具
       -> Java 内部业务 API
       -> MySQL 状态终结
       -> Redis Pub/Sub
  -> WebSocket
  -> 用户端文本、商品卡、订单卡或确认卡
```

这条链路的工程意义在于：HTTP 请求不承担完整模型执行；消息和任务先落事实账本，再进入可确认、可重试、可恢复的异步执行。相比在 Controller 中直接 `await llm.invoke()`，它更接近大厂 Agent 岗位 JD 中反复出现的 Runtime、Durable Execution、Tracing 和失败恢复问题。

核心代码入口包括：

- `AI_Shop-backend/AI_Shop-agent/app/services/agent_service.py`
- `AI_Shop-backend/AI_Shop-agent/app/worker.py`
- `AI_Shop-backend/AI_Shop-agent/app/graph/nodes.py`
- `AI_Shop-backend/AI_Shop-agent/app/services/agent_runtime.py`
- `AI_Shop-backend/AI_Shop-agent/app/domain/intent/classifier.py`
- `AI_Shop-backend/AI_Shop-agent/app/services/mcp_tool_router.py`
- `AI_Shop-backend/AI_Shop-agent/app/harness/guardrails/input_guard.py`
- `AI_Shop-backend/AI_Shop-agent/app/harness/guardrails/output_guard.py`

### 2.2 不能混为一谈的四条能力线

项目中的“AI”实际由四种不同技术问题组成：

| 能力线 | 核心问题 | 当前实现性质 |
|---|---|---|
| 智能客服 / Agent | 意图、对话、工具选择、风险控制、异步执行 | 完整度较高的 AI 应用工程 |
| RAG / 知识运营 | 检索、重排、证据、发布、评测 | 代码链完整，质量门禁仍不有效 |
| 智能导购 | 查询理解、商品召回、约束、解释和卡片交互 | 可运行的混合检索应用 |
| 搜索推荐 | 召回、排序、个性化、归因和实验 | 启发式工程原型，不是成熟算法系统 |

面试时应分别讲设计目标和评价指标，不能用“Agent + RAG + 推荐”一句话概括。大厂面试的追问通常会立刻拆到工具准确率、RAG Recall/MRR、推荐 NDCG/CTR、成本和任务成功率等不同指标。

## 3. AI 智能客服与 Agent

### 3.1 意图识别与对话决策

`IntentKind` 当前有 20 个枚举值，其中 19 个是业务/服务意图，另一个是通用 `CHAT`。覆盖商品咨询、商品搜索、订单、退款、取消订单、确认收货、物流、优惠券、评价/追评、投诉、转人工、支付异常、破损错发、发票、地址修改、退款状态和未知售后等场景。

输出不只是单个 label，还包含：

- `confidence`
- `entities`
- `sentiment`
- `urgency`
- `risk_level`
- `next_action`
- `handoff_reason`
- `source`

这是一个合理的客服决策对象，能够支持排队优先级、工具路由和人工转接，而不是仅把分类结果写进日志。

成熟点：

- 规则与 LLM 混合，模型异常时有规则回退。
- Worker 会二次判别，避免只信入口的粗分类。
- 多轮上下文会保留上轮意图和实体，而不是每轮从零猜测。
- 冻结会话评测覆盖意图、工具选择/参数、写操作策略、转人工、Prompt 注入、身份覆盖和 tool `userId` mismatch，结果为 120/120。

边界：

- 结构化意图结果仍依赖模型生成自由 JSON 后解析，不是模型提供方级别的 JSON Schema 强约束。
- 120/120 是确定性冻结 harness 的结果，适合做回归门禁，不能写成“线上意图准确率 100%”。
- 没有基于真实客服会话标注的混淆矩阵、分意图 Precision/Recall 或低置信度校准曲线。

结论：意图模块作为校招项目有充分的设计与测试深度，但仍缺真实数据分布下的统计评价。

### 3.2 ReAct 与工具体系

项目通过 LangGraph 执行多轮 ReAct，默认最多 5 轮，并带模型 fallback。当前工具策略表包含 11 个业务工具：

| 类型 | 工具 |
|---|---|
| 只读 | `SEARCH_PRODUCTS` |
| 只读 | `QUERY_ORDERS` |
| 只读 | `GET_PRODUCT_DETAIL` |
| 只读 | `QUERY_LOGISTICS` |
| 只读 | `QUERY_COMMENT` |
| 只读 | `QUERY_USER_COUPONS` |
| 只读 | `SEARCH_KNOWLEDGE` |
| 写提案 | `PROPOSE_REFUND` |
| 写提案 | `PROPOSE_CONFIRM_RECEIPT` |
| 写提案 | `PROPOSE_PRODUCT_REVIEW` |
| 写提案 | `PROPOSE_RECOMMENT` |

值得肯定的不是工具数量，而是工具有统一风险策略、身份覆盖防护和输出防伪；四个写工具只创建提案，模型不能直接制造成功结果。

需要准确说明两个默认配置边界：

- `force_mcp_on_llm_skip=False`。虽然 Prompt 要求事实问题先查工具，但某些路径仍依赖模型主动发起工具调用，不能声称“所有事实回答都由系统强制工具取数”。
- `agentic_rag=False`。默认是图节点固定预取 RAG；`SEARCH_KNOWLEDGE` 的 Agentic 路径代码存在，但不是当前主路径，不能包装成“完整 Agentic RAG”。

从岗位匹配看，这部分已经能回答 Tool Calling、ReAct、Function Calling、工具风险分级、模型跳过工具、循环上限和 fallback 等常见问题。弱项是缺少 provider schema enforcement、沙箱化通用执行环境和系统性的工具失败注入结果。

### 3.3 异步 Runtime 与可靠性

Agent 并不是仅靠 RabbitMQ “异步一下”。当前代码包含：

- `agent_message` 和 `agent_task` 的持久事实账本。
- RabbitMQ durable queue、publisher confirm、三级优先队列和 DLQ。
- Worker 租约续期、恢复扫描、指数退避和用户级串行锁。
- Redis Pub/Sub 向 WebSocket 分发状态与输出。
- Prometheus 指标、OpenTelemetry、trace 信息、反馈和 badcase 回流。

这与字节、腾讯、美团等岗位中对 Runtime、Durable Execution、AgentOps、Tracing、回放和 badcase 归因的要求有明显交集。

不过，当前证据尚未覆盖：

- Worker 在工具执行中被 `kill -9` 后的真实恢复。
- RabbitMQ 重投、重复投递和 DLQ 回放的端到端实验。
- Redis 短时故障期间的流式降级和恢复。
- 下游 Java 服务超时、返回不确定结果时的系统化混沌测试。
- 多实例压力下的租约竞争、吞吐、P95/P99 和队头阻塞。

因此可写“实现租约恢复和重试机制”，不可写“已验证高可用”“确保 exactly-once”或“支持高并发生产流量”。

### 3.4 Guardrails 与安全边界

当前可从代码和冻结评测确认：

- 输入侧有 Prompt 注入检测和敏感词处理。
- 工具身份由可信上下文覆盖，测试覆盖用户显式伪造 `userId`。
- 输出侧阻止模型伪造写操作确认卡和业务成功事实。
- Java 内部 API 使用内部服务认证过滤器。
- 写工具与读工具按风险策略分离。

但它不是完整的 Agent 沙箱：

- 工具集合是业务白名单，而不是通用代码执行沙箱。
- 没有文件、网络、命令执行的 capability 隔离问题，因为当前也没有开放这些通用工具。
- 没有系统化红队集、攻击成功率、越权审计报表和生产告警闭环。
- Prompt 注入防护只能降低风险，不能表述为“彻底防御提示词注入”。

## 4. 高风险写操作与幂等

### 4.1 正确的安全模型

退款、确认收货、评价和追评采用两阶段交互：

```text
LLM 选择 PROPOSE_* 工具
  -> 服务端校验用户、订单和动作参数
  -> pending action: PENDING
  -> 用户显式确认
  -> EXECUTING
  -> Java 领域 API，action token 作为 Idempotency-Key
  -> CONFIRMED / FAILED
```

关键实现包括：

- Python `pending_action` 是提案事实源。
- Java `order_request_idempotency` 使用唯一键 `(user_id, command_type, idempotency_key)`。
- `request_hash` 防止同一 key 携带不同参数。
- 四类 Agent 写动作都有持久幂等和契约测试。
- 网络结果不确定时保留 `EXECUTING`，不武断回滚为失败。
- 默认每 300 秒扫描一次超过 600 秒的悬挂动作。
- 对账会同时查看 Java 幂等账本与领域状态。

这是本项目最值得在面试中深入讲的一段，因为它回答了“模型重复调用工具怎么办”“响应丢失时能不能重试”“如何防止用户双击”“为什么不能仅用 Redis 锁”等真实工程问题。

### 4.2 仍然存在的边界

- 如果 Java 幂等记录永久停在 `PROCESSING` 且领域副作用没有发生，当前没有明确的自动失效、人工接管或重新执行策略。
- 同一业务动作可以生成多个新的 action token；现有唯一键保证同 token 幂等，但不是“同订单项同动作”的业务级提案去重。
- Redis graph checkpoint 的恢复粒度是单任务状态，不是跨天、跨会话的长流程 durable workflow。
- 没有真实执行 Worker 崩溃、MQ 重投和网络半开状态下的写操作故障演练。

所以该实现可以称为“at-least-once 环境下通过持久幂等与对账降低重复副作用”，不能称为 exactly-once。

## 5. RAG 与知识运营

### 5.1 真实检索链

当前知识检索不是单一向量库 Top-K，实际链路为：

```text
精确 FAQ
  -> 语义缓存
  -> 多轮指代改写
  -> Query Expansion
  -> BM25 + kNN
  -> 单查询 RRF
  -> 跨查询 RRF
  -> Cross-encoder rerank
  -> 证据阈值过滤
  -> sourceRefs + trace
```

工程能力包括：

- 1024 维 Embedding，配置启动时校验 Embedding 与 ES mapping 维度一致。
- Embedding 缓存、检索语义缓存和外部调用熔断。
- A/B 分桶与参数指纹进入缓存键，减少不同策略结果串用。
- rerank 不可用时回落 RRF。
- 引用信息、检索 trace 和盲评采样。
- Recall@K、MRR、拒答和引用指标评测脚本。
- TXT、MD、PDF、DOCX 上传解析、切片、发布、归档和索引任务。
- FAQ 候选审核、release version 和 active document catalog。
- 管理端知识运营页面。

### 5.2 发布一致性

知识发布通过 release version 和 active document catalog 隔离已发布内容。发布失败残留在 ES 的向量不会因为“物理存在”就自动成为在线证据，检索还要经过目录/version gate。这比直接 upsert 后立即可见更可靠。

但它还不是成熟知识平台的原子发布：

- 没有 shadow index 构建完成后通过 alias 原子切换。
- 文档无法形成不可变 manifest、可浏览的版本历史和一键 rollback。
- 异步 Context Prefix 可能 upsert 覆写同版本向量，完整重放和审计较弱。
- 模型、Prompt、Embedding、rerank 与索引版本没有统一 release manifest。

### 5.3 当前黄金集为什么无效

本轮实际运行现有 `scripts/rag_golden.jsonl` 得到：

```json
{
  "cases": 45,
  "retrievalCases": 35,
  "noAnswerCases": 10,
  "recallAtK": 0.0,
  "mrr": 0.0,
  "topKHitRate": 0.0,
  "answerCitationRate": 0.3714,
  "noAnswerAccuracy": 0.7

```

不能据此下结论“RAG 检索完全失效”。黄金集首行已经明确要求：

> Replace placeholder IDs with IDs from the target knowledge release before live evaluation.

其中 `faq_invoice_apply` 等是占位相关 ID，与当前已发布 FAQ/chunk/document 的真实 ID 不一致。检索可能返回语义正确内容，但 ID 永远无法命中，导致 Recall/MRR 机械归零。

正确结论是：**现有黄金集 ID 已漂移，因此核心检索指标目前不可用；项目有评测框架，但还没有有效质量门禁。** 对秋招而言，这比一个低分更危险，因为候选人无法回答“这次改动到底让检索变好还是变差”。

## 6. 人工客服与工单处理

### 6.1 当前准确定位

当前状态机为：

```text
QUEUED -> ASSIGNED -> ACTIVE -> RESOLVED / CANCELLED
```

已实现：

- AI 或用户发起转人工。
- 管理端客服认领、激活、回复、解决、取消、转回 AI。
- 会话历史、排队时长、首次响应和 SLA 统计。
- badcase 与 FAQ 候选回流。
- 每用户唯一活跃会话约束。
- `claim` 条件更新，避免多客服同时认领。
- `reply` 使用 `SELECT ... FOR UPDATE` 和显式事务。
- Java 管理端从登录态派生管理员身份，再调用 Python 服务。

这是一条完整的“AI 转人工客服会话闭环”，但还不是完整工单平台。缺少的典型工单能力包括：

- 工单类型、产品线、技能组、客服容量和智能路由。
- 自动升级、reopen、转派、协同处理和跨部门流转。
- 内部备注、附件、标签、客户主档和关联订单视图。
- CSAT、结案质检、抽检规则和细粒度 RBAC。

简历应写“AI 转人工客服会话闭环”，不能写“企业级工单平台”。

### 6.2 已证实缺陷一：回复到达但当前页面不显示

浏览器 E2E 完整执行了：

```text
用户 requestHuman
  -> 管理端登录
  -> claim
  -> activate
  -> reply
  -> 用户 WebSocket 收到 support DONE
  -> 当前页面不可见
  -> 刷新后历史可见
  -> resolve
```

观测结果：

```json
{
  "stateAtReply": "ACTIVE",
  "websocketReplyFrames": [
    {"id": "18", "type": 1, "messageType": "support"}
  ],
  "realtimeVisible": false,
  "visibleAfterReload": true,
  "finalState": "RESOLVED"
}
```

根因可以由源码解释：

- 后端 `support_service.py` 回复时插入一个新的 `agent_message`，并把这个新 `messageId` 推送给用户。
- 前端 `AgentChatList.vue` 的 `finishAnswering()` 只查找并更新已有消息；新人工消息不在列表时没有 append 分支。
- 刷新后历史 API 才把新记录加载出来。

这是 `E` 级已证实缺陷，优先级应高于继续增加客服后台功能。

### 6.3 已证实缺陷二：同秒 activate/reply 误报冲突

`reply()` 先正确地 `FOR UPDATE` 读取并校验会话所有权，随后又执行一次把状态设置为 `ACTIVE`、管理员设置为同一值、`updated_at=NOW()` 的 UPDATE，并要求 `cur.rowcount == 1`。

当 `activate()` 与 `reply()` 落在同一秒时，MySQL 秒级时间字段和相同字段值可能使 changed rows 为 0。代码将“匹配但值未变化”误当成“没有匹配或被别人认领”，抛出冲突；实际延迟约 1.2 秒再回复即可成功。

这是使用 changed rows 判断 matched rows 的错误。事务和行锁本身没有解决该语义问题。修复方向应是：锁定后以已读取会话作为所有权事实，避免依赖无变化 UPDATE 的 affected rows，或让 UPDATE 必然改变一个高精度/version 字段并使用乐观锁语义。

### 6.4 尚未证实的精确 FAQ 时序风险

源码存在以下潜在时序：

```text
后端 complete_message -> WebSocket push_done -> HTTP return
前端 await HTTP -> emit sendMessage -> 创建当前消息
```

如果 `FAQ_FAST_PATH` 的 DONE 在 HTTP 返回和前端建消息前到达，理论上可能找不到对应消息。当前尝试的浏览器请求实际都进入 Worker，没有满足 `deliveryState=FAQ_FAST_PATH`，因此不能把它列为已复现缺陷。

正确记录是：**源码时序风险，待用返回值明确为 `FAQ_FAST_PATH` 的精确 FAQ 做复现；目前证据等级只有 `C`，没有 `E`。**

## 7. 智能导购

### 7.1 当前能力

Agent 商品搜索链包括：

- taxonomy/query 规范化。
- 关键词和商品向量双路召回。
- RRF 融合。
- 商品快照补全。
- Cross-encoder rerank。
- 在售、库存、预算和品牌硬约束。
- 推荐理由、相似商品和澄清问题。
- serving 时生成不可伪造的曝光 `requestId`。

本地浏览器真实导购结果：

```json
{
  "messageId": "17",
  "deliveryState": "QUEUED",
  "elapsedMs": 18831,
  "frames": [
    {"id": "17", "type": 1, "biz": "product_search", "len": 756}
  ],
  "productCards": 2
}
```

这证明浏览器 -> RabbitMQ -> Worker -> 模型 -> 商品工具 -> WebSocket DONE -> 商品卡片的真实链路可用。该次商品搜索只观察到最终帧，不能用它证明逐 token 流式输出。

### 7.2 点击归因

同一真实浏览器会话点击导购商品卡，观察到：

```json
{
  "requestObserved": true,
  "requestShape": {
    "method": "POST",
    "hasProductId": true,
    "hasRequestId": true,
    "hasPosition": true
  },
  "httpStatus": 200,
  "businessCode": 200,
  "navigationMatched": true
}
```

它证明“曝光 requestId -> 点击事件 -> 商品详情跳转”闭环，不证明加购、下单、支付或 GMV 归因。

### 7.3 成熟度判断

智能导购作为 AI 应用是成立的：用户自然语言会变成约束化检索，模型必须依赖真实商品工具，结果以业务卡片而非纯文本交付。它比普通聊天机器人更有业务完成度。

不足之处：

- 18.8 秒的单次本地导购时延对于交互偏长，尚无分阶段耗时拆解和优化基线。
- 工具是否必须调用仍部分依赖模型；默认强制工具开关关闭。
- 没有基于真实 query-product 标注的 Recall/NDCG 或商品相关性人工评审。
- 商品搜索最终帧与普通问答逐块流式行为不同，应明确前端等待体验和超时降级。
- 导购与 Java 普通搜索页的检索/推荐逻辑没有统一服务化。

## 8. AI 搜索与推荐

### 8.1 搜索能力

必须区分两套搜索：

- Python Agent 商品搜索：关键词 + 向量召回 + RRF + rerank + 业务硬约束。
- Java 普通搜索页：以 IK/BM25/phrase 为主，并没有共享 Agent 的完整混合检索排序链。

查询理解冻结数据结果：

- keyword accuracy：97/97。
- term coverage：93/93。
- Layer 2 数据集没有 `relevantProductIds`，因此不能计算有效的商品相关性指标。

这说明 query normalization/term extraction 的规则回归较稳，但不能据此声称搜索 Recall、NDCG 或转化提升。

### 8.2 个性化推荐能力

当前 Python 推荐代码包含：

- 浏览历史与购买历史。
- 购买:浏览权重为 2:1。
- 类目偏好召回。
- 最近购买商品的共购召回。
- 多路合并去重。
- 简化 MMR 多样性重排。
- 无个性化信号时热销 fallback。

这足以说明作者理解多路召回、兴趣强弱、去重、多样性和冷启动，但实现仍是启发式策略：

- 没有训练数据、用户/商品特征平台、模型训练、模型注册和 serving 版本。
- 共购在请求时针对有限历史向 Java 查询，存在在线计算和 N+1 风险，不是离线物化 item-item 表。
- MMR 的相关性来自原始名次，相似度仅是“同类目=1、否则=0”，不是 embedding MMR。
- 没有随机线上实验、显著性检验、guardrail metrics 或 uplift。
- Python Agent 与 Java 搜索页是两套逻辑，实验口径与归因容易割裂。
- `requestId` 目前只闭合曝光到点击，没有贯穿加购、订单、支付和退款。

### 8.3 与强搜推岗位的差距

字节、京东、快手、小红书等强搜推岗位的 JD 和面经通常要求：

- 召回、粗排、精排、混排的分层架构。
- CTR/CVR/DeepCVR/LTV 等目标与多任务学习。
- 正负样本构造、特征工程、偏差修正和难负样本。
- HNSW/IVF、向量检索、生成式检索或多模态相关性。
- NDCG、Recall、AUC、GAUC，以及在线 CTR/CVR/GMV。
- A/B 实验、显著性、归因、长期价值和因果问题。

AI_Shop 当前只覆盖其中的召回/融合/简单重排概念和点击事件工程，算法深度与数据闭环明显不足。它可以支撑 AI 导购或搜索应用工程面试，不足以独立支撑“推荐算法工程师”主项目。

7. **业务效果**：客服解决率/转人工率/CSAT，搜索推荐 CTR/CVR/GMV，或其他可量化收益。

算法岗位则在此基础上额外要求训练框架、数据构造、后训练/RL、论文理解或搜推模型。这是 AI 应用工程岗和大模型/搜推算法岗的实质分界。

## 11. 牛客等社区面经旁证

### 11.1 使用限制

牛客内容是候选人自报，无法独立验证面试题是否完整、原话是否准确，也存在幸存者偏差、标题偏差、推广内容和 AI 生成内容。单篇面经不能当作公司的正式招聘标准。

本报告只使用多个岗位样本中重复出现的主题，并用官方 JD 校正方向。社区样本的价值是揭示“JD 里的名词会怎样被追问”。

### 11.2 高频追问

多个 AI 应用、Agent、RAG、后端和搜推面经反复出现：

- 项目是否本人完成，真实指标是什么，最困难的 badcase 是什么。
- 为什么需要 Agent，而不是固定 Workflow 或单次 LLM。
- Context、Memory、Planning、MCP、Skill 与 Tool 的边界。
- 工具失败怎么恢复，重复调用如何避免副作用，怎样防越权。
- Prompt 注入、幻觉、结构化输出和工具参数安全。
- RAG 如何切片，为什么 BM25 + vector，为什么 rerank，topK 怎么定。
- 父子索引、阈值、拒答、数据集、Recall/MRR 和性能如何评价。
- 模型、Prompt、索引如何灰度、降级和回滚。
- token 成本、端到端延迟、模型路由和缓存收益。
- Java/Python 基础、HashMap、线程池、限流、数据库事务和分布式系统。
- 手撕算法。
- 搜推岗的召回、粗排、精排、重排、样本、模型、AUC/NDCG、HNSW/IVF。

对 AI_Shop 而言，前半部分多数已有可讲代码；最容易被追问穿的地方是“有效指标、真实故障、回滚、成本和推荐算法”。

### 14.1 可以写进简历

- 基于 LangGraph ReAct 与 MCP 构建电商客服/导购 Agent，编排 11 个只读或写提案工具，覆盖订单、物流、优惠券、商品检索、RAG 和售后动作。

- 构建 BM25 + kNN + RRF + Cross-encoder rerank 的知识检索链，支持证据门控、引用持久化和知识发布目录。

- 打通 AI 转人工客服的排队、认领、回复、解决和会话历史闭环，并通过真实浏览器验证管理端到用户端链路。

### 14.3 建议的主项目叙事

推荐按问题而不是按框架名展开：

```text
问题：模型执行慢、可能失败，且售后写操作不能直接信任模型。

设计：
1. HTTP 只负责校验、意图粗判和落任务账本；Worker 异步执行。
2. LangGraph 负责多轮工具决策，工具按 READ / PROPOSE 分级。
3. 写动作先生成 pending action，用户确认后以 action token 贯穿 Python 和 Java 幂等账本。
4. 网络结果不确定时保持 EXECUTING，由扫描器查询幂等账本和领域状态对账。
5. Redis/WebSocket 把流式结果送回用户，人工客服可以接管。

验证：
- 390 个 Python 测试、125 个 Java 测试。
- 120 条离线冻结轨迹回归。
- 本地浏览器真实问答、导购和人工客服 E2E。

边界：
- 没有生产流量与 exactly-once 证明。
- 仍需做 Worker/MQ/Redis 故障注入和成本/延迟治理。
```

这个叙事能经受“为什么这样设计、失败时发生什么、证据是什么、还有什么没解决”的连续追问。

## 15. 秋招前整改优先级

### 15.1 两周：先消除演示硬伤

1. 修复人工客服实时消息追加。前端收到 `messageType=support` 且 `messageId` 不存在时创建并 append 消息；增加用户端组件测试和浏览器 E2E。
2. 修复同秒 `activate -> reply` 的 rowcount 误判。以锁后读取的状态/所有权为准，或引入明确 version 更新；增加同事务时序回归测试。
3. 用当前知识 release 的真实 FAQ/chunk/document ID 重建黄金集；将数据集与 release version 绑定，并在 ID 不存在时让评测直接失败而不是输出 0 分。
4. 基于标注查询做阈值扫描，分别报告 Recall@K、MRR、no-answer Precision/Recall、误拒率与误召率。
5. 用户端展示 `sourceRefs`，至少包含来源标题、文档/FAQ 类型和版本；无来源时不伪造引用。
6. 固化一条可重复演示脚本：登录 -> RAG 流式问答 -> 商品导购 -> 点击 -> 写操作确认 -> 转人工 -> 回复。

### 15.2 四周：把“代码能力”变成“可量化能力”

1. 建立 Agent 分阶段延迟：排队、意图、检索、首 token、工具、模型生成、总时延；输出 P50/P95 而不是单次 latency。
2. 记录每请求模型、输入/输出 token、缓存命中、fallback 和估算成本，形成按场景/模型的成本面板。
3. 为模型、System Prompt、工具 schema、知识 release 和检索参数建立统一版本 manifest，支持回放对比与回滚。
4. 让模型意图和工具参数使用 provider 支持的结构化 schema，保留解析失败与修复率指标。
5. 执行 Worker kill、MQ 重投、Redis 短时不可用、Java 超时和响应丢失等故障实验，并记录预期/实际状态迁移。
6. 将导购 `requestId` 贯穿点击、加购、订单、支付和退款，先完成数据契约，不虚构 uplift。
7. 给商品搜索数据集补 `relevantProductIds` 和分级相关性，报告 Recall@K、MRR/NDCG 与硬约束通过率。

### 15.3 八周：针对目标岗位拉开差距

AI 应用 / Agent 方向：

1. 构建轨迹级 eval：意图正确、工具选择正确、参数正确、事实有证据、写操作合规、最终任务完成。
2. 增加模型路由实验，用小模型处理简单意图、强模型处理复杂规划，并比较质量、时延和成本 Pareto 前沿。
3. 为高风险工具增加细粒度授权、审计和人工审批策略；明确业务工具白名单与通用 sandbox 的区别。
4. 将 badcase 从收集推进到标注、聚类、归因、修复、回归和发布门禁。

RAG 方向：

1. 建立不可变知识 release manifest、shadow index 和 alias 原子切换。
2. 对 chunk size、query rewrite、BM25/vector 权重、RRF 和 rerank 做可复现实验。
3. 增加引用正确性、faithfulness、answer completeness 和拒答校准，而不只测 ID 命中。

搜推方向：

1. 离线物化 item-item 共购，消除请求时 N+1，并记录数据窗口、去热门偏差和时间衰减。
2. 建立最小可训练 baseline，例如 item-based CF / LightGBM ranker，并与启发式策略按同一数据集比较。
3. 使用商品 embedding 做真实 MMR 相似度，补多样性、覆盖率和新颖度指标。
4. 若没有真实线上流量，只报告离线指标和实验设计，不伪造 A/B uplift。

## 17. 最终评估

AI_Shop 当前最接近“有分布式业务系统基础的 AI 应用工程项目”。它展示了三类对校招有价值的能力：

1. 能把 LLM 放进真实业务边界，而不是让模型直接操作数据库或伪造结果。
2. 能处理异步、幂等、人工接管、引用、监控和 badcase 等非模型问题。
3. 能同时阅读和连接 Java、Python、Vue、MySQL、Redis、RabbitMQ 与 Elasticsearch。

它距离大厂 AI 应用岗的主要差距，不是再增加一个 Agent 框架，而是把评测、故障、成本、版本和业务指标做实。当前最合理的秋招定位是：

> 以 AI 应用开发 / Agent 工程为主投，以 Java/Python 业务集成为稳定底座，以 RAG/智能客服为场景优势；把搜推作为辅助能力，不冒充训练或强算法项目。

修复两个人工客服 E2E 缺陷、重建有效 RAG 黄金集并展示引用后，项目将达到更稳定的校招主项目状态。完成故障演练、轨迹评测、成本/延迟面板和完整归因后，才更接近 Agent Infra 或成熟 AI 应用岗位对“可靠、可评、可运营”的要求。
