## 3. 客服与实时消息

客服 `claim/activate/reply` 现在先锁定会话行，再根据真实状态和 `assigned_admin` 做决定：同一客服的合法重复请求幂等返回，其他客服越权或结束状态明确失败。业务判断不再依赖 MySQL 对“无变化 UPDATE”的 rowcount 语义。

AI 普通 Worker、FAQ 快路径和人工回复统一为“先落终态、再发 DONE”。WebSocket 发布失败不会回滚数据库事实；历史接口承担恢复。DONE 与历史接口使用相同 `sourceRefs`，Web 引用区可展示 title、heading、snippet、version、source 和 retrieval，只有真实 URL 才出现链接。

Web reducer 将 `messageId` 字符串化后作为唯一聚合键。HTTP 先到、WebSocket 先到、未知人工消息、PARTIAL、空/非空 DONE、ERROR、取消和重复帧都以同一规则收敛；迟到 PARTIAL 不能修改终态，也不能覆盖另一条生成中的回答。

## 5. 工具事实、写操作与观测

意图分类优先使用 provider 的结构化输出；仅在 provider 不支持、schema 校验失败或调用异常时回退文本 JSON。回退仍经过 `IntentDecision` 校验，非法结果落入确定性安全意图。`schema_success/fallback/invalid` 提供可观测分流。

订单、物流、优惠券和写提案具备必需工具检查。模型跳过工具时，forced-tool 节点补齐真实调用；工具失败时给出明确降级，不能让模型凭上下文生成订单状态。

个人订单和售后动作还会先经过 `OrderReferenceResolver`：默认查询本人最近 90 天最多 30 单，显式 ID 仍校验用户归属；状态、时间、商品页指代、taxonomy、品牌、型号和规格共同缩小候选。唯一匹配才进入只读事实工具或 `PROPOSE_*`，多候选保存为 `ORDER_SELECTION`。“刚收到/收到的/收到了”等表达还会约束到已发货、已完成或部分退款状态，破损错漏发意图不会再把待付款、待发货、取消和关闭订单作为候选。候选消费在单个 MySQL 事务内同时创建消息、任务并写 `CONSUMED`，MQ 失败沿现有恢复机制处理；Worker 执行前复核最新业务状态。

写操作的当前契约：

1. `business_key` 标识同一用户、动作和业务资源。
2. `args_fingerprint` 是规范排序 JSON 的 SHA-256。
3. 同业务键同指纹复用 token；指纹不同返回冲突。
4. PENDING/EXECUTING/INCONCLUSIVE/MANUAL_REVIEW 持有活跃唯一键。
5. 未知传输结果只查询 Java 幂等账本和领域状态，绝不重发写操作。
6. 达到次数或时间边界进入 MANUAL_REVIEW，并继续阻止第二次动作。

模型指标增加 `kind/model/fallback`，按配置统计人民币 input/output/total cost；没有模型单价时 token 进入 `unpriced`，不猜成本。阶段时延严格限定为 `queue_wait/intent/rag/first_token/tool/generation/total`，指标 label 不含 query、userId 或 messageId。

以下仍是“项目对岗位能力模型的匹配度”，不是录用概率；外部 JD 和求职样本的时点仍为整改前报告中的 2026-08-05，不把本次源码整改描述成新的市场调研。
