# 客服 v2.1 标签政策双盲重标说明（2026-08-26）

## 任务边界

本任务只重新判断 25 条受标签政策冲突影响的客服输入，不评价模型答案。reviewer-a 与 reviewer-b 必须分别填写自己的 JSONL，全程独立；两份表都封存前，不得查看另一份表、当前 120 条 gold、规则/HTTP 预测、审计中的旧标签或 `adjudication-context.after-sealing.jsonl`。

每行只允许修改 `labels` 和 `comment`。不得改动 `id`、`input`、`reviewerId`、`guidelinesVersion`、顺序或行数；同名 manifest 不得编辑。

```json
{
  "labels": {
    "intent": "PRODUCT_SEARCH",
    "riskLevel": "LOW",
    "shouldHandoff": false,
    "handoffSeverity": null,
    "slots": {}
  },
  "comment": "仅示范格式，不代表任何实际样本答案"
}
```

五项标签要么全部为空，要么全部完成。`shouldHandoff=true` 时 `handoffSeverity` 必须为 `NORMAL` 或 `CRITICAL`；否则必须为 `null`。无槽位时填 `{}`，不能填 `null`。

## Intent 口径

| intent | 判定边界 |
|---|---|
| `ADDRESS_CHANGE` | 修改收货地址、地址簿或下单后的地址变更 |
| `AFTERSALES_UNKNOWN` | 已发生售后问题，但不能归入更具体的破损、错发、退款等类 |
| `CANCEL_ORDER` | 取消订单或询问取消条件/流程 |
| `CHAT` | 不涉及购物任务的闲聊、问候 |
| `COMPLAINT` | 主要诉求是投诉或表达对商品、服务、履约的不满 |
| `CONFIRM_RECEIPT` | 确认收货、签收状态或相关操作 |
| `DAMAGED_OR_WRONG_ITEM` | 破损、错发、漏发、颜色/型号不符等到货异常 |
| `HUMAN_REQUEST` | 主要诉求是明确要求人工客服 |
| `INVOICE` | 发票、抬头、税号、开票状态 |
| `PAYMENT_ISSUE` | 支付失败、重复扣款、异常扣款或支付状态；退款到账进度不在此类 |
| `PRODUCT_CONSULT` | 问参数、材质、适配、场景或比较，但不要求返回候选列表 |
| `PRODUCT_REVIEW` | 创建首次评价，或询问评价入口、规则、内容规范 |
| `PRODUCT_SEARCH` | 查找、筛选、推荐或继续细化商品列表；“换一批、再推荐、按上一批改条件”均在此类 |
| `QUERY_COUPON` | 优惠券领取、使用、门槛、面值、有效期 |
| `QUERY_FULFILLMENT` | 发货、预售、出库和履约时效 |
| `QUERY_LOGISTICS` | 物流轨迹、停滞、运单或配送状态 |
| `QUERY_ORDER` | 查询订单存在性、列表或状态，且没有更具体动作 |
| `RECOMMENT` | 对已识别订单追加追评/二次评价的写提案；绝不表示“重新推荐商品” |
| `REFUND` | 发起退款/退货退款，或询问申请条件和规则 |
| `REFUND_STATUS` | 已申请退款的到账、进度或结果 |

多诉求时按用户最后一个明确、可执行的主要诉求；确有边界冲突时选择最有原文依据的一项，并在 `comment` 写清冲突，不能新增枚举。

## 风险与转人工

- `LOW`：一般咨询、检索、物流/订单查询、优惠券和评价规则。
- `MEDIUM`：普通退款/取消、支付状态、地址修改、售后争议或投诉，需要核验但无立即高后果风险。
- `HIGH`：未授权扣款、欺诈、账户/隐私泄露、设备鼓包发热等人身安全风险，或其他可能立即扩大损害的事件。

明确要求人工、高风险需人工处置、信息不足且继续自动处理可能造成不可逆后果时，`shouldHandoff=true`。`CRITICAL` 只用于正在发生或可能立即扩大的资金、账号/隐私、人身安全风险；普通复杂售后、投诉和普通人工请求用 `NORMAL`。

## Slots v2.1 口径

只抽取用户原话中明确出现且与诉求有关的值，不补后台事实、不规范化改写原文：

- `amount` 保存完整可见原文 span，包括货币符号或“元”；数值归一化只能是下游派生值。
- 明确预算/上限同时写 `budget`，不能因为已有 `amount` 而省略。
- 商品件数才写 `quantity`；“投诉三次、扣款两次”等 occurrence/frequency 不写商品数量。
- `productName` 与 `feature` 使用不重叠 span；例如已把“降噪”写入 `feature` 时，不再在 `productName` 重复同一文字。
- 常用键包括 `orderId`、`orderItemId`、`productId`、`productName`、`brand`、`feature`、`amount`、`budget`、`quantity`、`discount`。
- 没有明确实体时填 `{}`；键和值必须为非空字符串。

## 完成与回传

每位 reviewer 完成全部 25 行后，只回传自己填写的 JSONL 和原 manifest；不要合并 A/B、不要自行算一致率、不要修改导出 hash。对 `false`、高风险或边界案例，建议在 `comment` 用一两句记录原文依据。

项目方收到两份完整表后依次执行：结构与来源校验 → 分别 seal → A/B 比较 → 只导出真实分歧 → 独立第三人仲裁 → 生成新 hash 的 120 条 v2.1 successor。若无分歧，不得伪造仲裁记录。
