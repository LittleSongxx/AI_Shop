Executive Summary

这个项目远超 Demo 水准，但上线前还有几道真实的坎

AI_Shop 在防护架构上的思考已经到了工程级别：输入归一化 + 分档注入检测、通道内容检疫、输出幻觉防护、Redis 多进程安全限流、熔断器、上下文压缩、写操作签名确认 ——这些在绝大多数"Demo 转生产"项目里都是空白，而这里都有具体实现。

但仍有几个真实风险点没有完整闭合：单用户 Token 消耗无硬性上限、逐字/低信息量消息对 LLM pipeline 的穿透、间接提示注入文档的入库时检查、以及 WebSocket 路径的输入验证一致性。这些不是"锦上添花"，是上线后第一周就可能被触发的洞。

已实现 · 输入 / 输出防护

深度防御栈：三层隔离已到位

输入归一化 + 分档注入检测（input_guard.py） 已实现

NFKC 折叠先将全角字符、零宽字符、Unicode 兼容形式统一为 ASCII 等价，再删除 C* 类别控制字符，最后压空白 + 截断到 max_input_chars=4000。这一步让 ｉｇｎｏｒｅ 和 ig​nore（夹零宽字符）都能被后续正则命中。

规则分两档：BLOCKING_RULES（10 条）命中即拒，涵盖指令覆盖、Prompt 泄露、角色劫持、模板注入、防护绕过；SUSPICIOUS_RULES（8 条）弱信号，单独命中只记日志，≥2 类才升级为拒绝——有效压住误伤。

通道内容检疫（channel_guard.py） 已实现

RAG 召回的知识库片段和工具返回结果在进入模型上下文前经过同一张规则表扫描。命中的片段被剔除而非拒答，整体按"无证据"处理——避免被污染文档劫持 LLM 输出，也避免"一个脏文档让整个对话崩溃"。

关键设计：检疫事件写入检索 trace + 观测日志，使"知识库出现被注入文档"可被发现、可定位到具体文档。

Spotlighting：用户输入隔离（prompt_boundary.py） 已实现

用户输入被包裹在 <user_input> 标签中送入模型，系统词中声明标签内是数据而非指令。RAG 知识库片段经 isolate_knowledge_text() 做同样的隔离处理。这是目前最有效的提示注入缓解手段之一。

输出幻觉防护（output_guard.py） 已实现

三类幻觉被主动拦截：

  • FALSE_COMPLETION：没有 PROPOSE_* 工具调用时，声称"退款已成功"等会被替换为澄清文案
  • FALSE_CONFIRM_CARD：声称已生成确认卡片但实际没有 → 重定向到正确流程
  • FALSE_CAPABILITY：声称"帮你下单"等不具备的能力 → 追加免责提示

同时剥离 Emoji（避免模型通过 Emoji 编码绕过文本过滤）和内嵌的产品 JSON 片段。

写操作签名确认 + 工具白名单（tool_guard.py） 已实现

所有写操作走 PROPOSE_* → 服务端生成 actionToken（加密签名）→ 用户点击确认 → 服务端校验归属 的两步确认流程。模型无论输出什么文本都无法直接触发写操作，Token 由服务端签发且绑定 user_id。工具白名单静态定义，不由对话内容决定。

数据分析 SQL 防护（sql_guard.py） 已实现

Admin DataAnalyst 模块使用 sqlglot AST 解析，强制：仅 SELECT、禁 JOIN/子查询/OR/变量/锁、仅允许视图白名单、函数白名单、LIMIT 强制、列名白名单、日期窗口强制且最大 90 天。这层防护使 LLM 生成的 SQL 无法泄露敏感表或执行危险函数。

已实现 · Java 后端基础设施

分布式系统核心模式已正确实现

分布式事务 + MQ 三层可靠性 已实现

下单路径使用 Seata AT 模式 @GlobalTransactional 保证跨服务一致性。MQ 可靠性通过三层叠加：本地 outbox 表 → TransactionalMqSender（事务提交后发送）→ 补偿扫描任务。支付回调、超时关单、迟到退款三路竞态由 Redis 互斥锁强制串行。

退款 Saga + 优惠券超卖防护 已实现

退款 Saga 含 MANUAL_REVIEW 状态和 CAS 保护的审批恢复，在审核窗口期检测数据漂移后重新校验。秒杀优惠券使用 Redis Lua 原子预扣 + DB 库存双重确认，全生命周期管理。

已实现 · 上下文管理

Token 预算 + 压缩 + 历史裁剪

会话上下文压缩（session_memory_service.py） 已实现

运行时 Token 预算 working_token_budget=16,000，压缩触发阈值 compress_token_threshold=12,000。超阈值时用独立的 Memory LLM 生成会话摘要，再把完整历史替换为摘要 + 最近若干轮。Redis 缓存层（TTL 24小时）+ MySQL 持久层双写，避免 Worker 重启后会话丢失。

历史消息上限 history_message_limit=15，助手历史最大长度 assistant_history_max_len=500，防止上下文随对话轮数二次方膨胀。

ReAct 轮次上限（graph_max_react_rounds=5） 已实现

Agent 图节点在每次进入 agent_loop_node 时检查 react_round，达到上限强制跳转 finalize，避免工具调用链被攻击者或边缘问题驱动成无限循环（Denial-of-Wallet 的一种常见路径）。

已实现 · 可观测性与质量闭环

Episode 追踪 + 影子评审 + Badcase 管线

Episode 服务 + Judge 影子评分 已实现

每次 Agent 运行生成 run_id，关键节点通过 episode_service.record_step() 录入。Judge 服务以 5% 抽样率异步评分（judge_sample_rate=0.05），低于 0.65 分的回答进入 Badcase 候选队列，由人工审核后沉淀为回归测试集。这是"上线后持续变好"而非"上线后慢慢变差"的核心机制。

RAG 语义缓存 + FAQ 快速路径 已实现

语义缓存 TTL 30 分钟，命中按 1% 比例进盲评队列（rag_cache_sample_rate=0.01）——"命中率突降按事故处理，误报率按周评审"的行业建议已内化。FAQ 精确匹配路径有 1.5 秒快速超时，6 小时 TTL。高频重复问题在此层被短路，不进 LLM。

人工转接 + SLA 监控 已实现

用户可主动发起 requestHuman；Agent 检测到意图连续重复（HANDOFF_SUGGESTED）或低置信时主动建议转人工，追加文案"可以回复'转人工'"。Support 队列有 SLA 告警：首响应 support_first_response_sla_seconds=300，队列预警 support_queue_alert_seconds=600。

边缘案例分析 · 01

用户直接粘贴商品网页 HTML 源码

📄 场景：用户复制整个商品页面源码（HTML + JS + CSS）发给客服

现有防护能做什么：max_input_chars=4000 会在归一化后截断超长输入并抛出 ValueError("输入内容不能超过4000个字符")，前端展示为业务错误码 600。一个典型的商品详情页 HTML 源码通常在 50KB~200KB 之间，远超这个上限，因此会被截断。

漏洞在哪里：4000 字符的阈值本身是对的，但有两个细节问题。第一，错误提示不够语义化——用户看到"不能超过4000个字符"时通常会剪短后重发，但 4000 字节的 HTML 片段依然是噪声。第二，template_injection 规则能命中 <system>、<user_input> 等 LLM 特殊标签，但普通的 <div>、<script>、<meta> 不会触发任何规则——如果用户分多次发送 HTML 片段（每次 < 4000 字符），这些片段会逐条进入 LLM，消耗大量 Token 但毫无信息价值。

实际危害：用户通常的真实意图是"帮我看一下这个商品值不值得买"。现有路径下这条问题会触发 PRODUCT_CONSULT 或 PRODUCT_SEARCH 意图，LLM 拿到一段残缺 HTML 尝试解析，大概率产生幻觉或回复"无法处理该格式"，同时消耗 2000-4000 个输入 Token。

✓ 超长输入截断 ✓ LLM 特殊标签拦截 ⚡ 错误提示不语义化 ✗ HTML 内容类型检测 ✗ 分段HTML累计防护
建议补充：内容类型预检 + 引导文案 建议

在 input_guard.inspect() 之后增加一层轻量内容类型判断：检测消息是否以 <html、<!DOCTYPE、<div 等开头，或包含大量 HTML 标签密度（如 </> 字符占比超过 15%），若是则直接返回友好提示："看起来您发送了网页代码，您可以复制商品名称或分享商品链接，我来帮您查找。" 这既降低 Token 消耗，又改善用户体验。

边缘案例分析 · 02

一个字一个字地发送消息

⌨️ 场景：用户依次发送"我"、"要"、"退"、"款" 四条消息

现有防护能做什么：sendMessage 接口限流为 1次/1秒（allow(user_id, "sendMessage", 1, 1)），所以每秒最多 1 条消息。ai_chat_limit=200 是会话总上限。每条消息都会触发 resolve_intent()，对单个字符消息，规则引擎很可能分类为 UNKNOWN 或 CHITCHAT，不进 LLM 的快速路径会直接返回兜底回复。

漏洞在哪里：1次/秒的固定窗口限流对此场景防护不足。如果用户每 1.1 秒发一个字，一分钟可以发 ~54 条单字消息。每条消息都触发：意图分类（可能含 LLM 调用）→ RAG 检索 → 历史消息保存。4000 字 × 200 条消息的会话上限，假设每条是 1 个字，则 200 条消息只有 200 个字符的信息量，但消耗了 200 次 LLM 调用的基础开销（系统词 + 历史 context + 工具 schema），每次至少 2000-3000 Token，总计约 40-60 万 Token。

还有一个更隐性的问题：短消息会不断清洗历史消息窗口（history_message_limit=15），使得真正有意义的上下文被单字消息挤出窗口，导致后续的正常对话质量下降。

✓ 1次/秒速率限制 ✓ 200条会话总上限 ⚡ 单字消息有兜底意图 ✗ 消息最小长度校验 ✗ Token 消耗预算上限 ✗ 短消息聚合/debounce
P1 缺口：无消息最小长度 + 无 Token 消耗上限 高优先级

最简单的补丁：在 InputGuardrail.inspect() 之后添加 min_effective_chars 校验（建议 2-4 字符），空消息或单个标点直接返回"请描述您的问题，例如：退款咨询"。更完整的方案是在 Settings 中引入 per_session_token_budget: int = 500_000，在 Worker 完成每次 LLM 调用后累加 Token 到 Redis key，超限后降级为 FAQ 快速路径或提示今日咨询配额已用完。

边缘案例分析 · 03

同一个问题反复问好几遍

🔁 场景：用户反复问"我的退款什么时候到账"（或稍微改写后重问）

现有防护相当完善：这是三个场景中项目处理最好的一个。

完全相同的问题会命中 faq_exact_cache（6小时 TTL）或 RAG 语义缓存（30分钟 TTL），直接短路返回缓存回答，不触发 LLM。recent_intents 被用于意图延续检测：连续相同意图会触发 HANDOFF_SUGGESTED 状态，系统在回答末尾追加"如仍未解决，可以回复'转人工'"的建议文案。agent_support_summary_limit=12 记录历史支持摘要，多次重复问题会被汇总到支持工单里。

剩余漏洞：语义缓存基于向量相似度，微小改写（"退款何时到账"→"什么时候到账退款"→"退款到账要多久"）可能绕过缓存，每次都进 RAG + Rerank + LLM 完整流程。目前没有明确的"您在过去 X 分钟内已经问过 N 次类似问题"的检测和响应策略，只有连续相同意图的软性提示。

✓ FAQ 精确缓存（6h） ✓ RAG 语义缓存（30min） ✓ 连续意图触发转人工建议 ⚡ 改写变体绕过缓存 ✗ 明确的重复问题计数+响应策略
建议补充：轻量重复问题检测 中优先级

在 agent_service.py 的意图解析前，检查 Redis 中 recent_intents 是否连续 3 次以上为同一意图（比 HANDOFF_SUGGESTED 当前的触发条件更直接），且时间窗口在 10 分钟内。若满足，直接跳过 LLM 推理，返回预设的"您的问题正在处理中，如需更快响应请转人工" + 强制推送工单创建 CTA。这样既节约 Token，又给了用户明确的行动路径。

缺口评估

分级缺口：P0 须上线前修复，P1 须上线后 30 天内修复

P0 · 单会话 Token 消耗无硬性上限 P0 · 严重

当前只有消息条数上限（200条）和 ReAct 轮次上限（5次），但没有按 Token 计量的消耗上限。一个精心构造的请求（超长输入 + 触发多次工具调用链）单次可消耗 20,000+ Token，乘以 200 条上限理论上可达 400 万 Token。按 DeepSeek-Chat 当前价格，单用户上限内可消耗约 ¥2。看起来不多，但在促销期并发千人时就是 ¥2000+/小时的 LLM 账单。

这是"Denial of Wallet"攻击的直接入口。攻击者不需要绕过任何安全检查，只需要正常登录后反复发送能触发长 ReAct 链的问题。

修复方向：引入 per_session_token_budget + 每日 daily_token_quota（Redis 计数），超限降级到 FAQ 快速路径。
P0 · 无消息最小长度校验（单字/空消息穿透） P0 · 严重

input_guard.normalize() 压缩空白后如果内容为空会走到 task_text = "查找图中同款或相似商品" 这个默认分支（非图片时，空消息在 agent_service.py:102 被 raise ValueError 拦截），但 1-3 字符的消息（"？"、"嗯"、"呢"）不会触发任何长度校验，会完整进入 intent 分类 + RAG + LLM pipeline。

修复方向：在 InputGuardrail 增加 min_effective_chars: int = 3 配置，低于阈值返回引导文案而非进 pipeline。
P1 · 知识库文档入库时无注入预扫描 P1 · 高

channel_guard.py 在检索时扫描 RAG 片段，这是"查询时检疫"。但被污染的文档已经进了 Elasticsearch 索引，每次检索都要过滤它。更好的策略是在管理端上传文档时（Java 侧 upload 接口或 Python 侧的索引 Worker）做一次预扫描，被标记为污染的文档拒绝入库 + 告警管理员。减少查询时的计算开销，同时将"被注入文档"这一事件提前可见。

修复方向：在 RabbitMQ 索引 Worker 消费文档前调用 scan_external_content()，污染判定为 True 时拒绝入库并发 structlog WARN + Prometheus counter。
P1 · WebSocket 路径缺少与 REST 路径等效的输入验证 P1 · 高

app/api/websocket.py 存在但未能确认是否复用了 InputGuardrail。如果 WebSocket 消息绕过了 input_guard.inspect()，所有注入检测、长度限制、Token strip 都失效。这是防护体系中最危险的不一致点。

修复方向：在 WebSocket 消息处理函数的入口处显式调用 input_guard.inspect()，与 agent_service.send_message() 保持同样的检查栈。
P1 · IP 级限流缺失（用户级限流可被多账号绕过） P1 · 高

当前 rate_limit_service 以 user_id 为 key。如果攻击者批量注册账号（或使用泄露的账号），可以绕过单用户限流。Gateway 层有 AuthGlobalFilter 和 InternalTokenGlobalFilter，但未见基于 IP 的滑动窗口限流。在公网环境下，这是分布式 DoW 攻击的入口。

修复方向：在 Spring Cloud Gateway 层添加基于 IP 的 Redis 限流（Spring Cloud Gateway RateLimiter 内置支持）；对异常高频 IP 触发 CAPTCHA 或临时封禁。
P1 · 会话压缩锁为乐观锁，高并发下可能多次触发压缩 P1 · 中

session_memory_service.try_acquire_compress_lock() 用 Redis SET NX 实现，TTL 60 秒。如果 Memory LLM 超时（>60秒），锁释放后第二个 Worker 会重新触发压缩，导致两次 Memory LLM 调用并发写入。压缩失败时也没有记录"本次压缩失败，使用上一次压缩结果"的 fallback 路径，可能导致 Token 持续膨胀直到 OOM。

修复方向：在 memory_llm_timeout 之外为压缩任务单独设置 deadline；压缩失败时记录 WARN 并在下一轮次重试，而不是让 Token 静默累积。
P2 · 商品数据幻觉无结构化防护 P2 · 中

output_guard.py 防止了"声称已执行操作"类幻觉，但没有覆盖"编造商品价格/参数/库存状态"类幻觉。如果 RAG 证据不足（rag_evidence_min_relevance 阈值以下），模型可能用训练数据中的"通用商品知识"来填充回答，给出不准确的价格或规格。

修复方向：在证据不足时（拒答逻辑）明确告知用户"暂无该商品的准确信息，请查看商品详情页"，而非让模型自由生成。这需要将 _has_enough_evidence 的判断结果更显式地传递到 system prompt 的引导词。
P2 · 无跨用户行为模式检测 P2 · 中

当前观测是单用户视角（Episode per run_id）。没有跨用户的异常模式检测：例如 100 个账号同时问同一类触发长 ReAct 链的问题（协调攻击），或 1 个账号在不同时间段累计发送了 5000 条历史消息后新注册的账号接续之前的攻击模式。这类攻击在限流和单用户配额体系下无法被检测。

Redis 固定窗口限流（rate_limit_service.py） 已实现

配额存储在 Redis，通过 EVAL 脚本原子完成计数 + TTL 设置，多 uvicorn worker 进程共享同一配额——解决了进程内计数器在多 worker 下实际倍乘的经典陷阱。

已覆盖的接口：sendMessage（1次/1秒）、confirmAction（1次/3秒）、cancelAction（1次/3秒）。

LLM 熔断器（circuit_breaker.py） 已实现

标准三态（CLOSED / OPEN / HALF_OPEN），连续失败 5 次开路，60 秒后半开探测。HALF_OPEN 状态只允许单个探测请求，探测超时（30秒）后自动回收探针位，防止因调用方崩溃导致熔断器永久卡死。状态指标通过 CIRCUIT_STATE Prometheus gauge 实时暴露。

用户锁 + 任务队列 + 优先级 已实现

agent_user_lock_ttl_seconds=180 防止同一用户并发提交多个任务。RabbitMQ 三级队列（HIGH/FAST/LOW）按意图类型路由，售后投诉走高优先级，避免闲聊阻塞紧急工单。任务有 lease 机制（30秒），Worker 崩溃后其他 Worker 可在 deadline 内接管。
